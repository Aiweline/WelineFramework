# 优化审查：请求上下文冻结与哈希层重复计算

> 状态：审查结论已核实，**未动任何缓存键代码**（等范围确认）。
> 来源：会话 7c0472d6（2026-10-05），两份全仓普查 + 本人逐处 file:line 复核。
> 根因一句话：**框架冻结了"值"，没冻结"由值导出的哈希"**。

## 一、对早期版本的修正

路径解析、lang/currency 收口（原 P0-1/P0-3）**成立但都是微秒级**：

- `State::resolveLocalizationFromPathSegments` 每次约 2µs；全站 23 个调用点合计每请求 <50µs。
- `Env::getAreaRoutePrefix` 的 80+ 处调用只是 `explode('.')` + 3 次数组查找。

这些该收口的理由是**一致性**（同一事实多处独立求值会串判），不是算力。真正的重复计算在**哈希层**。

## 二、已核实的高价值重复点（按收益排序）

### 1. 命名空间指纹：每请求 ~42 次 SHA-256，其中 21 次纯浪费

- `NamespaceGenerationSnapshot::resolve()`（Framework/Cache/Namespace/NamespaceGenerationSnapshot.php:37-85）确实把代际向量按 requestId 冻结——这点正确。
- 但 `NamespaceKeyDecorator::fingerprint()`（Framework/Cache/Namespace/NamespaceKeyDecorator.php:14-30）对 N 个 namespace 逐个 `hash('sha256',$ns)` 再末尾一次，**无任何 memoize**。
- `StorefrontCacheKeyContextResolver::fingerprintForIdentity()`（Framework/Cache/StorefrontCacheKeyContextResolver.php:131-133）在 `freezeCurrent` 里已算过一次并塞进不可变上下文；随后 `StorefrontScopeHotCache::policyKey()`（Framework/Cache/Service/StorefrontScopeHotCache.php:361）每个缓存读又走 `generations->fingerprint()` 重算同输入。
- N≈20 ⇒ 冻结时 21 次 + 之后每次读 21 次。

### 2. L1 命中也白烧全量指纹（最干净的一个缺陷）

- `StorefrontScopeHotCache::rememberPolicy()` 在 **:101** 就调 `policyKey()`，而进程 L1 查询在 `rememberKey()` 的 **:411**。
- 即**即使缓存命中，仍然付完** `namespacePaths()`（含 new NamespacePath + canonicalize）+ 21 次 sha256 + `KeyBuilder::policyKey` 再一次 sha256。
- 纯顺序错误。修法：scoped key 按 `(resource, logicalKey)` 请求内 memo，或延到 L1 miss 之后再算。

### 3. 模板编译作用域：每渲染一个 Block 重做一遍

- `Template::convertFetchFileName()`（Framework/View/Template.php:785-793）每次都跑 `viewEnvironmentCacheSuffix()` + `resolveThemeCacheKeyForFetchFile()` + `templateCompileScopeMapKey()`。
- 后两者内部各触发一次 `hooksRegistryCompileDigest()`（TraitTemplate.php:855-863，**is_file+filemtime+filesize 三个 syscall**）和一次主题事件 dispatch（:828，`new DataObject` + `dispatch('Weline_Framework_View::resolve_theme_cache_suffix')`，Theme 观察者里还额外 `md5($filename)`），最后 json_encode + sha256。
- 一页几十到上百 Block ⇒ **syscall 与事件派发按 Block 数放大**。
- 更糟：`processViewFileCache` 缓的是最终路径映射，而 key 本身就是上述哈希的产物——**命中也要先把 key 算完**。该作用域一请求内恒定，属最典型的"该进上下文却没进"。

### 4. FPC 键链：同请求同输入算 3~6 遍

- `getCacheKeyFullUri()`（FullPageCache Coordinator:5132）无 memo，15 处调用各自重跑 parse_url + query 过滤。
- `hash('sha256',$fullUri)` 作为回执索引，在单次快路径里被 4-5 个 resolver 分别重算（WorkerFullPageCacheFastPath:112-155）。
- `FpcPolicySnapshot:68` 的 policy_fingerprint 在探测/锁/发布/stale 各算一次。

### 5. 翻译回退链：冻结算了没人用

- 上下文构造时已产出 `translationLocales`（StorefrontCacheKeyContext:37-38，Resolver 显式传入避免二次 candidates）。
- 但 `Phrase/Parser::localeChain()`（:1157-1160）有 10 个调用点，每次重跑 `candidates()` + `websiteDefaultLocale()`（后者遍历 3 个 config key + 正则），且 :985 与 :996 在同一次构建里各算一遍。
- **现成正确样板**：prefetch 路径 :1836-1839 先读 `current()->translationLocales`，照抄即可。

### 6. Url::parser()：命中路径也不敢信缓存（补丁套补丁）

- `$parserCache`（Url.php:1948）按 URI 键控、:2292 写入，每请求只真解析一次；:2298-2312 的 scratch-state save/restore 保证模板生成他链不污染当前态。**它不是重复解析源。**
- 但 :1937 / :1951 每次**命中**都要过 `rehydrateVisitorLocaleOnParseResult()` → 无条件 `lockVisitorFacingRequestUri($visitorUri)`（:318）→ :295-302 再做一遍 `explode + array_filter + resolveLocalizationFromPathSegments(array_slice(segments,0,4))`。
- 源码注释自证："Cached parse results predate PATH_LANG / pretty ORIGIN fixes"——因为作用域没冻结，缓存结果不敢信，每次命中重验语言。**值缓存了，从值导出的校验还在重算。**
- 循环放大：LanguageSwitcher（:1327 foreach 内 :1344）= O(候选语种数) 次切分；`CustomerAuthReturnUrlService.php:315,367,389,399` 同形态。仍属微秒级，定性为一致性问题。

## 三、落地顺序（按改动风险 × 收益）

| 步 | 动作 | 为什么这个位置 |
|---|---|---|
| S1 | `rememberPolicy` 把 `policyKey()` 挪到 L1 判定之后 / 加 `(resource,logicalKey)→scopedKey` 请求内 memo | 单函数内改动、零语义变更、命中路径哈希直接归零 |
| S2 | `NamespaceKeyDecorator::fingerprint` 加 `(namespace→sha)` 进程表 + 整向量结果 memo | 纯函数，可单元断言同输入同输出 |
| S2.5 | `parser()` 命中路径把 visitor-facing locale 冻结进解析结果，去掉每次命中的 re-literalize + 重新切段 | 前提是作用域已冻结，必须排在 S1/S2 后 |
| S3 | 模板 compile-scope（theme suffix + hooks digest + environmentHash）请求内算一次挂 RequestContext | 收益随 Block 数放大，页面级最大项 |
| S4 | Parser `localeChain()` 优先读冻结 `translationLocales`（照抄 :1836 样板） | 有现成正确样板，风险低 |
| S5 | FPC canonical URI / receipt index / policy fingerprint 随作用域冻结一次写入共享 | 涉及建锁与发布一致性，单独验 |
| S6 | 路径维度与 area 前缀纳入 `RequestRoutingContext` | 目的是**消除串判风险**而非提速，放最后，别抢性能叙事 |

## 四、验收门禁（S1–S5 全部触碰缓存键，不能省）

键一变即全库 miss；两处派生不一致会出现"写在一个键、读在另一个键"的静默失效——本仓已有前缀 URL 永久 STALE 先例（见 memory: project-wls-prefixed-url-stale-lock）。

1. **基线**：真实首页 + 商品页各测一轮，统计每请求 `resolveLocalization*` / `fingerprint` / `hooksRegistryCompileDigest` / `environmentHash` 调用次数与总耗时（计数器，非猜测）。
2. **反证（防误报）**：改造后必须证明**同请求同输入产出的键逐字节相同**——用现有 `StorefrontCacheKeyContextTest`、`FullPageCacheCoordinatorTest`、`TemplateCacheManagerEnvironmentKeyTest` 加断言锁定键值，而不是只跑绿。
3. **端到端**：WLS reload 后 FPC HIT 率不降、STALE 不累积、页面 HTML diff 为空。
4. **S2.5 附加回归**：`/USD/en_US/x`、`/en_US/USD/x`、无默认前缀三种 URI 在 FPC 探测与 `route()` 两处派生的 lang/currency 完全一致（可扩展 `StateTest.php:137,141` 形状断言）。
5. 任一环节量不出边界，退回人工签收留痕，不留"大概没问题"的缓存改动。
