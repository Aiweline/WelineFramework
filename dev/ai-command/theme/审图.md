# MCP 指令：审图

**触发词（任一即执行，无需再确认范围）**

- `审图`
- `审查图`
- `UI 审图`
- `screenshot review`
- `发图即审`
- `附图`
- `截图审查`

**硬触发**：用户消息里只要出现**图片/截图附件**（粘贴图、Browser 截图、验收截图）——**含后台 Admin / CMS / 错误页 / 店面，不限零售/B2B**——即执行本指令——**不必**再说「审图」。MCP 硬规则 id：`user_image_attachment_triggers_shentu`；`prepare_project.agent_guidance.mcp_skills.image_attachment_shentu_bundle`。

### 仅附图 / 截图不说（硬默认）

用户消息**只有截图**、几乎无文字，或仅有红箭头/圈注/「？」时：

1. **默认意图 = 审查附图可见 UI 的人性化 + 规范美观审美 + 原型逻辑状态**（齐读 `frontend-design` + `prototype` + 主题技能），**不是**确认上一话题、不是闲聊插图、不是「用户在举证业务结论」。
2. 有箭头/圈注 → **优先**审被指控件的布局层次、信息密度、主次 CTA、状态一致性（例：地址栏 URL vs 表单检测 URL）。
3. 禁止因「像在确认默认布局/像在跟上下文」而跳过 E/F，或只口头对齐业务而不改丑点/逻辑 fail。
4. 判定为 `web_ui` 后：**先列 E/F/G fail → 再改码 → Browser 禁缓存验收**；不得先写「这张图说明…」就收口。

Agent 必须把本文件当作硬指令执行：先**判定图类型**，再按分支审查；若属本仓 Web UI / 前端图，对照**需求**、**主题技能**、**原型技能**、**UI/frontend-design 技能**审查并**找出问题后修改**，禁止只口头点评。审查维度必须覆盖**人性化**、**规范美观审美**、**与当前主题的契合**——凡这三项（或检查清单其它项）fail，**必须调整代码/样式到 pass**，不得以「仅供参考」收口。禁止因「还在查别的 bug」或「用户没说审图」而跳过本指令。

## 图类型分流（先做）

对每张图给出：`web_ui` | `frontend_candidate` | `non_frontend`。

| 判定 | 依据（任一即可） | 处理 |
|---|---|---|
| **web_ui** | 浏览器窗口/地址栏/`*.test.weline.com`/`*.weline.test`；店面顶栏/迷你车/PDP/结账/账户；后台 Admin 布局；可见 Weline UI 控件（`w-` 表单、抽屉、segment、胶囊规格等） | **按本指令 Web UI 约定全流程**（必读三技能 + 检查清单 + 能修则修） |
| **frontend_candidate** | 疑似本仓前端（模块 UI、部件局部、主题编辑器、组件态），但无完整浏览器框 | **自行识别**：对照已知模板/CSS/部件命名与布局习惯；**确认是本仓前端** → 升为 `web_ui` 约定；**无法确认** → 写明不确定点，只列可疑项，不擅自大改 |
| **non_frontend** | 示意图、竞品截图、设计稿、照片、日志/终端、架构图、非本仓产品 UI 等 | **不要**套用店面 Theme 修复流程；简述「非本仓 Web UI」与是否可作参考；除非用户明确要求对照改代码，否则不改生产 |

多图：逐张分流；至少一张为 `web_ui` / 确认的前端图时，本回合进入修复流程。

## Web UI 审查对象（默认）

用户未限定时，优先审查附图中的控件；附图为迷你车 / 购买方式 / 账户批发身份等时，默认覆盖：

| 面 | 典型表面 |
|---|---|
| 零售 ToC | 迷你车顶栏副标、抽屉「零售车」、PDP 购买方式「零售」 |
| B2B ToB | 抽屉「批发车」、PDP「批发」、申请抽屉、账户「批发身份」 |
| 其它店面/后台 | 附图实际露出的 Theme / Taglib / 账户 / 结账等表面 |

## Agent 必读技能（Web UI / 已确认前端图）

凡判定为 Web UI 或确认本仓前端图，写样式/改 UI 前必须齐读：

1. `weline-theme-development`（MCP `get_skill`；主题 Token / Taglib / 禁止私造色板）
2. `frontend-design`（构图层次、视觉克制、文案语气；本仓必须服从主题 Token）
3. `prototype`（抛出原型：对照已选 variant / 结构语义；**不要**把原型 throwaway hex 粘进生产）
4. `local-browser-urls`（验收 Host / 禁缓存 / 交付后关 Browser）

### 宿主 UI / 原型技能门禁（硬）

进入 Web UI 审图（含 E/F）前，必须核对本回合 **Agent Skills / available_skills** 是否同时具备宿主技能：

| 角色 | 宿主技能名 | 缺失时 |
|---|---|---|
| UI | `frontend-design` | 见下方「缺失提示 + 自行处理」 |
| 原型 | `prototype` | 见下方「缺失提示 + 自行处理」 |

主题技能 `weline-theme-development` 以 MCP `get_skill` 为准（宿主薄壳可选）；**不得**用「主题技能已读」替代 UI/原型技能。

**缺失提示（必须对用户可见写出，禁止静默跳过）**：

```text
⚠ 审图依赖技能缺失：缺少「UI 技能 frontend-design」和/或「原型技能 prototype」。
正在自行安装/挂载到本机 Cursor Agent Store；补齐并 Read 正文前，不得对 E（人性化）/ F（规范美观）写 pass。
```

**自行处理（Agent 立刻做，勿把安装甩给用户）**：

1. 若本机已有源：`~/.cursor/skills/{frontend-design,prototype}/` 或 `~/.agents/skills/...` → **复制/同步**到用户 Cursor Agent Store：`…/AgentStores/…/files/skills/{name}/`（与 `weline-ui-shentu` 同级）。
2. 若源也不存在：从本仓已知权威副本或既有技能树恢复 `SKILL.md`（及 `LOGIC.md`/`UI.md` 等附属文件）；禁止空壳占位。
3. 安装后 **立即 Read** 缺失技能全文；汇报「审图结论」时注明「本回合曾缺失并已自行补齐：…」。
4. **禁止**：缺技能仍对 E/F 写 pass；禁止只提示用户去 Settings 手工装而不自行处理。

**审美与人性化判定（硬）**：E/F/G 三项不得凭「感觉」空写 pass。必须显式用上述 **UI（frontend-design）** 与 **原型（prototype）** 技能的原则做对照，并用 **主题技能** 核对 Token/组件契合；任一 fail → 调整到 pass 再验收。

权威主题细则：`app/code/Weline/Theme/doc/theme-css-variables-only.md`；相关 PDP/部件样式以源码为准。

## 审图检查清单（Web UI：必须逐项 pass / fail + 证据）

### A. 需求对齐

- [ ] 相关 `doc/需求.md` 条目描述的交互是否在图中出现
- [ ] 是否出现需求禁止项

### B. 主题 / Token / 配色

- [ ] 选中/强调色是否走当前站点品牌 Token（`--color-primary` / 抽屉已用 token 等）；禁止另套无关 chrome 色或「实心深底 + 黑字」乱配
- [ ] 文字与背景对比度可读
- [ ] 颜色/间距/圆角是否走 `--weline-theme-*` / `--color-*` / 局部约定 token；禁止无必要硬编码 hex
- [ ] 文案是否 `<lang>` / i18n
- [ ] **分车 UI 归属**：零售/批发双车切换由 **B2B 模块 JS** 注入；Theme 迷你车无 B2B 时仍可独立零售
- [ ] 分车/模式切换后摘要与行项目必须换实体或空态，禁止错误缓存串态

### C. 原型功能设计

- [ ] 已选型原型结构是否保留
- [ ] 控件语义（切换 vs 装饰）与原型 verdict 一致
- [ ] 空态 / 游客 / 申请入口反馈合理（不整页乱跳）

### D. UI / 层次

- [ ] 主信号与次要信息不抢视觉
- [ ] 无多余卡片/徽章堆叠

### E. 人性化（须对照 `frontend-design` + `prototype`）

- [ ] 相关控件是否分组：设置 vs 主操作是否混在同一无层次扁平行里抢注意力
- [ ] 危险/高风险操作（如正式环境调试）是否与日常导航/登录有清晰间距与语义隔离
- [ ] 控件垂直对齐、触控/点击目标高度是否一致（同排 `select` / `switch` / `button` 共用控制高度 token）
- [ ] 文案是否用户能懂（非系统内部黑话堆砌）；同一动作命名前后一致
- [ ] 空态/错误/开关反馈是否告诉用户「发生了什么、下一步做什么」

### F. 规范美观审美（须对照 `frontend-design`；视觉字面量仍服从主题 Token）

- [ ] 间距节奏是否用主题 spacing token，同排控件 gap 均匀；组间间距大于组内
- [ ] 圆角/描边/阴影是否与周围 Weline UI 2.0 组件一致，无「一套控件多种视觉方言」
- [ ] 是否落入通用 AI 默认审美而不契合本页任务（无必要奶油底+赤陶强调、无意义卡片墙、全大写 eyebrow 堆叠等）——**主题品牌 Token 合法时不算违约**
- [ ] 装饰不抢主任务；一屏内主 CTA 通常一个主色实心，次要动作用 neutral/outline

### G. 主题契合（须对照 `weline-theme-development`）

- [ ] 是否复用 `w-button` / `w-select` / `w-switch` / `w-cluster` 等既有组件，而非私造平行控件皮
- [ ] 强调色、画布、表面、边框是否来自当前站点 `--weline-theme-*` / `--color-*`
- [ ] 禁止为「好看」另发明 hex/rgb 色板或 px 间距阶梯

## Agent 必做流程

1. **读图**：用 Read 打开每一张附图；完成分流表（`web_ui` / `frontend_candidate` / `non_frontend`）。
2. **非前端**：汇报分流结论后结束（或仅作参考对照）；不强制 MCP 修码。
3. **Web UI / 确认前端**：
   1. `ensure-project-guidance` → `prepare_project` → `submit_task_plan`（目标含「审图修复」）
   2. **技能门禁**：检查 `frontend-design` + `prototype` 是否在本回合可用；缺失则按上文提示用户并自行安装/挂载，再齐读三技能（+ local-browser-urls）
   3. 对照检查清单（含 E 人性化 / F 规范美观 / G 主题契合）列出 fail 项；E/F 须引用 UI+原型技能原则，G 须引用主题技能
   4. 读相关模块 `doc/需求.md` / 源码并修改 fail 项；主题 Token 优先；审美 fail 同样必须改到 pass
   5. Browser **禁用缓存** → 验收 Host → `curl` 探活
   6. 模块 `开发日志.md` 记审图结论
   7. 按模板汇报；写完「交付地址」后关闭验收 Browser

## 非目标

- 不对 `non_frontend` 图强行套店面 Theme 修复
- 不重做未选型的整页视觉改版（但清单 fail 项必须修到 pass）
- 不把原型 HTML 原样并入生产
- 不改 `generated/`、`view/tpl`
- 不扩大到无关模块（除非审图发现同源主题违约）
- 不以「审美主观」为由跳过 E/F/G；缺 UI/原型技能对照写 pass 视为违规
- 不把「缺 frontend-design / prototype」只当口头警告却不自行安装；也不要求用户去 Settings 手工挂载后才继续
