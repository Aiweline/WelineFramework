# MCP 指令：需求澄清与用例规格

**触发词（任一即执行）**

- `需求澄清`
- `澄清需求`
- `用例规格`
- `用例设计`
- `写用例`
- `EARS`
- `clarify`
- `use case`
- `use-case`
- `speckit`
- `kiro`
- `规格澄清`

**硬触发（不必用户再说「澄清」）**：任意**可执行编码/工程需求**（`work_kind=feature`，或用户一句话要做功能/改业务行为）在写码与架构落笔前，Agent **必须**执行本指令（MCP 硬规则 `requirement_clarify_use_case_spec`）。`non_feature`（纯文档/门禁/基建）可写 `clarify_status=skipped` + ≥24 字理由后跳过正文产出。

权威：`app/code/Weline/Ai/doc/AI工程交付流程.md` §1；硬规则索引同 id；MCP skill / surface：`requirement_clarify_use_case`（别名 `weline-req-clarify`）。

---

## 目标（Kiro / Spec Kit 形态，贴合 Weline）

把用户一句话变成**可测试规格**，再进入你们已有的架构计划 → e2e → 交付地址：

1. **澄清（Clarify）**：定向追问模糊点，答案写回规格  
2. **需求 + 验收标准（EARS）**：用户故事 + WHEN/IF…SHALL  
3. **用例（Use cases）**：主成功路径 / 备选 / 异常，直接喂给 `acceptance`（尤其 `type=e2e`）与 Browser 操作员用例  

**禁止**：跳过本指令直接改业务码；把假设当需求；只写散文验收而无 EARS/用例；feature 无持久化规格文件。

---

## 产出物（必须落盘）

路径：

```text
app/code/{Vendor}/{Module}/doc/开发/spec/{feature-slug}.md   # 耐久规格（模块 doc）
dev/session/{feature-slug}.md                               # SESSION 总控（仓库根 dev/；禁入模块 doc）
```

- `{feature-slug}`：kebab-case，可含 ticket 前缀（如 `gh-47-hang-balance`）。  
- 同功能已有草稿则**续写/更新**，禁止平行再开一份无关联文件。  
- 临时会话笔记不算完成；**必须**写入上述路径（宿主原生 Write）。  
- 模块尚无 `doc/开发/spec/` 时先建目录；SESSION 写 `dev/session/`（`module_doc_forbids_ephemeral_work_artifacts`）。  
- **SESSION stub（硬，`requirement_session_dashboard`）**：feature 澄清落盘同回合，按 [templates/requirement-session.md](./templates/requirement-session.md) 建/更新同 slug 的 `dev/session/{slug}.md`（`wave=clarifying`，计划项 `main`=`open`）；仅项目经理/监工维护；明细在 `dev/team/{slug}/`。`non_feature` 若跳过澄清正文，仍建议建 SESSION 标 `status=open` 与缺口，或写 `session_status=skipped` + ≥24 字理由。

文首 YAML（推荐）：

```yaml
---
status: draft | clarified | ready-for-plan
work_kind: feature | non_feature
feature_slug: example-slug
module: Weline_Example
updated: YYYY-MM-DD
session_path: ../session/{feature-slug}.md
---
```

`ready-for-plan` 之后才允许进入架构映射 / 写码（见硬规则）。

## Agent 必做流程

### 0. 取技能正文（可选但推荐）

```text
get_skill(skill_id=requirement_clarify_use_case)
# 或 weline-req-clarify
```

同时可 `resolve_task_context` 取模块 `doc/需求.md` / 代码地图，**禁止**用通用框架经验发明业务规则。

### 1. 澄清（Clarify）— 像 Spec Kit `/clarify`

1. 先据用户原话草拟「目标 / 非目标 / 角色 / 成功标准」草稿（可先写进文件 `status: draft`）。  
2. 扫描模糊点，按优先级追问（**一次最多 5 题**，编号列出；用户答完再继续）：  
   - 范围与非目标  
   - 角色与权限  
   - 主路径 vs 边界（空态/失败/并发/权限拒绝）  
   - 数据归属与是否动 schema  
   - 前台 / 后台 / API 哪侧可见  
3. 将 Q&A 写入规格 **「澄清记录」** 节；改写正文需求。  
4. 与框架审视并行：不合理字面需求写入后续 `requirement_scrutiny`，本规格先记「待纠偏」点。  
5. 澄清足够后设 `status: clarified`。

**禁止**在关键问题未回答时假装已澄清并开写码。

### 2. 需求规格 + EARS

每个需求块必须含：

- **用户故事**：As a [角色], I want [能力], so that [收益].  
- **验收标准（EARS，≥2 条）**，优先：  
  - `WHEN [事件] THEN [系统] SHALL [可观察响应]`  
  - `IF [前置] THEN [系统] SHALL [行为]`  
  - `WHILE [状态] [系统] SHALL [行为]`  
- **隐形需求摘要**：对齐 `implicit_requirements`（环境已有 Taglib/表/映射页等）。  

聚焦 **what**，不写具体类名/补丁步骤（how 留给架构阶段）。

### 3. 用例设计（喂 e2e / Browser）

至少 **1** 条主成功用例；feature 且含 Web 时建议 ≥2（含一条异常/权限失败）。每条用例：

| 字段 | 要求 |
|------|------|
| id | `UC-1`… |
| 名称 | 短标题 |
| 角色 | 谁操作 |
| 前置 | 登录态/数据前提 |
| 主成功步骤 | 有序、可点选/可断言 |
| 备选/异常 | ≥1 条或写「无」 |
| 期望结果 | 可观察 |
| 映射 acceptance | 对应计划里 `type=e2e` / Browser WB-OP 用例 id |

Web 用例步骤须能直接改写成 Playwright / Browser 操作员路径（URL + 步骤 + 期望）。

### 4. 门禁自检（写进规格末尾「就绪检查」）

- [ ] `status` ≥ `clarified`（进入计划前升到 `ready-for-plan`）  
- [ ] ≥1 用户故事 + 每故事 ≥2 条 EARS  
- [ ] ≥1 用例（含主成功路径）  
- [ ] 非目标明确  
- [ ] feature：已点名将产生的 `type=e2e` / `e2e-plan-suite` 验收意图  
- [ ] 未把架构实现细节写进本规格正文  

全部勾选后 `status: ready-for-plan`，再进入：

1. **宿主计划模式（默认硬，`host_plan_mode_for_planning`）**：Cursor `SwitchMode` → `plan`；**简单需求**可 `plan_complexity=simple` + 理由≥24 跳过 Plan Mode。  
2. **计划正文（硬，`plan_content_focus_only`）**：只写 **背景 / 方案 / 细节**；禁止无关描述把主题带偏。  
3. **前后端范围**：记录 `fe_be_scope`。  
4. 框架审视 → `architecture_design` → 分章计划（非简单）。  
5. 实现后：**一定验收**——Web 须本机 Browser WB-OP（视觉+逻辑）；非简单再跑 e2e；布局/吐槽/审图时原型+UI 必须调整。

禁止跳过验收宣称完成；跳过计划 ≠ 跳过验收。

### 5. 向用户汇报（澄清回合）

```markdown
## 需求澄清
- 已追问 / 已确认要点…
- 规格路径：`app/code/.../doc/开发/spec/{slug}.md`
- status: clarified | ready-for-plan

## 用例规格摘要
- UC-1 …
- EARS 要点…

## 下一步
启用宿主计划模式（Cursor：SwitchMode→plan），进入架构映射与计划（尚未写业务码）。
```

**交付地址**：本阶段通常 N/A（无 UI 交付）；若仅澄清文档则写 N/A。

## 与现有硬规则的衔接

| 本指令产出 | 后续硬规则 |
|------------|------------|
| 澄清后的需求正文 | `requirement_framework_scrutiny` / 「需求纠偏」 |
| 隐形需求摘要 | `requirement_implicit_analysis_skill_decision` |
| `ready-for-plan` | `host_plan_mode_for_planning`（Cursor SwitchMode→plan） |
| 用例 → e2e 步骤 | `ui_feature_requires_e2e` / `plan_full_pathway_e2e_suite` / Browser WB-OP |
| 规格落盘 | `docs_reconcile_on_closeout`（收口时规格与实现对照） |

本指令 **不替代** 架构映射、e2e、汇审、交付地址；只补齐 Spec Kit/Kiro 式「澄清 + 用例规格」层。

## 反例（禁止）

- 用户说「加个批发价」→ 直接改 PHP  
- 只写「应正确显示价格」而无 EARS  
- 用例只有「打开页面看看」无可断言步骤  
- 规格写在聊天里不落 `doc/开发/spec/`  
- feature 标 `clarify_status=skipped` 却无充分理由
