# 回灌（核心修复 → 合入推送 → 站点回灌 → 验证）

## 口令语义（硬）

用户说 **「回灌」**，即明确授权：

1. 在**框架仓**修复本任务真正需要的 `app/code/Weline/**`（及任务相关的 `pub/errors` 等核心路径）；
2. 按框架仓 Git 约定提交 / 合并 / 推送（仍须用户已授权或口令上下文覆盖的 commit/push 范围；见下文「Git」）；
3. 用 `php bin/w update:core`（或 `core:update`）把线上 tip **回灌**到当前消费站点；
4. 在站点侧做足以证明修复的验证（本地 + 任务范围内的线上）。

**近似词不算授权**：`改核心`、`修框架`、`同步核心`、`update:core`、`合并到框架`、`分项` 等**不**单独等于「回灌」。

## 前置闸门（缺一不可）

| 条件 | 不满足时 |
|---|---|
| 当前会话/工作区**已给出框架仓**（路径或可写 clone，如 `/Users/weline/Project/Official/框架`） | **禁止**本流程；在消费仓只汇报，不改 `Weline/**` |
| 用户本轮（或明确延续的授权）出现精确口令 **「回灌」** | **禁止**改核心、禁止主动回灌 |
| 缺陷/需求确实必须动核心（Event / Interface / Hook / 应用模块无法解决） | 先说明为何必须动核心；能应用侧解决则不要回灌 |

> 消费仓（如 ManyCartSync）默认 `Weline/**` 只读。看见「回灌」= 允许按本技能在**框架仓**改核并回灌验证，**不是**允许在消费仓直接改 `weline/app/code/Weline/**` 当长期源。

## 与相近口令的区别

| 口令 | 做什么 |
|---|---|
| **回灌** | 修核心（框架仓）→ 合入推送 → `update:core` 进当前站点 → 验证 |
| **分项** | 把已有核心分支分发到脚本配置的多站点（见 `CI发布工程师-分项更新`）；不隐含「可以改核心」 |
| **分仓** | 分仓发布流程；与回灌无关 |
| §7 跨仓对齐提示 | 改过 `Weline/**` 结案前必须提示合并；**不等于**已授权回灌 |

## 可执行流程

### A. 框架仓修复

1. 工作目录切到框架仓：`/Users/weline/Project/Official/框架`（或用户给出的等价路径）。
2. 分支：只在 **`dev`** 上改代码（见 `global-constraints.md` §7 Local branch policy）。
3. 只改本任务需要的核心文件；更新所属模块 `doc/需求.md` / `doc/开发日志.md`（若适用）；补聚焦单测。
4. 在框架仓跑通相关单测 / 最小复现证据。

### B. Git（框架仓）

口令「回灌」同时授权完成本流程所需的 **commit + merge `master` + push 到已配置 remote（通常 Gitee `origin` + GitHub `github`）**，范围仅限本任务核心改动。

1. `dev` 上只 stage 本任务文件；审查 staged diff；不含密钥与无关脏文件。
2. Commit（信息说明 why）。
3. `checkout master` → merge `dev` → push `origin`/`github` 的 `master` 与 `dev` → 回到 `dev`。
4. 记下 tip（例：`ef5ab89f`）供回灌与报告。

若用户明确说「先别推 / 只合本地」，则缩小到其口头范围。

### C. 站点回灌（`update:core`）

在**当前消费站点**的 `weline/`（或站点根）执行：

```bash
php bin/w update:core -b master
# 若冲突检测报「本地核心相对基线有私改」且用户已说回灌/允许覆盖：
php bin/w update:core -b master -f
```

- 默认分支与用户指定一致；ManyCartSync / 多数生产消费仓跟 **`master`** tip。
- `-f` 会覆盖站点侧核心文件：仅在冲突挡住且回灌目标就是对齐官方 tip 时使用；保护文件（`env.php` 等）仍按命令规则跳过。
- **不要**整树 rsync 框架仓盖站点；不要用手改站点 `Weline/**` 充当源。

多站点时：只回灌用户点名或当前工作区站点；「回灌」≠ 自动全网「分项」。

### D. 验证（硬）

按变更表面取证（`global-constraints.md` §5）：

1. **本地站点**：聚焦单测；相关 HTTP/路由/行为探针；产品 UI 则按 WebUI 规则。
2. **线上**（用户任务含生产/已给主机时）：同一验收点再测一遍；记录状态码与关键正文特征。
3. 交付必须写出：框架 tip、回灌命令、本地证据、线上证据；未测不得写「已完成」。

## 禁止

- 未给框架仓却在消费仓改 `Weline/**`「先顶上」。
- 无「回灌」口令自行改核、自行 `update:core -f`、自行 push 核心。
- 把无关脏核心、会话外文件、业务模块塞进同一次回灌提交。
- 用 Git `checkout`/`restore`/`reset` 当跨仓合并工具冲掉脏工作区（见 §7 Merge-back baseline）。
- 声称全站已回灌但只做了本地、或 tip 与报告不一致。

## 报告模板

```text
回灌完成
- 框架：branch / tip / remotes
- 改动：模块与关键路径（会话范围）
- 回灌：站点路径 + update:core 参数（是否 -f）
- 验证：本地 …；线上 …（URL/状态码/关键断言）
- 残留：冲突跳过、reflection 超时等
```
