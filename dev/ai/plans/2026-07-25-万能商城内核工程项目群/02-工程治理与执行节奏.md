# 工程治理与执行节奏

## 1. 交付模型

采用 Stage-Gate 控制风险、Kanban 控制在制品、Rolling Wave 控制远期不确定性：

- Stage-Gate：只有证据通过才能跨阶段；
- Kanban：限制同时进行的 HIGH/CRITICAL 工作，避免“大量开始、少量完成”；
- Rolling Wave：全量冻结项目边界和依赖，近期项目细化到文件/符号级，远期项目在上游契约稳定后再完成 L4；
- Evidence-driven：进度按可验收输出计算，不按代码量或“完成百分比”主观估算。

## 2. 角色与职责

| 角色 | Accountable 内容 | 不得承担 |
|---|---|---|
| Program Owner | 范围、优先级、Gate、最终验收、用户沟通 | 以进度名义放宽安全/质量门禁 |
| 技术主管 | WBS、调度、文件冲突、依赖、一级验收、阻断分派 | 替专业 Owner 临场重设计 |
| 架构/Framework Owner | 公共接口、Scope、Schema、Runtime、跨模块契约 | 直接耦合其他模块内部类 |
| Module Owner | 项目章程内的模块实现、文档和一级证据 | 修改计划外模块或公共契约 |
| Data/Migration Owner | checkpoint、迁移、fresh verify、回滚/前向修复 | 无隔离库或无授权 apply |
| Security Owner | ACL、CSRF/Origin、密钥、审计、威胁边界 | 为兼容放宽 default-deny |
| QA Lead | 风险分层、证据完整性、独立 Gate 判定 | 用泛化“测试通过”替代真实证据 |
| Runtime/WLS Owner | 独立实例、reload/restart、日志、清理 | 触碰 9501 或留下未托管实例 |
| Documentation Owner | owning docs、API、运行手册、任务记录 | 用历史报告替代当前文档 |

台账中的每个正式 Project ID 必须指定一名 Accountable Owner；其他角色是 Responsible/Consulted/Verifier。一个项目不能存在两个最终负责人。

## 3. 项目状态流

```text
NOT_READY → READY → IN_PROGRESS → IN_REVIEW → IN_VERIFICATION → ACCEPTED
                    ↘ BLOCKED ←───────────────┘
```

| 状态 | 进入条件 | 退出要求 |
|---|---|---|
| NOT_READY | 上游未满足或 L4 未冻结 | 完成项目 DoR |
| READY | DoR 全通过、容量已分配 | Owner 接单并冻结基线 |
| IN_PROGRESS | 仅执行允许 Slice | 实现、静态检查、文档自检完成 |
| IN_REVIEW | diff、契约、impact 和偏差材料齐全 | 技术主管一级验收通过 |
| IN_VERIFICATION | QA 已接受证据方案 | TEST/ACC、Browser/WLS/数据证据通过 |
| ACCEPTED | QA + Program Owner 签收 | 合入/发布动作仍需单独 Git/部署授权 |
| BLOCKED | 触发停止条件 | 由规划者更新 DEC/MOD/L4 或用户解除外部阻断 |

禁止状态：`90% complete`、`基本完成`、`待补测试后完成`。没有证据即未完成。

## 4. WIP 限制

| 层级 | WIP 上限 | 原因 |
|---|---:|---|
| Program | 同时最多 1 个包含资金/不可逆迁移的 Gate | 避免恢复路径互相污染 |
| Release Train | 同时最多 2 个 CRITICAL 项目进入 IN_PROGRESS | 保留审查和故障处理容量 |
| Project Owner | 1 个 CRITICAL 或最多 2 个 HIGH 工作包 | 确保单点责任和证据闭环 |
| 文件 | 同一文件同时只有 1 个项目拥有写锁 | 防止语义冲突和合并误伤 |
| Migration | 每个默认 connector 同时只允许 1 个 apply/cutover | 保持 checkpoint 和 writer 水位唯一 |
| WLS | 每个验证任务独立名称和端口；不得复用 9501 | 隔离运行时和日志证据 |

阻断不释放 Owner 责任，但经技术主管登记后可释放实施 WIP；阻断项目的文件锁是否释放必须单独决定。

## 5. 分支、worktree 与集成

以下是实施期约定，当前规划任务不创建分支：

1. 在 `TASK-P0-001` 冻结干净、可重现的集成基线；当前脏 `master` 不可直接作为施工工作区；
2. 计划集成分支命名：`codex/commerce-kernel-program`；项目分支：`codex/commerce-kernel/<project-id-lower>`；
3. 每个活动项目使用独立 worktree，基于最近已验收的 Program Gate；
4. 依赖项目未合入集成基线时，下游不得从上游个人分支继续堆叠；
5. 同文件项目按 `01-项目与任务台账.md` 的依赖顺序串行，技术主管维护文件所有权表；
6. 合入顺序：项目自检 → 技术主管 review → QA verification → Program Gate → 集成；
7. commit/push 只有用户明确授权后执行；授权提交时遵守本仓双端推送规则；
8. 禁止 rebase/force 操作覆盖用户既有未提交工作。

## 6. L4 Execution Slice 规则

一个 L4 Slice 必须同时满足：

- 只有一个可观察输出；
- 主责文件通常不超过 3 个，跨模块契约/迁移例外须写明；
- 一个 Slice 不同时承担 schema、业务接入、UI 和 cutover 四类结果；
- 有精确路径、符号、输入/输出、正常/异常/并发分支；
- 有明确验证入口和失败判据；
- 有停止条件，代码与计划不一致时不自扩范围；
- 预估不超过项目 Owner 可在一次证据闭环内完成的容量；过大必须再拆。

迁移 TASK 即使归属领域项目，也必须有独立 Data/Migration Task Owner、独立切换窗口和独立证据包；功能 Project Owner 对整体 Gate 负责，不能让功能开发者自签迁移结果。

建议拆分顺序：契约 → additive schema → 核心服务 → 适配/接入 → UI/运维面 → 迁移 dry-run → cutover → contract。资金和库存类 Provider 调用、DB 事务、outbox/CAS 必须按 R4 的事务边界拆分，不能为了减少卡片合并。

## 7. 工作节奏

### 每个项目开工前

1. DoR review；
2. 冻结 baseline/dirty/branch/worktree；
3. 项目智能上下文和 impact；
4. 文件写锁与接口契约 review；
5. QA 确认验证层和数据准备；
6. Program Owner 把项目从 NOT_READY 改为 READY。

### 每个工作包结束

1. 更新任务状态，不写模糊百分比；
2. 记录真实修改、命令、退出码、日志、Browser/WLS/数据证据；
3. 技术主管核对范围和依赖；
4. QA 判定通过、返工或阻断；
5. 关闭文件锁并更新风险/决策/偏差台账。

### 每个 Gate

1. 重新计算关键路径和剩余 CU；
2. 检查 upstream ACC、迁移水位、未解决 CRITICAL 风险；
3. 做 Go / Conditional Go / No-Go 决策；
4. Conditional Go 只能处理不影响安全、数据和公共契约的明确尾项，且不得启动依赖该尾项的下游；
5. 更新下一波 L4 计划和容量，不提前启动未就绪项目。

## 8. 进度度量

只使用以下可验证指标：

- Accepted CU / 当前 Train 总 CU；
- Accepted TASK / 当前 Train TASK；
- Gate 通过数；
- 阻断龄期和责任人；
- CRITICAL 风险未关闭数；
- 返工率、计划外文件数、shadow mismatch、数据不变量差异；
- 证据包完整率、Browser/WLS 清理率。

不使用代码行数、提交次数、忙碌时长或主观完成百分比衡量交付。

## 9. 变更控制

| 变更级别 | 示例 | 决策人 | 处理 |
|---|---|---|---|
| C0 澄清 | 不改变行为的文字/定位修正 | Project Owner + QA | 更新 L4/文档并留痕 |
| C1 项目内 | 已有 DEC 下新增必要文件或调整 Slice 顺序 | 技术主管 | 更新 MOD/L4、影响和验证 |
| C2 架构 | 公共接口、数据所有权、状态机、跨模块边界改变 | Program Owner + 架构/安全/QA | 停工，修订 R4 DEC/MOD/TRACE 后重新 Gate |
| C3 外部/不可逆 | 生产迁移、真实支付、密钥、删除、部署范围 | 用户明确授权 | 单独审批、checkpoint、回滚和人工窗口 |

任何执行者只能报告偏差，不能自行把 C1/C2/C3 当作“实现细节”。

## 10. 证据包

每个 TASK 的任务记录至少包含：

- 基线 HEAD、dirty、worktree、分支；
- 项目智能/impact 结果及风险；
- 实际修改文件与符号；
- 命令、退出码、关键输出；
- schema/迁移 checkpoint、fingerprint、水位和不变量；
- HTTP/Browser 完整 URL、步骤、可见结果、console；
- WLS 名称、端口、状态、日志、reload/restart/stop；
- 通过/失败/未执行 TEST；
- 与计划偏差、新风险和文档同步；
- DoD/ACC 判定、QA 与 Program Owner 签收。

证据只能来自实际执行，不接受“理论上”“看代码应该”“命令已发送”。
