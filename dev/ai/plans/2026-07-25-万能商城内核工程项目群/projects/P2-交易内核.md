## 1. 阶段目标

在 `PG-2` 平台底座上交付 Product → Inventory/Provider → Order/Cart/Checkout → Payment/Webhook/Refund/Invoice 的单一交易事实链。P2 采用两次不可逆语义检查点：Order 新 writer 单写（`PG-4`）和资金主链切换（`PG-5`）。

```text
  └─ PRJ-PROVIDER-22(renderer) ────────────────────────┤
                                                       ↓

                                                       ↓
                                              PRJ-PAYMENT-25
```

## 3. `PRJ-CATALOG-20` 商品目录与物理分片

### 目标

交付通用 Shard Provisioner、Website 物理目录分片、全局 SKU registry、Product/Offer/EAV/Price/Media/Store overlay 和 Provider SPI；请求路径绝不执行 DDL。

### 工作包

| 波次 | TASK | 依赖 | 输出 |
|---|---|---|---|
| P2A-1 | `TASK-P2A-001` | `PG-2` | Shard family/provider discovery、SchemaDiffStage、真实 diff/executor、fingerprint/status |
| P2A-2 | `TASK-P2A-002` | P2A-1 | Product shard schema/state、provisioning queue、ready gate、resolver whitelist |
| P2A-3 | `TASK-P2A-003` | P2A-2 | SKU/Product/Offer unique identity、claim/alias/ref_count/DTO |
| P2A-4 | `TASK-P2A-004` | P2A-3 | **ACCEPTED** repository、same-Website fallback、cleared、COW、publish lock |
| P2A-5 | `TASK-P2A-005` | P2A-2；与 P2A-3/4 可并行 | **ACCEPTED** 小型 Provider capability SPI、registry metadata、duplicate fail-fast |

### 门禁

**`GATE-P2A = GO`**（`2026-07-24-1715-gate-p2a-final-acceptance`）。

### 关键冲突与门禁

- Schema Provider 必须从 R4 指定的 Framework extends 发现路径接入；
- 通用 Provisioner 与 Product schema 分责，Product 不复制一套 migration engine；
- registry 与 shard DML 的事务/补偿不得产生孤儿；
- 分片 `ready` 前 Product 写 fail-closed；
- `cleared` 终止所有剩余 fallback；
- SPI 只发布小接口，不暴露 Product 内部 Service/Model。

### DoD

R4 `GATE-P2A` 及其映射的全部 P2A 测试通过；所有计划 Website shard ready，无请求 DDL、孤儿 SKU 或跨 Website 回退。

## 7. `PRJ-CHECKOUT-24` Cart、Shipping 与 Checkout

### 目标

交付 Cart V2、一次 CheckoutGroup 报价、Shipping owner 100/0 分摊、Tax stub、Order Facade 提交和 bin-query UI。

| 波次 | TASK | 依赖 | 输出 |
|---|---|---|---|
| CKO-1 | `TASK-P2E-001` | Provider Copy/Renderer + Order build | **ACCEPTED** Cart V2 SPI/registry、OfferIdentity、server selection hash、guest token、same-Scope merge |
| CKO-2 | `TASK-P2E-002` | Cart + Inventory + Order | **ACCEPTED** freeze/reprice/compat、单次 Quote、owner allocation、Tax stub、Order+reservation transaction |
| CKO-3 | `TASK-P2E-003` | CKO-1/2 | **ACCEPTED** server ViewModel/Hook、`Weline.Api.*` UI、Browser |

### 不变量

- 跨 Scope/币种 Cart 不合并；客户端金额/hash 不可信；
- 一次 CheckoutGroup 只调用一次 `Weline_Shipping` Quote；
- 第一个 shippable Order 是 shipping owner，owner 收 100%，其他 Order 为 0；最大余数只在 owner items 内分配；
- 只有全组、发货前取消才自动退完整 shipping；
- Checkout 失败没有半组 Order、半预占或 outbox；
- Tax stub 明确服务端写零税，不把计算错误当零税；
- 前端业务请求禁止 native fetch/XHR/axios。

DoD：CKO build + `TASK-MIG-P2-ORDER` 完成 → **`GATE-P2E=GO`**（`2230-gate-p2e-final-acceptance`）。

## 8. `PRJ-PAYMENT-25` 支付、Webhook 与退款

### 目标

复用现有 `Weline_Payment`，在 Order PayableResolver 上交付 Payment Facade V2、Intent/Attempt、事务外 Provider 出站、Webhook inbox/outbox、Refund/Invoice/Fulfillment/Customer account 和 reconciliation。

### 工作包顺序

| 波次 | TASK | 依赖/并行 | 输出 |
|---|---|---|---|
| PAY-1 | `TASK-P2F-001` | `PG-4` | **ACCEPTED** Order PayableResolver、immutable snapshot、registry、eligibility、Scope/account freeze |
| PAY-2 | `TASK-P2F-002` | PAY-1 | **ACCEPTED** nullable unique guards、Intent/Attempt、command outbox、Provider idempotency、second-tx CAS、ledger |
| PAY-3 | `TASK-P2F-003` | PAY-2 | **ACCEPTED** endpoint/secret lookup、raw verify、pure parse、immutable encrypted inbox、2xx policy |
| PAY-4 | `TASK-P2F-004` | PAY-3 + Inventory | **ACCEPTED** inbox consumer、same-connector lock/CAS、唯一 inventory owner、deterministic outbox |
| PAY-3 | `TASK-P2F-005` | PAY-2 + Order；与 webhook build 文件无冲突可并行 | **ACCEPTED** RefundCase/PaymentRefund、额度/数量锁、unknown/late-success reconcile |
| PAY-5 | `TASK-P2F-006` | PAY-4 + Refund | **ACCEPTED** Invoice/Fulfillment/Customer account/tombstone historical whitelist |
| PAY-6 | `TASK-P2F-007` | PAY-4/5/6 build | **ACCEPTED** invariants、dry-run/repair ACL、metrics、urgent notification、retention |
| PAY-7 | `TASK-MIG-P2-PAYMENT` | 全 build + `PRJ-MIG-00` | **ACCEPTED** 历史 Transaction 映射、水位、fresh verify/reconcile、禁止删历史 |

### 资金硬门禁

- 调用方不能传金额、账户或 Provider reference，全部由服务端 Payable snapshot 冻结；
- 一个 Order 同时最多一个 active Intent；Intent 内最多一个非终态 Attempt；
- 第一事务只建本地事实/command outbox，Provider 在事务外调用，第二事务 CAS 记录响应；
- Provider timeout/未知态继续占用，不允许新 Attempt；
- Webhook 原始验签后才入箱，DB 提交后才 2xx；同 event ID 不同 hash/schema/account 是冲突 urgent；
- Payment/Order/Inventory 默认 connector 必须相同，否则作为计划偏差停止；
- Inventory commit 只有 webhook consumer 事务内一个 Owner，不额外建 inventory commit outbox；
- Refund pending/unknown 占用额度，只有权威 terminal failed 释放；释放后迟到成功冻结并人工对账；
- normal/test Provider 账户和真实仓/资产严格隔离，不执行真实支付。

### DoD / `PG-5`

Payment、Webhook、Refund、Invoice、Inventory、Order、Outbox、Reconcile 全部不变量为零差异；Browser/后台/账户中心证据通过；Payment MIG 可重复且历史可追溯；mode off 后仍继续 webhook/query/reconcile/已提交资金义务。

## 9. 文件冲突串行规则

| 共享面 | 先后顺序 |
|---|---|
| Framework Schema | Catalog 通用 Provisioner 先，Product shard 后；后续 Search/Warehouse 只扩展既有 SPI |
| Product models/EAV | Catalog → Provider Copy；Checkout 只读 OfferIdentity/快照 |
| Inventory ledger/reservation | Inventory → Checkout reserve → Payment webhook commit → P3 Warehouse |
| Order Facade/models | Order build → Checkout submit → Payment resolver/refund/invoice |
| Checkout/Cart | Cart V2 → Checkout core → B2B/Subscription 后续扩展 |
| Payment | Facade/Intent → Webhook → Refund/Invoice → Vendor/Asset/Subscription |
| Customer account | P2 Invoice/Order 页面先，P4 Asset/Subscription 通过正式 account layout Hook 后接 |

## 10. P2 停止条件

- R4 签名/路径与真实代码不一致且会改变公共契约；
- Product shard 未 ready 却需要请求 DDL；
- Order 需要双写或回滚到旧 writer；
- Checkout 无法在同一 connector 保证 Order/Inventory 原子边界；
- Payment Provider 必须在数据库事务内调用；
- Webhook 无法保存原始验签证据、事件冲突或确定性 outbox；
- Refund unknown 需要释放额度或迟到成功被静默覆盖；
- 验证需要真实支付、生产写入或未授权测试产物；
- 发现 Scope/权限/金额/库存/重复副作用任一非零差异。
