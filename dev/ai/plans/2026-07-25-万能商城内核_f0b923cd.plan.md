### 1.2 范围

包含：

- P1：Store/Channel、请求 Scope、Token、Queue Envelope、ACL、EAV 骨架、SystemConfig/Meta/Theme/I18n、安全头、Storage/CDN、加密导入导出、SEO、Consent、维护与限流；
- P2：Product、Inventory、Provider/Renderer、Store 复制、Order、Cart/Checkout、最小运费、Tax stub、Payment/Refund/Webhook/Invoice、Fulfillment、Customer 账户；
- P3：多仓、完整 Tax、Search；
- P4：`Weline_Vendor`、`Weline_Subscription`、`Weline_B2B`、`Weline_CustomerAsset`。

明确不包含：

- 营销、优惠券、愿望单、浏览历史；
- 阶段二共享真实物理仓；
- 阶段二 Search 强依赖、PDF/报税发票、跨法务主体复杂运费；
- 未授权的测试产物、提交、推送、部署、生产写入或真实支付。

### 1.3 非功能约束

- 金额统一以整数最小货币单位持久化并冻结 precision；业务时间统一 UTC Unix 秒；
- 所有浏览器业务请求使用 bin-query / `Weline.Api.*`，禁止 native fetch/XHR/axios；
- 长生命周期 WLS 下 RequestContext、Scope、Session、缓存必须请求结束清理；
- 对外接口版本化，跨模块只依赖 `Api/Interface`、QueryProvider、事件、Queue 或 Hook；
- 高风险状态以数据库唯一键、CAS、行锁和不可变 ledger/outbox 证明，不以进程内锁证明；
- 所有回滚 fail-closed：可暂停、只读或阻断新交易，不扩大权限、不接受伪 Scope、不产生错误零税或真实扣款。

### 2.2 当前与目标调用链

当前 HTTP 范围链：

`Host/URI → DetectWebsite → RequestContext/WebsiteData → Controller/QueryProvider`。  
目标链：

`Host/URI/Scope Token → Websites ScopeResolver → immutable ScopeIdentity → RequestContext freeze → QueryBin/Controller/Service → response scope_meta → request reset`。

`Cart QueryProvider → CartService → CheckoutQueryProvider/CheckoutService → Checkout 旧 Order 表 → Payment/Order 零散接入`。

### 4.3 Product 分片状态

`unprovisioned → provisioning → ready | maintenance | failed`。

~~~php
interface ShardSchemaFamilyProviderInterface extends SchemaProviderInterface
{
    public function getFamilyCode(): string;
    /** @return list<string> */
    public function getRegisteredShardKeys(): array;
    /** @return list<TableSchema> */
    public function getTableSchemasForShard(string $shardKey): array;
    /** @return list<TableSchema>；展开全部 registered shard */
    public function getTableSchemas(): array;
}
~~~

- Website 创建只写注册表并进入 provisioning；
- Product provider 实现 `ShardSchemaFamilyProviderInterface extends SchemaProviderInterface`；无参 `getTableSchemas()` 展开 registry 全部分片，单站 provision 调 `getTableSchemasForShard((string)$websiteId)`；现有 `SchemaDiffStage` 扫描扩展并逐表调用 `SchemaDiffEngine::diff(TableSchema, ?TableSchema, ?string)`，最终调用 `SchemaMigrationExecutor::execute(ConnectorInterface, array, array)`；
- Product 实现类固定 `Weline\Product\Extends\Module\Weline_Framework\Schema\ProductShardSchemaProvider`，文件为 `app/code/Weline/Product/extends/module/Weline_Framework/Schema/ProductShardSchemaProvider.php`，family code=`product.website`；重复 table declaration 立即硬失败；
- fingerprint、schema version 和校验通过后才能 ready；
- Resolver 只接受 `website_id>=0` 且状态 ready；maintenance/failed 只读或拒绝；
- `setup:upgrade` 枚举全部注册分片；单站失败不开放该分片写入；
- DDL 与 SKU/投影业务写永远不在同一事务中，业务写前置条件是分片 ready。

### 4.4 Product/EAV

- `weline_sku_registry` 是 SKU/global_product_uuid/global_offer_uuid 的唯一身份源；
- Website 分片保存 Product/Offer/Category/EAV/Price/Media 目录；Store 表保存 selection 和显式经营覆盖；
- 运行时只允许 `Channel→Store→Website`，绝不跨 Website；
- EAV 搜索顺序：每层先目标 locale→声明的 locale fallback；第一条 explicit 返回；第一条 cleared 返回显式空并终止；
- required 属性 cleared 产生 `cleared_at_scope/locale` 诊断并阻止发布/可售；
- Store 建品事务顺序：锁 SKU registry → 写/取 Website Product/Offer → 写当前 Store 投影 → 来源链路/中心只读索引；其它 Store 不自动出现。

### 4.5 Inventory reservation

| 字段 | 规则 |
|---|---|
| `reservation_uuid` | 全局稳定，唯一 |
| `order_id/order_item_id` | 绑定业务边界 |
| `state` | `reserved\|committed\|released\|expired\|conflict`，只允许单调迁移 |
| `quantity` | 正数；所有变化写不可变 ledger |
| `lease_owner_attempt_code` | 仅当前支付 Attempt 可持有 |
| `lease_version` | CAS 每次 +1 |
| `lease_expires_at` | 当前有效截止 |
| `lease_max_expires_at` | `attempt_started_at+2h`，不可延长 |
| `idempotency_key/request_hash` | 同 key 不同 hash 返回 conflict |

续租 CAS 必须同时匹配 `state=reserved`、owner、version、未过期；禁止复活 expired/released。Provider 未知态在上限后进入 reconciliation_required 并停止续租。

### 4.6 Order 与展示号

- `OrderFacadeInterface` 固定发布 `plan(CreateCheckoutGroupCommand): OrderPlan`（纯计算、零写）、`create(CreateCheckoutGroupCommand): CreateCheckoutGroupResult`（唯一 writer）、`get(OrderId): OrderReadResult`；Checkout、Payment、Inventory 不得引用 Order 内部 Model/Service；
- `CheckoutGroup`、`Order`、`OrderItem`、`FulfillmentUnit`、`Invoice`、`RefundCase` 都有 UUID；
- 展示号由 `DisplayNumberAllocator` 使用 `random_int` 生成，表内唯一键固定 `(website_id, store_id, number_kind, display_number)`，冲突最多 5 次；
- Order/Invoice/Refund URL 和 Query schema 必须同时携带 `number_kind`；kind 缺失返回 `display_number_kind_required`；
- Money/Catalog/Scope/Tax/Shipping 快照不可变，活状态另表或明确可变字段；
- 新订单只写 Order；旧 Checkout 表保留只读兼容投影，切换水位后禁止写。

### 4.7 Payment 基数与状态

`Order(payable) 1:N PaymentIntent 1:N PaymentAttempt 1:1 provider_reference ownership`。

公开编排契约固定为：

- `PaymentFacadeV2Interface` 固定发布 `start(PaymentStartCommand)`、`resume(PaymentResumeCommand)`、`query(PaymentQueryCommand)`，均返回 `PaymentOperationResult`；`start()` 的第一事务只做本地 DML，创建/复用 Intent、Attempt、reservation lease 与 `provider-command` outbox，不调用 Provider；
- `PaymentStartCommand` 只允许 payable type/id、method code、idempotency key、request hash、Actor、服务端冻结 Scope、白名单 return URL；调用方不得传金额、币种、merchant account 或 Provider reference，Facade 必须经 PayableResolverRegistry 获取冻结快照；
- `PaymentOperationResult` 固定 intent/attempt code、status、terminal、`nextActionType=none|redirect|qr|sdk|poll`、脱敏 nextAction、retryAfterSeconds、errorCode；禁止公开 createIntent/createAttempt；
- `PaymentProviderCommandConsumer` 在第一事务提交后以 `provider_request_key=attempt_code:submit:v1` 调 Provider；响应在第二事务以 attempt version CAS 落库。Provider 已成功而响应落库前崩溃时，同 key 重查/重试并由 webhook/reconcile 收敛；
- 现有 `PaymentFacadeInterface::tryCreatePayment()` 保持 ABI，只经 V2 adapter 服务旧调用方；Order cutover 后只依赖 V2；
- Order 的 `PayableResolverInterface` 实现固定在 `app/code/Weline/Order/extends/module/Weline_Payment/PayableResolver/OrderPayableResolver.php`，由现有 registry 自动发现。

正式/default 数据库为 PostgreSQL；SQLite 仅供开发与补充测试。需要兼容
MySQL/PostgreSQL/SQLite 的数据库约束统一使用 nullable guard：

- `PaymentIntent.active_guard`：active 时=`active`，终态/被 supersede 时 `NULL`；唯一索引 `(environment, payable_type, payable_id, active_guard)`；
- `PaymentAttempt.nonterminal_guard`：非终态时=`open`，终态时 `NULL`；唯一索引 `(intent_code, nonterminal_guard)`；
- `PaymentAttempt.provider_reference_guard`：分配后为 `sha256(environment|provider_code|normalized_merchant_account|provider_reference)`，未分配为 `NULL`；唯一索引 `(provider_reference_guard)`；
- guard 与状态在同一锁内事务更新，并以 DB check/服务校验拒绝不一致；`PaymentLock(SCOPE_PAYABLE_ACTIVE_INTENT)` 只作竞争协调，不替代唯一键；
- `(merchant_account, environment, provider_reference)` 唯一；`PaymentIdempotency` 保存 request_hash，同 key 不同 payload 必须冲突。

| 对象 | 状态 | 允许下一步 |
|---|---|---|
| Attempt | `created\|provider_pending\|requires_action\|processing\|reconciliation_required` | 阻止新 Attempt；query/resume/reconcile |
| Attempt | `succeeded` | Intent paid/captured；永久禁止该 Order 再付 |
| Attempt | `failed\|cancelled\|expired\|superseded` | 释放/重预占后才可新 Attempt/Intent |
| Attempt | `late_success_review` | Order `paid_inventory_conflict` 或人工裁决 |
| Order payment | `unpaid\|paying\|paid\|paid_inventory_conflict\|refund_pending\|refunded\|payment_failed` | 只按状态机服务迁移 |
| Group | `pending\|paying\|partial\|complete\|failed\|attention_required` | 冲突时冻结整组后续扣款与履约 |

Provider 成功而 reservation 无效：Attempt 保持 succeeded，Order→`paid_inventory_conflict`，Group→`attention_required`，停止后续扣款/履约，创建唯一补偿退款 outbox 并 urgent 告警；不得记成普通支付失败。

### 4.8 Webhook inbox/outbox

`PaymentWebhookEndpoint` 是 endpoint 事实源，字段固定：endpoint ID/code、provider/method code、merchant account、environment、Scope/store_mode snapshot、status、active secret version、context version、timestamps/retain_until；`PaymentWebhookSecret` 保存 `(endpoint_id,secret_version)` 唯一的 `secret_ref`、`active|grace|retired`、valid/retain 窗口，禁止明文。公开 `WebhookEndpointDirectoryInterface::resolveActive(code)` 与 `resolveVerificationSecrets(record,receivedAt)` 只返回冻结验签上下文；轮换保留仍在退款/争议/回调保留期内的历史版本，Store tombstone 后只能验签、查询、退款，禁止新扣款。

阶段 A（回调线程）：

1. endpoint code 只定位 Provider、merchant、environment、secret version，不构成认证；
2. 用原始字节、签名头、Provider 时间和 frozen secret version 调用 `verifyCallback`；默认时间偏差 ≤300 秒，Provider 更严则从严；
3. 调用纯 `parseCallback` 取得非空 provider_event_id、schema/version 和 payload hash，不改变业务状态；V2 缺 event ID 固定报 `payment_webhook_event_id_required` 且不入箱；
4. 单事务插入 immutable inbox，唯一 `(endpoint_code, provider_event_id)`；保存 provider/account/environment/schema version、payload hash、加密 raw payload/headers/signature、received_at、retention；
5. 重复 ID 必须逐项比较 endpoint、provider、account、environment、schema version 与 payload hash；完全一致才返回幂等 2xx，不一致记 `event_id_payload_conflict`、不改业务状态并 urgent；验签失败 4xx 且不入箱，DB 失败 5xx；
6. inbox 首次提交后才返回 2xx。

阶段 B（异步消费者）：

1. 锁 inbox、Intent/Attempt、Order；
2. 按记录的 Provider API/webhook schema version 解析；
3. 通过单调 CAS 更新 Payment 与 Order；
4. P2 固定 Inventory 与 Payment/Order 共用 default connector，同事务唯一写 reservation commit/conflict ledger，不生成 inventory commit outbox；检测到 connector 不同立即阻断并报告计划偏差；
5. 同事务插入后续确定性 outbox 并标记 inbox applied；effect key 形如 `attempt:invoice:create:v1`、`attempt:notification:paid:v1`、`refund:provider:submit:v1`；
6. 消费者以 effect key 调用本地/外部幂等入口，失败重试/死信，禁止同步事件替代持久 outbox。

### 4.9 Refund/Invoice/Fulfillment

退款额度公式（整数 minor unit）：

`succeeded + submitted + pending + unknown + current <= captured_amount`，数量逐 OrderItem 使用同样不变量。

- Order RefundCase 保存顾客/客服意图、服务端金额、数量、库存/Provider/通知步骤；
- PaymentRefund 保存渠道状态 `not_submitted|submitted|pending|succeeded|failed|unknown`；
- 事务内先锁并创建不可变 RefundCase/PaymentRefund、占用额度，再由 outbox 以 refund_uuid 调 Provider；
- accepted/submitted 仅显示“处理中”；网络超时一律为 unknown 并持续占额、只允许 query；只有 Provider 可证明的终态 failed 才释放占额并允许关联的新 Refund；已释放的旧请求若迟到成功则进入 `refund_late_success_review`，冻结该 Order 后续退款并 urgent 对账，禁止自动吞并或继续退款；
- 现金 succeeded 后不得回滚；库存、资产、Provider 后处理失败分别重试；
- Invoice 扩展现有 Order InvoiceService，`一张 paid Order 最多一张最小 Invoice`，由唯一 outbox 生成；
- tombstone Store 仍允许历史 payment/reconcile/refund/invoice/fulfillment 白名单任务，禁止目录、SEO、配置分发和新交易。

### 4.10 Shipping

- 一个 CheckoutGroup 在阶段二只允许一个配送地址和一个 shipping method；
- 运费事实源归现有 `Weline_Shipping`：新增 `ShippingQuoteServiceInterface::listOptions(ShippingQuoteRequest): array` 与 `quote(ShippingQuoteRequest,string serviceCode): ShippingQuote`，扩展 QueryProvider operation，内部复用 `ShippingServiceManager`、`RateCalculationService`、`RateTemplate`、`FreeShippingRule`；Quote 返回 ID、service、整数 minor unit、currency/precision、rule/scope version、request hash、free/reason、expiresAt；Checkout 不再另建报价引擎；
- Checkout 对全部需配送行调用一次 Quote API，冻结 `group_shipping_amount_minor`、currency、method、rule_version；
- 稳定选择首张需配送 Order 为 `shipping_charge_owner_order_id` 并强制先支付；100% 组运费进入 owner，其他 Order 为 0；owner 内按 Item 未税需配送金额做最大余数分摊，全为零按 quantity，同余按稳定 UUID 升序；分摊和严格等于组运费，禁止浮点；
- 只有整组需配送数量在发货前全部取消才自动退全部未退运费；部分退款、已发货或仍保留需配送项时自动退 0。管理员显式运费退款只记 owner Order 且不得超过冻结未退余额；任何路径不得重新报价或跨 Order 挪额；
- 多个不能共同收取运费的法务主体在阶段二直接阻断结账，P4 Vendor 另行版本化拆组。

Cart V2 契约固定为 `getProviderCode()` 与 `resolveCartItemSnapshot(OfferIdentity, ScopeIdentity, array selection): CartItemSnapshot`；新 Registry 扫描 `extends/module/Weline_Cart/CartItemSnapshotProviderV2/` 并以规范化 provider code 唯一 O(1) 映射，重复 code 编译失败。Product 实现固定在 `Product/extends/module/Weline_Cart/CartItemSnapshotProviderV2/ProductCartItemSnapshotProvider.php`。最终 selection hash 只能由 CartService 计算 `sha256(global_offer_uuid + "\n" + selection_schema_version + "\n" + canonical_sorted_json)`；客户端 hash 不作事实。V2 无匹配 Provider 时，仅当 OfferIdentity 明含 legacyProductId 才走旧 adapter。

### 4.11 AEAD 配置包

容器字段固定：

| 字段 | 规则 |
|---|---|
| `schema_version` | `weline-config-envelope/1` |
| `package_uuid` | 每包随机 UUID；进入 AAD；目标以唯一消费账本拒绝重放 |
| `recipient_kid` | 目标实例已发布且未吊销的 X25519 public key id |
| `wrapped_key` | 使用 recipient public key sealed 的随机 data key |
| `nonce` | 每包随机 XChaCha20 nonce，禁止复用 |
| `aad` | canonical JSON：package_uuid、版本、source_instance、recipient_kid、原文件名、Scope、created_at、expires_at；source_instance 默认仅审计，要求受信来源时另验 Ed25519 signature |
| `ciphertext` | XChaCha20-Poly1305 完整配置 payload |
| `payload_hash` | 密文 hash，仅作传输诊断，不替代 AEAD |

导出要求重认证、export ACL、一次性下载、短 TTL、大小/schema 限制和临时明文清理；目标按 kid 选择私钥，在任何配置写入前先 CAS 插入 package consumption ledger，失败或已消费均零写入；旧 key 在过渡期只解密不新导出，吊销后拒绝。libsodium 不可用则功能 fail-closed，禁止回退 `Framework\System\Security\Encrypt`。

### 4.12 ACL 与可观测性

动作矩阵最小集合：

| 资源 | 普通动作 | 高风险动作 |
|---|---|---|
| Website/Store/Channel | list/view/create/update | delete/physical-delete/all-sites |
| Config/Secret | view/update | export/import/unlock/restore-suppressed |
| Queue/Outbox | list/view | replay/cancel/quarantine-release |
| Order | list/view | fulfill/cancel |
| Payment/Refund | view | pay-live/refund/reconcile |
| Product/Inventory | list/view/update | ownership-transfer/stock-adjust |

每个入口先做角色动作权限，再做对象 Scope 交集；后台高风险写还必须校验框架 CSRF token 与可信 Origin/同站策略，并在提交时重新鉴权/重认证。预览与提交分别校验，预览后权限撤销必须使提交失败。All Sites 永远只读且独立授权。

Scoped urgent 告警必须向 `w_msg()` 传显式非空 `notify_users`；当前空数组含义是“全部用户”，因此无授权接收人时禁止调用，只写受控审计。`SystemNotification` 新增 `scope_hash`、`dedupe_key`、`occurrence_count`、`last_occurrence_at`，唯一 `(topic_code,scope_hash,dedupe_key)`；Router 只为明确授权用户创建状态/外部通知，不把 Scope ACL 交给前端。

correlation 链固定为 `request → checkout_group → order → payment_intent → payment_attempt → provider_event → inbox/outbox → refund/invoice/fulfillment`。至少监测：

- succeeded Attempt 无 reservation result 或 compensation；
- paid Order 无 invoice record/outbox；
- reservation 超过 lease 上限；
- Refund pending/unknown 超 SLA；
- inbox received 未 applied、outbox retry/dead letter；
- SubscriptionPeriod 无 Order、资产 ledger 不守恒；
- Scope/ACL 拒绝率异常和 WLS cross-request mismatch。

所有对账命令先 dry-run 输出不变量、数量和差异；修复模式需独立 ACL、审批、幂等和审计。

~~~php
function startPayment(PaymentStartCommand $command): PaymentOperationResult {
    $resolver = $payableResolverRegistry->getResolver($command->payableType);
    $snapshot = $resolver->snapshot($resolver->resolve($command->payableId, $command->actor));

    });

function receiveWebhook(RawHttpRequest $http): HttpResponse {
    $endpoint = $endpointDirectory->resolve($http->routeEndpointCode());
    $verified = $endpoint->provider->verifyCallback($http->toCallbackRequest());
    if (!$verified->signatureValid || !$verified->withinTimeWindow) {
        throw new InvalidWebhookSignature(); // 映射 4xx，零 inbox/业务写入
    }
    $event = $endpoint->provider->parseCallback($http->toCallbackRequest()); // pure
    $inbox->insertOrCompareImmutable($endpoint, $event, encrypt($http->raw()));
    return HttpResponse::ok(); // 仅在 inbox 提交后
}

function applyPaymentInbox(InboxId $id): void {
    $txRunner->run($connector, function () use ($id) {
        $event = $inbox->lockReceived($id);
        $attempt = $paymentRepository->lockAttempt($event->attemptCode);
        $transition = $paymentStateMachine->compareAndAdvance($attempt, $event);
        $connectorGuard->requireSameDefaultConnector('Payment', 'Order', 'Inventory');
        $inventoryResult = $inventory->commitOrConflictLedger($transition); // 唯一库存 owner
        foreach ($effectPlanner->deterministicEffects($transition, $inventoryResult) as $effect) {
            $outbox->insertUnique($effect->key, $effect->payload);
        }
        $inbox->markApplied($event->id, $transition->version);
    });
}
~~~

~~~php
function requestRefund(RefundCommand $command): RefundCase {
    return $txRunner->run($connector, function () use ($command) {
        $order = $orderRepository->lock($command->orderId);
        $items = $orderItemRepository->lockMany($command->itemIds);
        $amount = $refundCalculator->fromFrozenSnapshots($order, $items, $command->quantities);
        if ($refundLedger->succeededPlusOccupied($order) + $amount > $order->capturedMinor) {
            throw new RefundAmountExceeded();
        }
        if (!$refundLedger->quantitiesWithinPurchased($items, $command->quantities)) {
            throw new RefundQuantityExceeded();
        }
        $case = $orderRefundService->createImmutableCase($command, $amount);
        $paymentRefund = $paymentRefundService->reserveAndCreate($case->uuid, $amount);
        $outbox->insertUnique("refund:{$case->uuid}:provider:submit:v1", $paymentRefund->payload());
        return $case;
    });
}

function allocateMinorUnits(int $total, array $weights, array $stableIds): array {
    $denominator = array_sum($weights) ?: count($weights);
    $base = floorEach($total * $weights / $denominator);
    $remainder = $total - array_sum($base);
    foreach (sortByFractionThenStableId($weights, $stableIds) as $index) {
        if ($remainder-- <= 0) break;
        $base[$index]++;
    }
    if (array_sum($base) !== $total) throw new AllocationInvariantViolation();
    return $base;
}
~~~

## 7. 原子任务卡

### 7.1 所有任务共享护栏

每张任务卡开始前必须：

1. 在仓库根执行 `git status --short --untracked-files=all`、`git rev-parse HEAD` 并记录；
2. 调用一次项目 `get_edit_bundle`（当前任务、所有已知路径、所有符号），以其 impact summary/regions/hashes 为准；若 MCP 明确不可用，记录原始错误后只做 exact-path `rg`、AST-aware `sg`、LSP/type check 等有界 fallback，不重建仓库级上下文；
3. 只有用户明确要求 GitNexus 或 Weline MCP 明确报告无法满足该代码任务时才使用另一仓库级索引；任何来源给出 HIGH/CRITICAL impact 都必须先向用户报告；
4. 创建/恢复当前任务记录，确认测试产物和外部写入授权；
5. 核对上游批次 ACC 全部通过；否则停止。

所有任务统一禁止：越出“允许文件”、改 generated、用 9501、真实支付、提交/部署、忽略失败、用临时 fallback 或假数据。

统一停止条件：符号/签名与 EVD 不符；计划外核心文件成为必改；用户修改冲突；数据/安全风险；命令不适用；需要未授权外部写入或专项测试产物。

本节只设计验证场景，不授权创建测试文件。优先使用现有测试、真实服务入口、CLI、HTTP、Browser、数据库不变量、日志和 sandbox Provider。结果状态固定 `NOT_RUN|PASS|FAIL|BLOCKED_AUTHORIZATION|BLOCKED_ENVIRONMENT`。并发或故障窗口若没有现成受控入口，相关 TASK 可以完成代码但对应 Gate 必须为 `BLOCKED_AUTHORIZATION` 并向用户申请专项测试产物授权；不得用顺序点击冒充并发/崩溃证明，也不得在生产代码加入隐藏故障开关。

### 8.1 WLS 运行参数与命令

在每批任务记录中先物化一次性数据库/schema clone，记录 `<TEST_DB_PROVISION_COMMAND>`、`<TEST_DB_RESTORE_OR_DESTROY_COMMAND>` 与脱敏 `TEST_DB_FINGERPRINT=SHA-256(driver|host|port|database|schema|server_uuid)`。该指纹必须命中 test allowlist、不得等于 canonical/normal/production denylist，且 CLI、WLS、worker、Queue consumer 实测一致；无法证明时禁止任何 MIG apply、并发或资金验证并标 `BLOCKED_ENVIRONMENT`。然后解析实际端口：

~~~bash
WLS_INSTANCE="ai-test-commerce-$(date -u +%Y%m%d%H%M%S)-$$"
WLS_PORT=""
for p in $(seq 9517 9599); do
  if ! lsof -nP -iTCP:"$p" -sTCP:LISTEN >/dev/null 2>&1; then
    WLS_PORT="$p"
    break
  fi
done
test -n "$WLS_PORT"
printf '%s %s\n' "$WLS_INSTANCE" "$WLS_PORT"
~~~

`WLS_PORT` 输出必须是实际整数且不为 9501；写入 progress 后再运行：

~~~bash
php bin/w setup:upgrade --model --sync
php bin/w setup:upgrade --route --sync
php bin/w command:upgrade
php bin/w server:start "$WLS_INSTANCE" -p "$WLS_PORT" --no-ssl
php bin/w server:status "$WLS_INSTANCE"
php bin/w server:status "$WLS_INSTANCE" --doctor --json
php bin/w http:request / -I="$WLS_INSTANCE" -P="$WLS_PORT"
~~~

普通 Worker/业务代码：

~~~bash
php bin/w server:reload "$WLS_INSTANCE"
php bin/w server:status "$WLS_INSTANCE"
~~~

Master/Dispatcher/启动参数变更：

~~~bash
php bin/w server:start "$WLS_INSTANCE" -r
php bin/w server:status "$WLS_INSTANCE"
~~~

自动验证清理：

~~~bash
php bin/w server:stop "$WLS_INSTANCE"
php bin/w server:status "$WLS_INSTANCE"
~~~

注意：当前 CLI 的实例名是位置参数；`-n` 在 `server:reload` 中是 no-wait，禁止把 `-n ai-test-*` 当实例名。后台 URL 必须从 `Env::getAreaRoutePrefix('backend')` 或框架 `getBackendUrl()` 生成；实际 URL 由 Browser 打开后写入任务记录，禁止硬编码 `admin/backend`。

P1d Cookie/TLS 使用独立实例：P0 先确认实际 `TLS_CERT`、`TLS_KEY`、空闲 `TLS_PORT`，再执行 `php bin/w server:start "${WLS_INSTANCE}-tls" -p "$TLS_PORT" --ssl-cert "$TLS_CERT" --ssl-key "$TLS_KEY"`、`php bin/w server:status "${WLS_INSTANCE}-tls" --doctor --json`、`php bin/w http:request / -I="${WLS_INSTANCE}-tls" -P="$TLS_PORT" --https tls`；Browser 以完整 `https://127.0.0.1:$TLS_PORT/` 验收 Cookie，结束后 `php bin/w server:stop "${WLS_INSTANCE}-tls"` 并复查 status。证书不可用则 `BLOCKED_ENVIRONMENT`，禁止用 HTTP 静态头替代。

## 9. 迁移、灰度与切换

### 9.1 统一迁移命令契约

以下是本计划要求新增的薄命令，不是假定已存在。业务映射在 migration service 中；命令注册后运行 `php bin/w command:upgrade`。每个 phase 使用独立 checkpoint，禁止跨命令复用。

~~~bash
php bin/w scope:migrate:p1a --mode=preflight
P1A_CP="p1a-$(date -u +%Y%m%d%H%M%S)-$$"
php bin/w scope:migrate:p1a --mode=checkpoint --checkpoint="$P1A_CP"
php bin/w scope:migrate:p1a --mode=apply --checkpoint="$P1A_CP"
php bin/w scope:migrate:p1a --mode=verify --checkpoint="$P1A_CP"
php bin/w scope:migrate:p1a --mode=rollback --checkpoint="$P1A_CP"

php bin/w scope:migrate:p1b --mode=preflight
P1B_CP="p1b-$(date -u +%Y%m%d%H%M%S)-$$"
php bin/w scope:migrate:p1b --mode=checkpoint --checkpoint="$P1B_CP"
php bin/w scope:migrate:p1b --mode=apply --checkpoint="$P1B_CP"
php bin/w scope:migrate:p1b --mode=verify --checkpoint="$P1B_CP"
php bin/w scope:migrate:p1b --mode=rollback --checkpoint="$P1B_CP"

php bin/w commerce:migrate:p2-order --mode=preflight
P2_ORDER_CP="p2-order-$(date -u +%Y%m%d%H%M%S)-$$"
php bin/w commerce:migrate:p2-order --mode=checkpoint --checkpoint="$P2_ORDER_CP"
php bin/w commerce:migrate:p2-order --mode=apply --checkpoint="$P2_ORDER_CP"
php bin/w commerce:migrate:p2-order --mode=verify --checkpoint="$P2_ORDER_CP"

php bin/w commerce:migrate:p2-payment --mode=preflight
P2_PAYMENT_CP="p2-payment-$(date -u +%Y%m%d%H%M%S)-$$"
php bin/w commerce:migrate:p2-payment --mode=checkpoint --checkpoint="$P2_PAYMENT_CP"
php bin/w commerce:migrate:p2-payment --mode=apply --checkpoint="$P2_PAYMENT_CP"
php bin/w commerce:migrate:p2-payment --mode=verify --checkpoint="$P2_PAYMENT_CP"
~~~

实现文件固定见 6.4。统一退出码：0 仅表示所有不变量通过；冲突、quarantine、计数不等、回滚不安全或执行失败均非零。`preflight` 只读；`checkpoint` 必须在首次写前完成；`apply` 幂等；`verify` 重读数据库；`rollback` 不得隐藏新事实。报告禁止 secret/token/cookie/raw payment 明文。

Checkpoint manifest 至少包含 command/phase、代码版本、创建人、UTC 时间、脱敏数据库 fingerprint、涉及表 schema hash、关键行数/守恒 hash、旧/新 writer 与 Queue/Inbox/Outbox 水位、rollout 配置版本、可恢复快照或反向 DML journal 引用及 SHA-256。`apply` 必须验证 manifest 与当前 command/phase/fingerprint/schema 完全匹配；失败零写并非零退出。`rollback` 遇到不可逆外部事实、隐藏新事实或 manifest 不一致时拒绝并转 continue-forward。所有命令只允许运行在 8.1 已证明的一次性 clone；批次后恢复基线或销毁并记录指纹/行数。

### 9.2 MIG-P1A

顺序：

1. expand Store/Channel/Queue typed columns，不立即强制；
2. 枚举所有 Website（含 0）幂等补 default Store/Channel；
3. Queue 仅按冻结聚合/生产者契约分类 global/website/store/channel，歧义 quarantine，禁止映成零号站；
4. 迁全部 producer/consumer/Handler 声明；
5. 非产品 EAV 可判定行迁 typed scope；歧义保留旧值并报告；
6. verify 后强制新写；旧读限期兼容并告警。

守恒：

- `Website数 = default Store数 = default Channel数`；
- 每 Website/Store default 唯一；
- `源 Queue 行 = 成功映射 + 明确取消 + quarantine`；
- 可消费行 100% 符合 kind，quarantine 不可领取；
- EAV 源行数/实体/属性/value_state hash 与目标守恒；
- 连续 apply 两次新增 0 行。

回滚：关闭新能力并进入只读兼容 reader；保留 additive schema；新 producer 仍强制 Envelope；任何新业务引用存在时不得删种子。

### 9.3 MIG-P1B

- Global 三段全空；Website 仅 Website；Store 两段；Channel 三段；
- 旧短 scope/Meta key 仅唯一可判定时迁移；裸 `default` 无法归属时冲突，禁止猜零号站；
- lock 前预览后代；提交写 lock version + suppressed marker；解锁不复活，显式恢复需要 expected_version；
- 敏感值只迁 encrypted/secret_ref，报告全脱敏；
- 新旧最终有效值、来源和 locale fallback 在已迁 Scope 上一致；
- rollback 永不重开短 scope write。

### 9.4 MIG-P2-ORDER 与 MIG-P2-PAYMENT

`MIG-P2-ORDER` 仅在 P2e build 后、P2f 前执行：

1. Product/Inventory/Order additive schema 与所有 Product 分片先 provision/verify ready；
2. `mode=shadow` 时旧 Checkout 是唯一 writer；新 `OrderFacade::plan()` 只做纯 DTO/金额/拆单比较，禁止 DML、锁、预占、outbox、Provider 或权威缓存写；
3. checkpoint 记录最后旧订单 ID、首个新 Order ID、UTC 切换时间、schema/rollout version；
4. allowlist cutover 后新交易只写 Order，旧表只读；第一个新 Order 产生后 rollback 必须保留新 reader，禁止恢复旧 writer。

`MIG-P2-PAYMENT` 仅在 P2f 全部能力与对账 build 后执行：

1. 把现有 Payment Transaction 以兼容 reader 确定映射到 Intent/Attempt、provider reference、环境和终态，不发起 Provider 调用、不生成业务 outbox；
2. 历史记录不可删除或改写，无法确定映射的行进入只读 conflict report 并阻断 Gate；
3. verify 重新计算 payment/refund/inbox/outbox/ledger 水位与 provider reference 唯一性；rollback 保留所有新旧 reader 与历史事实，只能 mode off/continue-forward。

阶段二执行顺序以 5.1 DAG 和 7.1.1 Gate 为唯一权威：`P2a → P2b/P2c-render → P2c-copy/P2d → P2e build → MIG-P2-ORDER → P2f build → MIG-P2-PAYMENT`。

### 9.5 P3/P4 迁移

每条命令都执行独立 preflight→checkpoint→apply→verify→按需 rollback，文件见 6.4：

### 9.6 灰度门禁

Global-only、env-lock、仅 release ACL 可写的 SystemConfig key：

`commerce.rollout.{scope_kernel,config_scope,product,inventory,cart_checkout,shipping_quote,order_writer,payment_v2,warehouse,tax,search,vendor,subscription,b2b,customer_asset}.mode`、`.allowlist`、`.shadow_sample_bp`。默认 `mode=off`、`allowlist=[]`、`shadow_sample_bp=10000`。

- `off`：新能力不接流量，兼容 reader 保留；
- `shadow`：旧实现是唯一事实源；新实现只纯计算/归一化比较，禁止业务写、锁、预占、outbox、Provider 与权威缓存；Search 仅写隔离版本化 shadow index；
- `allowlist`：仅精确规范化 `(website_id,store_id,channel_id)` 列表启用；
- `on`：全量启用。禁止随机百分比切资金、库存或订单 writer；shadow 采样只能减少纯比较负载。

| 阶段 | 范围 | 最低观察量与晋级条件 |
|---|---|---|
| R0 Preflight | 只读 | 冲突/quarantine/orphan=0，隔离 DB/checkpoint 可恢复 |
| R1 Expand | schema，能力 off | 混合版本兼容，关键不变量 0 |
| R2 Shadow | 只比对 | 每 capability ≥100 可比样本并覆盖完整 Queue/scheduler/reconcile 周期；未分类 mismatch=0 |
| R3 Sandbox | allowlist dev/test | 连续≥2h、≥20 条 sandbox 交易，覆盖失败/重试/退款/崩溃窗；CRITICAL 违规=0 |
| R4 Normal Canary | 单一 normal Store；需用户生产授权 | 连续≥24h、≥10 笔授权交易，含一次失败和一次退款，覆盖完整对账周期 |
| R5 Allowlist expand | 明确 Scope | 每次扩大后观察≥24h且重跑门禁 |
| Contract | 全量稳定 | ≥72h；旧 writer 调用=0，旧 reader 连续≥24h 调用=0；删除 schema 另立任务 |

共同阈值：资金/库存/Scope/金额守恒违规=0、重复外部副作用=0、未分类 shadow mismatch=0、未解决 urgent/dead-letter=0、Inbox/Outbox/Search 增量最老待处理≤5 分钟；Refund pending/unknown 默认 SLA=24h（Provider 更严从严），超 SLA 必须为 0；Scope/ACL 拒绝率高于同流量基线 2 倍或绝对增加>1 个百分点即停。错误率或 p95 比基线退化>10%立即 mode off/allowlist 收缩。未达到最低样本不得以“暂无异常”晋级。

全局停止条件：

- 计划与真实签名/路径不一致且需改公共契约；
- 必须修改未列入 MOD 的核心文件；
- 发现用户已有变更冲突；
- 迁移计数不守恒、quarantine 非零却准备 contract；
- 任何真实支付、生产写入或不可逆迁移未经授权；
- 验证只能靠新测试产物而用户尚未授权；
- Browser/WLS/日志证据失败或无法恢复；
- HIGH/CRITICAL impact 无明确缓解和人工批准。

统一回滚顺序：

1. 对受影响 Scope 维护/只读，停新加购、结账、退款申请和配置写；
2. 保持历史义务所需的 webhook inbox、payment reconcile、已成功支付的 inventory commit、refund/invoice/fulfillment、CustomerAsset settle/return、Vendor settlement reversal、已扣 Subscription refund consumer；只停新交易 producer；
3. 冻结 checkpoint、队列水位、开关和不变量报告；
4. 停新副作用 producer，排空可安全完成的 outbox；
5. 回 UI/route/feature flag，但保留所有新事实 reader；
6. 不删 additive schema，不恢复旧 Checkout writer、短 Scope write 或缺 Envelope write；
7. 运行 verify/reconcile/Browser 只读验收/WLS status；
8. 不变量为 0 差异后才能解除维护，否则前向修复。

禁止回滚：放宽 Queue、授予 `Store=*`、恢复短 Scope 写、Tax 回零、无预占继续扣款、关闭 tender 后丢弃既有义务。
