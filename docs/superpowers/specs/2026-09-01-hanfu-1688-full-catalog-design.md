# 汉服 1688 全量商品导入与测试目录清理设计

- 日期：2026-09-01
- 状态：待用户复核
- 目标站点：`website_id=0`
- 设计范围：测试商品清理、1688 店铺核验、全部公开商品采集、幂等导入、供应商店铺地址治理、真实运行时验收

## 1. 背景与已确认决策

汉服后台已经存在分类、品牌、供应商以及一批由种子、主题演示和验收流程创建的商品。用户已明确确认以下决策：

1. 正式导入前清理当前全部 29 个测试或演示商品，以及只由这些商品使用的对应媒体文件。
2. 保留分类、品牌、供应商、品牌与供应商实体图片、分类图标和仍被其他数据引用的共享资产。
3. 对每个能够核验真实 1688 店铺的目标品牌，导入该店铺当前公开且归属明确的全部商品，不设置每品牌商品数量上限。
4. 以 1688 `offerId` 作为来源唯一标识；重复运行不得创建重复商品，只更新既有来源商品。
5. 供应商店铺地址必须是主体一致、可打开的真实 1688 店铺或工厂主页，不允许用关键词搜索页代替。
6. 无法核验的供应商停用，并由已核验的真实供应商记录替代；无法证明品牌归属的商品不伪造品牌关系。
7. 1688 检索和最终核验使用用户已登录的内置浏览器，但实现不得读取 Cookie、密码、令牌或会话存储，也不得下单、发消息或联系供应商。

## 2. 范围

### 2.1 清理范围

清理目标冻结为执行前盘点得到的 29 个商品，而不是运行时无限扩展的“所有商品”条件：

| 分组 | 商品 ID | 数量 | 识别依据 |
| --- | --- | ---: | --- |
| 临时、手工与验收数据 | `1, 2, 25, 36, 45` | 5 | `R43-*`、`HF-LEG-*`、`HANFU-SAVE-TEST-*`、临时名称或草稿状态 |
| 主题演示商品 | `5-12` | 8 | `THEME-STORE-*` SKU |
| Web 演示商品 | `13-24` | 12 | `WEB-*` SKU |
| 汉服种子或测试商品 | `26, 27, 28, 39` | 4 | `HF-*`、`HANFU-*` SKU 与汉服种子脚本来源 |

每个目标商品的以下从属数据一并清理：

- 商品 EAV 属性和 Store 覆盖；
- Product 与 Store、分类的关联；
- Offer、Offer 与 Store 的关联、价格、库存及变体数据；
- Product/Offer 身份投影与搜索投影中仅属于目标商品的记录；
- 商品媒体行及其不再被任何其他记录引用的 FileAsset 对象；
- 预检清单中列出的商品专属本地文件。

明确保留：

- 全部分类及分类层级；
- 全部品牌、供应商及品牌—供应商关系；
- `pub/media/catalog/hanfu-entities/**`；
- `pub/media/catalog/hanfu/r2/categories/**`；
- 仍被分类、首页配置、品牌、供应商或非目标数据引用的文件；
- 与本任务无关的工作区文件和 `generated/`。

`pub/media/catalog/hanfu/r2/homepage/**` 只有在相关首页引用先被安全解除且全局引用数为零时才进入清理清单；否则保留并在报告中列为“仍被引用”。禁止递归删除整个 `pub/media/catalog/hanfu`。

### 2.2 导入范围

“全部商品”定义为：每个已核验目标店铺在本次完整分页快照中公开、可访问，并且能够唯一归属到目标品牌或该品牌的独占供应商的所有 listing。

- 独占品牌店铺：导入店铺全部公开 listing。
- 多品牌或混合店铺：只有标题、详情或明确的店铺分类能够唯一证明目标品牌归属时才导入。
- 同一 `offerId` 无论从多少入口发现，只导入一次。
- 店铺无法核验、分页未完整结束或 listing 归属冲突时，不把该批次标记为成功；输出待处理清单。
- 非汉服但确属目标品牌的配饰商品仍导入，并映射到现有配饰或兜底分类；不得因分类器无法细分而静默丢失。

### 2.3 非目标

- 不购买、不加入采购车、不发询价、不评价、不联系供应商。
- 不绕过验证码、风控页面、访问限制或 1688 安全机制。
- 不调用未公开的写接口，不保存用户登录凭据。
- 不在本任务中删除、合并重复品牌记录；同名品牌只选择一个确定的规范记录用于新商品，并在报告中保留别名与冲突说明。
- 不自动发布到前台。新导入商品默认保存为草稿，完成后台复核后再由用户决定发布。

## 3. 不变量

实现和运行必须同时满足以下不变量：

1. 清理开始前，目标商品集合、更新时间、从属记录计数、媒体引用和文件哈希形成不可变预检清单与摘要。
2. 应用清理时，数据库当前摘要必须与用户批准的预检摘要一致；发现新增商品、目标商品漂移或引用关系变化时立即停止，不扩大删除范围。
3. 任何文件只有在数据库媒体引用、EAV/配置路径引用和 FileAsset 引用均为零时才能删除。
4. 分类、品牌、供应商在清理前后的 ID 集合和计数必须一致。
5. 导入商品的来源键始终是规范化十进制 `offerId`，不得用标题、价格或图片作为主键。
6. 已存在的非 1688 商品不得因 SKU、标题或 slug 相似而被覆盖。
7. 一个完整店铺快照必须到达自然分页终点；命中安全上限、重复页、登录阻断或解析失败都算失败而不是“已抓完”。
8. 供应商地址必须通过店铺主体名称、工厂/旺铺页面和规范主页 URL 三者核验。

## 4. 方案选择

采用“已核验店铺全量采集 + 显式品牌映射”的方案。

不采用品牌关键词搜索结果全量导入，因为搜索页包含经销商、仿牌和无关商品，且搜索 URL 不能证明供应商主体。不采用“整店抓取后无条件写入品牌”，因为一个供应商可能经营多个品牌，容易制造错误品牌关系。

选定方案先建立店铺主体与品牌映射，再按店铺完整分页；它能覆盖全部合格商品，同时把无法证明的归属隔离到报告中。

## 5. 组件与边界

实现保持在 `Weline_Product` 模块内，不新增 Event、Query、Hook、公开 Interface 或 Taglib 扩展点。

计划新增两个 CLI 入口：

- `app/code/Weline/Product/scripts/cleanup-hanfu-test-catalog.php`：只负责预检、清理与清理验证；
- `app/code/Weline/Product/scripts/import-1688-hanfu-catalog.php`：只负责来源清单、采集快照、导入预览、应用与导入验证。

可复用的解析、归属和清理逻辑放入模块内部 Service；CLI 只解析参数、调用 Service 并输出结构化报告，避免把业务规则堆在一次性脚本中。

### 5.1 清理入口

新增 CLI 清理入口，支持三个互斥模式：

- `--dry-run`：生成目标商品、从属数据、媒体和文件清单以及 `selection_digest`，不写数据库、不删除文件。
- `--apply --selection-digest=<digest>`：只在当前摘要完全一致时执行清理。
- `--verify --run=<run-id>`：验证目标商品及从属记录为零、保留数据未变化、文件状态与报告一致。

清理逻辑只接受 `website_id=0` 和预检冻结的 29 个商品 ID。商品级数据按依赖顺序移除；媒体行必须走 `MediaRepository::remove()` 维护 blob owner 与引用计数；共享身份数据走框架既有引用清理逻辑，禁止直接删掉仍有引用的全局身份。

本地文件先移动到 `var/hanfu-1688/quarantine/<run-id>/`，数据库与页面验收通过后再按清单永久删除。若数据库阶段失败，可依据运行报告继续或恢复文件；在所有目标商品清理成功前不得进入正式导入。隔离区是失败恢复手段，不是最终状态；整个任务完成前，已验证无引用的目标文件必须从隔离区永久清除。

### 5.2 店铺核验与来源清单

来源清单以后台 active 品牌和供应商为输入，记录：

- `brand_id`、品牌代码、显示名和别名；
- `supplier_id`、供应商代码、主体名和状态；
- 1688 工厂页、规范店铺主页、member/company 标识；
- 核验证据、核验时间和结论；
- 该店铺是独占品牌还是多品牌店铺。

同名品牌采用确定性规则选择规范记录：优先选择已经与核验供应商关联的记录；仍有并列时选择最小 `brand_id`。其他同名记录只作为别名记录在报告中，本任务不删除或合并它们。

供应商店铺治理规则：

1. 页面可打开，且公司/店铺主体与供应商名称一致时，写入规范主页 URL。
2. 已有 URL 指向错误主体、搜索页或无法验证页面时，不沿用该 URL。
3. 能找到真实替代主体时，停用错误记录并新建或启用真实供应商，然后重建品牌关联。
4. 无可靠结果时，将现有 active 供应商改为 disabled，并输出原因；不得保留“active 但没有真实店铺地址”的记录，也不得编造地址。

### 5.3 全量采集器

采集器优先读取公开的 1688 工厂或旺铺 HTML 和其中的结构化商品数据，不携带浏览器 Cookie。用户已登录的内置浏览器用于搜索、主体核验、可见分页与最终复核；不得读取登录存储。

对每个店铺：

1. 从规范主页进入商品列表。
2. 逐页提取 `offerId`、标题、详情 URL、价格信息、主图、店铺分类及可见规格。
3. 对 `offerId` 去重，并为每页保存页码、页面指纹和新发现数量。
4. 只有在“下一页不存在或明确禁用，且当前页没有未处理 offer”时到达自然终点。
5. 重复页面指纹、下一页循环、验证码、登录阻断、网络错误或解析结构变化时停止该店铺并标记失败。
6. 可以配置请求间隔、重试次数和诊断性安全上限；命中上限必须报失败，不能把截断结果宣称为全量。
7. 若页面声明商品总数，最终去重数量必须与其一致；不一致时进入失败报告。

采集先生成不可变快照，再导入。快照至少包含店铺、品牌、供应商、全部去重 offer、分页证据、采集时间、完整性状态和内容摘要。

### 5.4 品牌与分类解析

供应商始终由店铺主体确定。品牌按以下优先级确定：

1. 独占品牌店铺的唯一映射；
2. listing 标题或详情中的唯一品牌别名；
3. 店铺内部明确品牌分类的唯一映射。

出现零个或多个品牌匹配时，不猜测品牌；该 offer 进入 `unresolved_brand` 报告。规范品牌一经确定，导入使用其 `brand_id`，同名别名不生成重复商品。

分类使用可解释的规则表映射到现有汉服分类。无法细分但确属目标品牌的商品落入现有汉服兜底或配饰分类，并记录原始店铺分类；不得自动创建一批不可控的新分类。

### 5.5 幂等导入器

每个 1688 listing 对应一个本地 Product：

- Product 主 SKU：`1688-<offerId>`；
- slug：基于标题生成并附加 `offerId`，避免重名冲突；
- `reference_source`：保存规范 offer URL、店铺 URL 和采集时间；
- 属性集：`hanfu`；
- 状态：`draft`；
- 商品类型：有完整可验证规格时使用 configurable，否则使用 simple；
- 价格：使用页面公开的最低有效采购价，保留原始阶梯价证据；
- 规格：只写入页面真实给出的选项，不推测颜色、尺码或库存；
- 媒体：下载并验证 MIME、大小和哈希后，通过 FileAssetLibrary 与 MediaRepository 注册到 `pub/media/catalog/hanfu/1688/<offerId>/`。

页面没有公开有效价格时仍可创建草稿 Product，但不创建可售报价或虚构价格，并在 `missing_price` 报告中列出；该商品在补齐真实价格前不能发布。

写入流程先用 Product 主 SKU 查找 `offerId`：

- 不存在：通过现有 `ProductAdminMutationService` 和仓储创建商品、报价、价格、媒体、Store 与分类关联。
- 已存在且来源为同一 `offerId`：更新可变字段和媒体，不新增重复 Product。
- 已存在但不是 1688 来源或来源冲突：停止该 offer，输出 `identity_conflict`，不得覆盖。

一个店铺只有在采集快照完整时才能进入导入。导入按店铺分批，单个 offer 失败不伪装成功；失败项可根据同一快照安全重跑。首版不自动删除或禁用“本次未再次发现”的旧 1688 商品，只报告 stale 候选，避免把临时下架误判成永久删除。

## 6. 数据流

```text
后台品牌/供应商
  -> 店铺主体核验
  -> supplier-brand 来源清单
  -> 店铺全部分页快照
  -> offerId 去重与归属解析
  -> dry-run 导入预览
  -> 分店铺幂等写入
  -> 重跑验证
  -> 后台浏览器验收
```

清理流程独立于采集流程：

```text
冻结 29 个商品
  -> 依赖与文件预检
  -> selection_digest
  -> 用户已批准的 apply
  -> 数据库零残留验证
  -> 文件引用归零后清理
  -> 保留对象计数回读
  -> 允许正式导入
```

## 7. 运行产物

所有运行产物位于非公开运行目录 `var/hanfu-1688/<run-id>/`，不进入商品媒体目录：

- `cleanup-preflight.json`：29 个商品及全部从属记录和文件清单；
- `cleanup-report.json`：逐表、逐商品和逐文件处理结果；
- `source-map.json`：品牌、供应商和真实店铺映射；
- `crawl-manifest.json`：逐店铺分页、offer 与完整性证据；
- `import-preview.json`：新增、更新、冲突、跳过计划；
- `import-report.json`：逐店铺发现、新增、更新、跳过、失败计数；
- `verification.json`：幂等重跑与后台验收结果。

报告不得包含 Cookie、令牌、订单详情、收货地址或其他账号敏感信息。

## 8. 错误处理与恢复

- 清理摘要漂移：零写入退出，重新生成预检并重新确认范围。
- 商品级清理失败：记录已完成项并停止正式导入；验证模式给出剩余从属记录。
- 文件仍被引用：保留文件并报告引用来源，不强删。
- 店铺主体不一致：供应商映射失败，不导入该店铺。
- 分页不完整：该店铺快照无效，不导入部分结果。
- offer 详情暂时失败：保留在失败清单，可按相同快照重试。
- 媒体下载失败：商品写入不得冒充完全成功；根据事务边界回滚该商品或保留为带明确失败状态的草稿。
- 验证码：停止浏览器操作并请求用户决定是否接管处理，不尝试绕过。
- 后台验收失败：保留可重跑脚本、快照与报告，不通过额外臆测逻辑掩盖失败。

## 9. 测试与验收

### 9.1 开发测试

最小测试集覆盖：

1. 清理 dry-run 精确选中 29 个商品，不选中新增或非目标商品。
2. 摘要漂移时 apply 拒绝执行。
3. 媒体共享引用大于零时只移除目标媒体关系，不删除共享对象。
4. 分类、品牌、供应商在清理前后 ID 集合与计数不变。
5. 分页去重、自然终点、重复页和安全上限失败语义。
6. 独占店铺、多品牌唯一匹配、零匹配和多匹配的品牌解析。
7. `offerId` 首次创建、重复更新和身份冲突。
8. 媒体下载校验与失败回滚。

### 9.2 真实运行时验收

清理验收：

- 在正式导入开始前，后台商品搜索结果为 0；
- 目标商品相关 Offer、价格、库存、属性、分类与 Store 关联为 0；
- 清理门禁通过时允许待验证文件处于有报告的隔离状态；整个任务最终完成前，29 个商品的无引用独占媒体必须从活动目录和隔离区永久清除；
- 分类、品牌、供应商和保留资产仍存在。

采集与导入验收：

- 每个目标品牌都有“已核验店铺”或“无可靠货源”的明确结论；
- 每个已匹配店铺都有自然分页终点证据及发现、导入、跳过、失败计数；
- 所有 active 且用于导入的供应商都有真实可打开、主体一致的店铺地址；
- 后台可见导入商品，品牌、供应商、分类、价格和媒体关系正确；
- 使用同一快照重跑后 Product 总数不增加，只产生更新或无变化；
- 再次抓取时按新快照增量更新，身份冲突和 stale 候选有单独报告。

浏览器验收使用用户指定的内置浏览器，覆盖 1688 店铺主体页、本地后台商品列表、商品详情和供应商列表。CLI 与浏览器证据必须同时存在；只通过单元测试或 curl 不视为完成。

## 10. 交付与安全边界

实现完成后，模块 `doc/需求.md` 与 `doc/开发日志.md` 必须同步记录实际行为、验证命令、逐店铺统计和探活后的后台地址。

最终交付必须列出：

- 1688 已核验店铺页面；
- 本地后台商品列表与供应商列表；
