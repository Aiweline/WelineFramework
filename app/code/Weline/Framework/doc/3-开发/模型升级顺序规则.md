# 模型升级顺序规则

## 概述

在系统升级过程中，模型的安装和升级顺序非常重要。如果模型之间存在依赖关系，错误的升级顺序可能导致数据库表创建失败或其他错误。

为了确保模型按照正确的顺序进行升级，框架实现了基于**目录层级深度**和**类名长度**的自动排序机制。

## 排序规则

模型升级顺序按照以下优先级规则进行排序（优先级从高到低）：

### 1. 目录层级深度（第一优先级）

**规则：目录层级越浅（深度越小）的模型越先升级**

目录层级深度通过类命名空间中的反斜杠（`\`）数量来计算。

**示例：**

```
Weline\Eav\Model\EavEntity                    // 层级深度：3（Model）
Weline\Eav\Model\EavAttribute                 // 层级深度：3（Model）
Weline\Eav\Model\EavAttribute\Type            // 层级深度：4（Model\EavAttribute）
Weline\Eav\Model\EavAttribute\Type\Value      // 层级深度：5（Model\EavAttribute\Type）
```

**升级顺序：**
1. `Weline\Eav\Model\EavEntity`（层级 3）
2. `Weline\Eav\Model\EavAttribute`（层级 3）
3. `Weline\Eav\Model\EavAttribute\Type`（层级 4）
4. `Weline\Eav\Model\EavAttribute\Type\Value`（层级 5）

### 2. 类名长度（第二优先级）

**规则：在相同目录层级下，类名越短的模型越先升级**

当两个模型的目录层级深度相同时，按照类名的字符长度进行排序。

**示例：**

```
Weline\Eav\Model\EavEntity        // 层级：3，长度：32
Weline\Eav\Model\EavAttribute      // 层级：3，长度：35
```

**升级顺序：**
1. `Weline\Eav\Model\EavEntity`（层级 3，长度 32）
2. `Weline\Eav\Model\EavAttribute`（层级 3，长度 35）

### 3. 字母顺序（第三优先级）

**规则：在相同层级和长度下，按字母顺序排序**

当两个模型的目录层级深度和类名长度都相同时，按照字母顺序进行排序，确保排序的稳定性。

**示例：**

```
Weline\Eav\Model\EavAttribute\Type\Value      // 层级：5，长度：45
Weline\Eav\Model\EavAttribute\Type\Option    // 层级：5，长度：45
```

**升级顺序：**
1. `Weline\Eav\Model\EavAttribute\Type\Option`（按字母顺序，O 在 V 之前）
2. `Weline\Eav\Model\EavAttribute\Type\Value`

## 为什么需要这个规则？

### 问题场景

在 EAV（Entity-Attribute-Value）模型中，存在以下依赖关系：

1. `EavEntity` - 实体模型（基础表）
2. `EavAttribute` - 属性模型（依赖实体）
3. `EavAttribute\Type` - 属性类型模型（依赖属性）
4. `EavAttribute\Type\Value` - 属性值模型（依赖属性和类型）

如果 `Value` 模型在 `EavAttribute` 和 `EavAttribute\Type` 之前升级，可能会因为依赖的表不存在而失败。

### 解决方案

通过按照目录层级深度和类名长度排序，确保：

- **基础模型先升级**：层级较浅的模型（如 `EavEntity`）会先于层级较深的模型（如 `EavAttribute\Type\Value`）升级
- **依赖关系正确**：被依赖的模型会在依赖它的模型之前升级
- **稳定性**：排序规则明确，不会因为文件系统顺序或其他因素导致不一致

## 实际应用示例

假设有以下模型结构：

```
Weline\Eav\Model\
├── EavEntity.php                    // 层级 3
├── EavAttribute.php                 // 层级 3
└── EavAttribute\
    ├── Type.php                     // 层级 4
    ├── Option.php                   // 层级 4
    └── Type\
        └── Value.php                // 层级 5
```

**升级顺序：**

1. `Weline\Eav\Model\EavEntity`（层级 3，长度 32）
2. `Weline\Eav\Model\EavAttribute`（层级 3，长度 35）
3. `Weline\Eav\Model\EavAttribute\Option`（层级 4，长度 42）
4. `Weline\Eav\Model\EavAttribute\Type`（层级 4，长度 41）
5. `Weline\Eav\Model\EavAttribute\Type\Value`（层级 5，长度 45）

## 开发者注意事项

### Schema checkpoint 表身份

`setup:upgrade` 会以“模块名 + 模块版本 + 声明式表结构”记录不可变的 Schema checkpoint。
同一版本的列、索引、外键或表注释发生语义变化时，必须提升模块版本，不得删除或改写历史 checkpoint。

format 2 checkpoint 会从连接器实际格式化的探针表名中提取当前连接主动注入的
database/catalog/schema 限定符，并只按精确大小写去掉该限定符；方言引号不属于身份。
配置中的数据库名、SQLite `temp` 等约定名称不会被推测为当前限定符。比如当前 PostgreSQL schema
为 `public` 时，`"public"."w_role"` 与历史 `"w_role"` 表示同一逻辑表；`"Public".w_role`、
`audit.w_role` 仍是其他显式表身份。带点的引号标识符按分段编码，不能在去重阶段互相吞并。
若同一模块的两张表归一化后身份碰撞，升级会在执行任何 DDL 前硬失败。

历史 format 1 checkpoint 继续按其原始格式和校验和只读验证；执行器会在当前逻辑身份与旧限定名候选中
选择唯一匹配项，不改写历史记录。新模块版本只写 format 2。这一兼容规则只排除部署限定名差异，
列、索引、外键和表注释的真实变化仍要求提升模块版本。

### 单命令 SchemaDiff 阶段约束

`setup:upgrade` 在执行 pending module registration 前必须先准备并提交 Framework bootstrap、EAV 和 SchemaDiff，因为 Theme/I18n/ACL 等注册器会立即读取目标表。后续通用 `StageUpdateManager` 必须复用这三个已 prepared/committed 的同一实例，不得重新构造另一个 `SchemaDiffStage`。

### SchemaProvider 与分片 DDL

`SchemaDiffStage::prepare` 在扫描 Model `#[Col]` 之后，还会合入 `extends/module/Weline_Framework/Schema/` 下全部 `SchemaProviderInterface` 的 `getTableSchemas()`。重复表声明立即硬失败。

物理分片族实现 `ShardSchemaFamilyProviderInterface`：

- `getFamilyCode()` 全局唯一；
- `getSchemaVersion()` 作为 `shard:{family}` 的 Schema checkpoint 版本；声明变更时必须提升，否则同版本不同指纹会硬失败；
- `getRegisteredShardKeys()` / `getTableSchemasForShard($shardKey)` 供单站 provision；
- 无参 `getTableSchemas()` 必须展开全部已注册分片，供 `setup:upgrade` 枚举；
- 单站 DDL 走 `ShardSchemaProvisioner::provision($family, $shardKey)`（diff → `SchemaMigrationExecutor` → fingerprint）；失败状态为 `maintenance`/`failed`，**不删表**；
- `TableSchema` 建表必须严格收敛为声明列；声明式路径调用 `CreateInterface::create(false)`，不得隐式补 `create_time` / `update_time`。旧建表 API 的无参 `create()` 仍保留自动时间列，避免破坏既有模块；
- 每条 DDL 必须先取得有效 `migration_id`，执行后 `installed` 状态写回必须成功；审计落盘或状态写回失败时立即 fail-closed，不得继续伪装成功；
- 业务写只用 `DatabaseTransactionRunnerInterface`（包装 `TransactionContext::enter/leave`，禁止伪造 `TransactionContext::run()`），且前置条件是分片 `ready`；DDL 与 DML 不得同事务。

`website_id=0` 合法；仅 `website_id < 0` 非法。

### PostgreSQL 类型与 DDL 回读契约

- PostgreSQL 的 `NUMERIC(p,s)` 必须同时回读 `numeric_precision` 和 `numeric_scale`；`DECIMAL`/`NUMERIC`、`TINYINT`/`SMALLINT`、`CHAR`/`CHARACTER`、`FLOAT`/`REAL` 等按声明到物理映射比较，不得每轮重写同一列。
- 类型转换只能处理未引号的 SQL 语法 token；双引号标识符、单引号默认值和 `COMMENT` 文本不得进入全局正则替换。例如字段 `"json"` 和文案 `配置JSON` 必须保持原值，不能被改成 `"JSONB"` / `配置JSONB`。
- PostgreSQL `ALTER COLUMN` 修复列时必须同步发布 `COMMENT ON COLUMN`；否则被旧版建表器污染的注释会永久重复 MODIFY。
- Schema checkpoint 的只读门禁必须与升级执行器复用同一组 current / historical / legacy 指纹候选。PostgreSQL 历史 checkpoint 中的 `"w_table"` 与当前 canonical 身份 `w_table` 只有引号风格差异且候选 checksum 完全一致时视为兼容；任何真实表结构指纹变化仍必须报告漂移并 fail-closed。

### 列级 UNIQUE 的索引所有权

- `#[Col(unique: true)]` 是“该列必须单列唯一”的语义事实，不拥有固定索引名。同列显式单列 `#[Index(type: 'UNIQUE')]` 可承载它；普通索引和复合 UNIQUE 不能代替单列唯一语义。
- 新 CREATE/ADD 的非主键 UNIQUE 统一由外置索引承载，列 DDL 必须将 `unique` 物理选项收口为 false，不得同时产生列内约束和外置索引。没有显式承载者时，执行期生成稳定隐式名；该名必须同时避让声明名、现存名和适配器物理名，但不写回 `TableSchema` 或 checkpoint。SQLite MODIFY 只在旧物理列真实含 inline UNIQUE 时保留该历史所有权；普通属性修改不得静默丢失旧库唯一性，也不得新建第二份唯一索引。
- 所有显式索引名在忽略大小写后必须唯一，映射后物理身份也必须唯一。MySQL 显式名不得超过 64 个字符；PostgreSQL 新物理名使用表所有的 canonical name，在有效 UTF-8 边界内不超过 63 bytes，并只读兼容旧名。
- SchemaDiff 对同名索引必须比较精确列序、唯一/全文/普通类型和方言支持的 method。同名错定义在任何 DDL 之前硬失败，不得伪装为零差异，也不得自动破坏性替换。
- CREATE 后以及每次 ADD/DROP INDEX 后都要回读物理定义。prepare 后才出现的同名表视为过期 CREATE 计划并拒绝接管；部署期间不得并发执行两个 `setup:upgrade`。
- SQLite 历史 inline/table-level UNIQUE 以 `PRAGMA index_list.origin='u'` 识别为框架保留 surrogate。声明仍为 unique 时按精确单列语义保留；改为 false 时用 rebuild 删除约束并保留数据、普通索引与 trigger。回滚可恢复为等价外置 UNIQUE，且再次删除仍必须可收敛。显式 `#[Index]` 不得使用该保留前缀。
- SQLite 只有建表 SQL 明确出现 `AUTOINCREMENT` 时才回读 `autoIncrement=true`；不得把任意单列 `INTEGER/INT PRIMARY KEY` 的 rowid 别名推断为声明式自增。SQLite 不允许复合主键列使用 AUTOINCREMENT，因此创建器会抑制该物理 token，SchemaDiff 对“复合主键声明 true / 物理 false”按方言映射收敛。

因此，一次完整升级或 `--stage=schema_diff` 调用中，SchemaDiff 最多 prepare/commit 一次，每个模块最多写一个当前版本 checkpoint。后段提交器看到 `isCommitted()` 时只记录“已前置提交”并跳过；不得依赖“第二轮恰好无差异”来得到幂等外观。若后续阶段验证失败，保持原有边界：不回滚 pending registration 已依赖的前置数据库事实，只回滚尚未提交的准备阶段。

### 单次升级 operation_id 边界

每次非 hot `setup:upgrade` 在通过参数校验后建立一个长度不超过 64 字符的进程内操作 ID，并在命令最外层 `finally` 清理。嵌套或重入 begin 必须明确拒绝，不得清掉、替换或复用外层 ID；`--hot` 不建立操作 ID。

Upgrade 把该 ID 显式传给 `SchemaDiffStage::prepare()` 和 `upgrade_after` 事件。SchemaDiff DDL、Schema checkpoint 以及 Setup Observer 触发的脚本 migration 因此共用同一 ID，包括已落盘后转为 `failed` 的记录。独立 migration/rollback 服务不读取该上下文，只有调用方显式传入时才写 `operation_id`。无 Schema diff 且无 pending script 的 Run2 不新增 migration 记录。

### Setup / Cron 数据库访问协调

`setup:upgrade` 与 `cron:task:run` 通过稳定的 `var/process/setup_database_access.lock` 协调同一应用实例的数据库访问。顶层 `bin/w` / `bin/m` 在应用 bootstrap 前取得门禁：Setup 非 hot 命令使用 EX，Cron 以及 Setup hot/help 使用 SH。顶层入口租约贯穿 bootstrap、命令、`command_executed`、footer、可选 follow-up、异常渲染和全部 shutdown 回调，直到 PHP 进程退出后由运行时关闭描述符。协调文件永久保留，状态只由实际 `flock` 决定；锁打开/获取发生真实错误时必须 fail-closed。

锁忙分支在取得租约之前只能使用 `DatabaseFreeTranslator` 从 `app/etc/env.php` 文本和模块 i18n CSV 生成提示；禁止调用常规 `__()`、Cache、Event 或 Model。`CronTask` 也不能在 `Run` 构造器注入，只能在共享锁内延迟解析，因为 Model `__init()` 可能初始化数据库连接。

绕过顶层入口直接执行命令时，命令本地取得租约，并通过不可克隆的 `CommandResult` finalizer 在 Cli post/footer 完成后释放；直接调用者必须在自己的 `finally` 中显式 `finalize()`。受管 Cron 子进程取得 SH 后先发布 READY，等待父进程完成 `BLOCK/pid=0 → RUNNING/pid` 围栏 CAS；只有收到 GO 后才能解析 Model 并执行业务。任何交接失败都必须先发布 ABORT，再进行身份安全终止和围栏失败写入。完整协议见 `app/code/Weline/Cron/doc/开发/setup_cron_database_access_coordination.md`。

### 旧 MySQL Alter 迁移幂等性

声明式 SchemaDiff 可能已在模块历史 migration 之前创建相同列。旧 migration 即使检查到所有列都存在，仍可安全调用 MySQL `Alter::alter()`：没有待执行变更时不发送 SQL，不得把 `NULL` 交给 Query；执行 ADD/COMMENT 后，如果没有显式 `new_table_name`，不得在方法末尾重复执行上一条 SQL。只有 `forTable(..., new_table_name: ...)` 明确请求重命名时，末尾才生成并执行 `ALTER TABLE ... RENAME TO ...`。

MySQL 冷建表的整数类型必须保持声明语义：`INTEGER(1)` 仍是 `INT`，`SMALLINT` 仍是 `SMALLINT`。显示宽度不是存储范围选择器，不得按 `length <= 2` 把 INTEGER 降成 SMALLINT，也不得因默认宽度把 SMALLINT 升成 INT。冷 CREATE 与增量 ALTER 对同一 `#[Col]` 必须产生相同类型，否则第二次 `setup:upgrade` 会产生伪 MODIFY。

### 1. 模型目录结构规划

在创建模型时，应该遵循以下原则：

- **基础模型放在 `Model` 目录下**：如 `Model\EavEntity.php`
- **依赖模型放在子目录中**：如 `Model\EavAttribute\Type\Value.php`
- **目录层级反映依赖关系**：被依赖的模型应该在更浅的目录层级

### 2. 避免循环依赖

虽然排序规则可以处理大部分依赖关系，但**无法处理循环依赖**。如果模型之间存在循环依赖，需要重新设计模型结构。

### 3. 测试升级顺序

在开发新模型时，建议：

1. 检查模型的依赖关系
2. 确保模型目录结构符合依赖关系
3. 在测试环境中验证升级顺序是否正确

### 4. 特殊情况处理

如果模型之间存在特殊的依赖关系，而目录结构无法反映这种关系，可以考虑：

- 调整目录结构以反映依赖关系
- 在模型的 `install()` 或 `upgrade()` 方法中处理依赖检查
- 使用数据库迁移脚本明确处理依赖关系

## 实现细节

排序逻辑在 `Weline\Framework\Database\Model\ModelManager::sortModelsByPriority()` 方法中实现：

```php
private function sortModelsByPriority(array $model_classes): array
{
    usort($model_classes, function ($a, $b) {
        // 第一优先级：目录层级深度
        $depthA = substr_count($a, '\\');
        $depthB = substr_count($b, '\\');
        if ($depthA !== $depthB) {
            return $depthA <=> $depthB;
        }
        
        // 第二优先级：类名长度
        $lengthA = strlen($a);
        $lengthB = strlen($b);
        if ($lengthA !== $lengthB) {
            return $lengthA <=> $lengthB;
        }
        
        // 第三优先级：字母顺序
        return strcmp($a, $b);
    });
    
    return $model_classes;
}
```

## 总结

### MySQL Alter 执行约束

`alterTable()->forTable(...)->addColumn(...)->alter()` 允许只追加或修改字段，不要求同时修改表名。MySQL 适配器只有在 `new_table_name` 非空时才能执行 `RENAME TO` SQL；普通加列完成后不得再提交空 SQL。生产升级应覆盖“仅加列、仅改列、仅改表名”三类路径。

模型升级顺序规则确保了：

1. ✅ **基础模型优先**：层级较浅的模型先升级
2. ✅ **依赖关系正确**：被依赖的模型在依赖它的模型之前升级
3. ✅ **排序稳定**：排序规则明确，结果可预测
4. ✅ **易于理解**：规则简单直观，开发者容易遵循

遵循这些规则可以避免模型升级过程中的依赖问题，确保系统升级的顺利进行。
