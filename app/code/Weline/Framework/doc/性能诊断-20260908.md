## 已完成的修复与验证

### 菜单翻译批量读取

框架新增 `Parser::prefetchWords()`，菜单渲染缓存未命中时一次收集待显示标题。公共词典按语言、每批最多 200 词读取，填入原有 Worker 逐词缓存，命中和确认缺词都复用原来的失效周期；模块词典、覆盖层、语言回退及独占词典的优先级保持原有规则。独占词典请求在初始化公共 Provider 前返回。

没有新增随任意词组合增长的共享缓存键；`CachePool::getMultiple/setMultiple` 当前仍是逐项调用，不能拿它们替代批量数据库访问，否则会把 DB N+1 换成 RPC N+1。

- 定向验证：`ParserExactWordPrefetchTest`、`ParserEventScopeCacheTest`、`ParserRequestModuleCacheTest`，14 项测试、50 个断言通过。
- 当前配置、真实数据库、同一组 200 个后台菜单词（en_US）：逐词查询 200 次、823.98 ms；批量查询 1 次、14.86 ms；之后逐词解析 0 次查询、0.07 ms。
- 两条读取路径的结果完全一致：17 个命中、183 个缺词。该结果是指定环节的观测，不代表整页加速倍数。

### 修复合并事件覆盖与并发覆盖

同目标、同 scope 的 pending 槽位保留被合并事件的 `event_id/event_seq`；乱序到达时保留最新投影，同时收集旧事件身份。最终文档更新与覆盖记录共享事务，仍按连续序号推进，不越过其他商品的缺口。

队列更新增加可选 `expected_content`，比较调用方实际用于合并的内容快照。旧快照不再覆盖新写入者；发生竞争时重新读取并合并。原有调用方式与运行中任务处理保留，原 `SearchIndexStorageInterface` 签名未改。

先复现再修复的行为包括：seq 2、3 合并后水位停在 1；两个写入者均读 seq 2 后，较旧的 seq 3 覆盖 seq 4。当前均通过。Consumer、Applier、真实 `DatabaseSearchIndexStore` 的 SQLite 内存库用例验证了同品覆盖、别品缺口、投影失败与部分文档写入失败的完整回滚。

7 个定向测试类逐文件运行，总计 95 项测试、776 个断言通过；root 独立复跑结果相同。13 个 PHP 文件语法检查及定向 diff 检查通过。测试入口使用 `app/code/Weline/Search/Test/fixtures/source-bootstrap.php`，明确加载工作区源码。SQLite 验证不冒充配置环境的 PostgreSQL 全流程验收；本次未新建真实商品，未切换搜索 alias。

## 尚需处理的性能项

1. **搜索读取范围**：先验证持久索引与网站/店铺/渠道范围的一致性，再使用正式索引读模型；若保留 direct 路径，应把筛选、分页及数据读取约束到请求范围，避免每次网站水位变化都重建全站快照。本次没有盲目切换 alias。
2. **WLS 长同步段**：`FiberScheduler::tick()` 的 8 ms 预算只在下一次恢复前检查，无法抢占单次 `Fiber::start/resume`；现有 trace 证明延迟，但未指认具体占用线程的业务段。最小后续测量是在 start/resume 与 poll/tick 边界记录超过 20 ms 的执行区间、Fiber/request ID。没有证据支持直接把它归咎于 SQL 引擎或索引任务。
3. **后台 ACL 查询**：路由保护判断对多个别名分别执行 exact/LIKE 查询，样本累计约 1.29 s；可批量读取后统一判断。必须保留角色、路由和 scope 的权限隔离，不能直接共用无权限维度的菜单缓存。
4. **浏览器完整加载**：需用已登录询价页的新请求关联服务端 timing，继续验收首页/商品页页底以及一直 pending 的资源。公共 HTTP/2 响应完整和单环节变快都不等于该问题已经解决。
5. **重载可观测性**：排水超时会中止后续批次，调用方需区分 accepted、failed 和所有槽位实际换版；编译期间输入变化也会中止启动。本次只记录实际失败及恢复状态，未修改 Server 排水算法。
