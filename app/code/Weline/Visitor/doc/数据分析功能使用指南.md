# 像素数据分析功能使用指南

## 功能概述

像素数据分析系统提供了全面的数据分析和可视化功能，包括商业价值分析、实时大屏展示、数据对比分析和A/B测试管理。

## 报表查询数据源边界

- `PixelQueryRouter` 开放热明细与温聚合路由；冷明细走显式 `archive-list`（G09），不接入本聚合路由。设计冻结合同见 `Visitor_Pixel_GTM_GA4_系统设计.md` §10。
- 默认短窗上限为 7 天；热/温保留默认 365 / 1095 天（`VisitorTrackingConfig` 可配）。短窗落热；长窗或早于热保留且仍在温保留内走温（默认日表；仅超热且跨度 ≤2 天走小时表）；超温或高基维拒绝并抛 `cold archive route is not available`，不会静默扫热或伪装为空结果。
- 查询维度必须先通过 `PixelDimensionRegistry` 校验；重复维度会按首次出现顺序去重。
- `PixelReportQueryService` 热路由支持**单维** group-by；温路径对可加总指标 SUM 预聚合列；日表权威 `sessions`/`engaged`/`bounce`/`funnel_json` 不在本引擎温 SUM 范围。
- 预设报表目录：`etc/report_catalog.json`，由 `PixelReportCatalog` 加载；当前含 `pixel_channels` / `pixel_traffic_type` / `pixel_paid` / `pixel_social` / `pixel_event_value` / `pixel_value_by_channel`，可供后续 detail Tab 与部件按 `code` 引用。
- 事件价值走引擎：`PixelEventValueReportService` 通过 catalog `pixel_event_value` 按 `event_name` 聚合，行级附派生 `avg_value`；总计口径（`total_value`=SUM(value)、`total_events`=COUNT(*)、`avg_value`=均值）与旧 `Pixel::getBusinessValueByPeriod` 一致，有对齐单测保障。
- detail 引擎 Tab：`PixelDetailReportTabService` **每次只追加 1 个** catalog 报表；**D07a–D07f 已全部挂完**六个预设（`pixel_channels` / `pixel_traffic_type` / `pixel_paid` / `pixel_social` / `pixel_event_value` / `pixel_value_by_channel`）。长于 7 天的筛选会钳到热短窗；带 catalog filters 的 Tab（`pixel_paid`/`pixel_social`）在热行取回后就地过滤，仅取数一次，下钻链接同时带上该 filter 与维度值；事件价值 Tab 的 `avg_value` 复用 `PixelEventValueReportService::decorateRows()`；渠道价值 Tab 指标更窄（仅 `events`/`value_sum`/`valued_events`）。
- Dashboard 部件：catalog 六个预设（E01–E04b）已注册于 `extends/.../widget.php`；模板走对应 `get*Report()`；**E05** 已将六 code **追加**进 `VisitorDashboardPageInstaller` 种子布局（`replace_layout=false`，不整页覆盖运营已存布局；已有页靠 `default_injections`/`layout_identity_ready` 可选补齐）。
- 部件下钻 URL（E06）：有 `websiteId` 且无 `event` 时 `detailUrl` → `pixel-dashboard/detail`；带 `event` 或无站点时 → `index`；行下钻/`事件列表` 走 `listUrl`→`pixel-dashboard/list`（键集与 C07 `LIST_DRILLDOWN_QUERY_KEYS` 一致）；路由一律短横线 `pixel-dashboard`。
- 电商漏斗（F01）：`PixelEcommerceFunnelService` 按字典四步 `view_item → add_to_cart → begin_checkout → checkout_success`（`purchase` 兼容末步）在热表按 session 顺序去重；长于热短窗会钳制；已挂像素详情报表「电商漏斗」卡片。单渠道口径见 F05b。
- 购成与收入（F02）：`PixelEcommercePurchaseRevenueService` 统计 `purchases` / `purchase_revenue`（**仅**购买类事件 value）/ AOV / 相对 `view_item` 会话的购成率；支持按渠道、按日拆分；已挂详情报表「购成与收入」卡片。
- 商品表现（F03）：`PixelEcommerceItemPerformanceService` 从 `browser_info.additionalInfo.ecommerce.items` 展开，按 `item_id` 聚合曝光/加购/结账/购买与商品收入；prepare/JS worker 压缩已保留 items；已挂详情报表「商品表现」卡片。
- 路径探索（F04a 简版）：`PixelPathExplorationService` 仅取页面事件（`page_view`/`page_enter`），按 session 时间序构建路径，相邻重复折叠、限深 3 步，输出 Top 落地页 → 次页分布（含单页离站）与 Top 路径序列；仅用 `url` 扁平列（不拉 `browser_info`）、扫描封顶 2 万行、长窗钳到热短窗；已挂详情报表「路径探索」卡片。留存分析属 F04b。
- 留存分析（F04b 简版）：`PixelRetentionService` 按日队列（Day0–Day6）计算留存；访客键优先 `user_id`，匿名用 IP+UA 软指纹；超出筛选窗的偏移不计入分母；输出回访率、次日留存与队列矩阵；已挂详情报表「留存分析」卡片。
- 电商部件（F05a）：Dashboard 注册 `pixel_ecommerce_funnel` / `pixel_ecommerce_revenue` / `pixel_ecommerce_items`，分别复用 F01/F02/F03；`VisitorDashboardPageInstaller` 增量追加种子（`replace_layout=false`）；需站点作用域，详情报表下钻带 `#ecommerce-*` 锚点。
- 渠道漏斗可切换（F05b）：流量渠道详情的漏斗卡片支持 `funnel_mode=marketing|ecommerce`，缺省仍是 B12 营销简漏斗（落地 → 互动 → 加购 → 转化），旧链接语义不变；切到 `ecommerce` 走 `PixelChannelEcommerceFunnelService`，步骤/比率/顺序门槛完全复用 F01（`view_item → add_to_cart → begin_checkout → checkout_success`，`purchase` 兼容末步），仅把取数范围换成 `channel_code`（+ 站点绑定）。两种模式共用渠道详情的 7/30 天窗口（`PixelChannelHotTotalsService::resolveWindow`）而非报表引擎热短窗，保证切换时窗口可比；模式与日窗切换互相保留参数并锚回 `#channel-funnel`。
- 小时聚合温表（G01）：`Model/PixelStatsHourly`（表 `pixel_stats_hourly`）为归档波次 G 的第一张温表，本 WP 仅落 schema、不跑 Cron（写入在 G04）。列含流量维（`traffic_type` / `channel_code` / `utm_source` / `utm_medium` / `utm_campaign` / `event_name` / `device_category`）与小时指标（`events` / `value_sum` / `valued_events` / `session_starts` / `purchases` / `add_to_carts`）；唯一键 `(hour_bucket, website_id, dim_hash)` 保证 UPSERT 幂等重跑覆盖，`tz` 记录小时桶所用时区。`dim_hash` 契约由 `PixelStatsHourly::dimHash()` 提供：对 `DIM_FIELDS` 有序取值、逐维小写去空白后以 `\x1f` 连接再 sha1，大小写/空白/键序不影响结果，白名单外维（如高基 `page_path`）不参与也不入表。会话口径提示：`session_starts` 只是当桶起始数，**权威会话数在日表（G02）**，禁止 SUM 小时当会话数。
- 日聚合温表（G02）：`Model/PixelStatsDaily`（表 `pixel_stats_daily`）复用 G01 的流量维、`DIM_FIELDS`、`dimHash()` 与 `normalizeDims()`，唯一键为 `(day_bucket, website_id, dim_hash)`；`day_bucket` 按站点时区生成，`tz` 记录实际时区。日指标包含全部小时指标，并增加日内按 `session_id` 去重的权威 `sessions`、`engaged_sessions`、`bounce_sessions`、`conversions` 与 `funnel_json`。`funnel_json` 仅保存 G05 计算的日漏斗摘要，不保存事件明细、不是新的事实源。G02 仍只落 schema、不跑 Cron；实际日聚合、校验和覆盖式 UPSERT 在 G05。`website_id=0` 是合法的系统默认站点，不得当作缺失站点过滤。
- 聚合任务日志表（G03）：`Model/PixelStatsJobLog`（表 `pixel_stats_job_log`）为归档波次的任务台账，本 WP 仅落 schema、不接 Cron（写入方为 G04/G05）。每个聚合桶一行，唯一键 `(job_type, bucket, website_id)`，重跑覆盖同一行并累加 `attempts`；`job_type` 取 `hourly|daily`，`bucket` 为整点或当日 00:00:00（站点时区），`tz` 记录该桶实际使用的时区。`status` 取 `pending|running|success|failed`；`check_json` 保存 G05 的校验摘要（日表 `events` 与热表同日 COUNT 的 expected/actual/rel_error/abs_diff），`message` 存失败原因。G08 Retention 以 `status=success` 为**唯一放行凭据**：失败或缺行的日期一律跳过迁冷/删热，日志缺失不默认放行。
- 小时聚合 Cron（G04）：`Service/PixelStatsHourlyAggregateService` + `Cron/PixelStatsHourly`（`5 * * * *`）。按站点时区取上一完整小时，从热表 `w_pixel` 聚合写入 `pixel_stats_hourly`（覆盖式：先清该站该桶再批量插入，等价 UPSERT 全量覆盖），并写 `pixel_stats_job_log`（running→success/failed，累加 attempts，记录 tz）。指标含 events/value_sum/valued_events/session_starts/purchases/add_to_carts；`session_starts` 仅计会话全局 first_at 落在本小时的首事件维；`dim_hash` 走 G01 `PixelStatsHourly::dimHash`；`device_category` 缺省时由 UA/browser_info 派生。website_id=0 始终纳入目标站。本 WP 不写日表、不删热。
- 日聚合 Cron（G05）：`Service/PixelStatsDailyAggregateService` + `Cron/PixelStatsDaily`（`15 1 * * *`）。按站点时区取前一完整日，从热表聚合写入 `pixel_stats_daily`（覆盖式清桶再插入），并写 `pixel_stats_job_log`（`job_type=daily`，bucket=`Y-m-d 00:00:00`）。除小时同款指标外，计算权威 `sessions` / `engaged_sessions` / `bounce_sessions`（对齐 Insight：参与事件或 dwell≥10s 为 engaged；未参与且 ≤1 次 page_view、≤2 事件、时长&lt;10s 为 bounce）、`conversions`（checkout_success|purchase|lead_submit）与站点级营销漏斗摘要 `funnel_json`。§2.5 校验：日表 `events` 合计与热表同日 COUNT 相对误差 ≤2% 或绝对差 ≤5，失败则 `status=failed`（G08 Retention 跳过该日），`check_json` 存 expected/actual/rel_error/abs_diff。不删热。
- QueryRouter 接温（G06）：`Service/Report/PixelQueryRouter` 短窗（≤7 天且落在热保留 365 天内）仍走 `hot`/`w_pixel`；长窗或早于热保留但仍在温保留（1095 天）内走温——默认 `warm_daily`/`pixel_stats_daily`/`day_bucket`，仅超热保留且跨度 ≤2 天时走 `warm_hourly`。高基维（`page_path`/`landing_page`）及非默认温维拒绝温路由；超温保留抛 `cold archive route is not available`（冷明细见 G09，禁止静默扫热）。`PixelReportQueryService` 温路径对可加总指标（events/value_sum/valued_events/purchases/add_to_carts）SUM 预聚合列；权威 sessions/engaged/bounce 不在本引擎温 SUM 范围。
- 冷归档表与手动迁移（G07）：`Model/PixelArchive`（表 `pixel_archive`）镜像热表明细列并保留原 `pixel_id`（唯一）与 `archived_at`；索引 `(website_id, created_at)` 供 G09 冷查。`Service/PixelArchiveMigrateService` + `Console/Pixel/ArchiveMigrate`（`pixel:archive-migrate`）支持 dry-run / apply（apply 需 `--enable-apply`），按 `--before`（默认 now-365d UTC）分批复制；已归档 `pixel_id` 幂等跳过。**本命令永不删除 `w_pixel`**（删热仅 G08 Retention）。
- 热表 Retention（G08）：`Service/PixelHotRetentionService` + `Console/Pixel/HotRetention`（`pixel:hot-retention`）。仅当 `created_at < now - hot_days`（默认 365）且对应站点日桶在 `pixel_stats_job_log` 为 `job_type=daily` + `status=success` 时，才「先迁冷再删热」；failed/缺行日一律跳过，绝不默认放行。默认 dry-run；正式执行需 `--enable-apply` **且** `--enable-delete` 双开关。可配天数 UI 见 G10。
- 冷查 UI 强约束（G09）：显式入口 `Controller/Backend/PixelDashboard::archiveList` → `pixel-dashboard/archive-list`（ACL `pixel_dashboard_archive_list`），取数 `Service/PixelColdArchiveQueryService` 读 `pixel_archive`。**硬拒绝**：缺站点/`all`；时间窗 &gt;31 天（含 `90d` 预设）；查询始终分页（默认 50、最大 200）。`website_id=0` 为合法系统默认站。热表明细页提供「冷归档明细」入口；报表聚合路由超温仍抛 `cold archive route is not available`，禁止静默扫热。
- 热温冷保留配置（G10）：`VisitorTrackingConfig` 键 `visitor/tracking/retention_hot_days`（默认 365）、`retention_warm_days`（默认 1095，且 ≥ 热天数）、`cold_archive_enabled`（默认 true）。后台 SystemConfig「热温冷保留策略」可改；`getRuntimeConfig().retention` 暴露 hotDays/warmDays/coldArchiveEnabled。`pixel:hot-retention` / `pixel:archive-migrate` 默认天数读配置，`cold_archive_enabled=0` 时 apply 阻断；`PixelReportQueryService` 未注入 router 时按配置构造热/温边界。
- 单测门禁（H01）：波次 G 门禁脚本 `test/Unit/gate-wave-g.sh`（schema/Cron/Router/archive/Retention/冷查/保留配置 + 下钻契约）；已修复 detail 模板下钻断言为 D07 `$dimExtras`/`drilldownExtras`；补齐 `PixelStatsDaily`/`PixelStatsJobLog`/`PixelArchive` schema 契约单测。VendorSplitSnapshot setup 红灯仍非本模块。

## 功能模块

### 0. Dashboard 事件统计视图

#### 功能说明
- Visitor 安装/升级时会通过 `Weline_Dashboard::layout_page_ensure` 创建自己的 Dashboard 页面身份。
- 页面名称为“事件统计”，视图 code 为 `weline_visitor_event_statistics`。
- 六个 Visitor Dashboard 部件通过 `default_injections.default_view = weline_visitor_event_statistics` 定向自动进入该视图：像素概览、像素参与度、像素事件趋势、像素实时动向、热门像素事件、热门页面。
- 未声明 `default_view` 的部件不会自动进入任何 Dashboard 视图；上述六个部件也不会自动污染默认概览或用户自建视图。
- 该页面和 Dashboard 默认概览是两个不同的布局身份；用户编辑或保存“事件统计”页不会影响默认概览，反过来也一样。
- 如果用户已经在布局编辑器删除过某个自动部件，系统会记录 `user_deleted`，后续安装/升级/刷新不会自动补回；可在部件库“应用”tab 手动恢复。
- 如果用户已经保存过“事件统计”页布局（含整页清空哨兵），后续安装/升级不会整页强制重种。

#### 访问页面
```
/weline_dashboard/backend/dashboard/index?website_id={website_id}&view_id={view_id}
```

`view_id` 由 Dashboard 页面身份创建后分配。后台 Dashboard 顶部视图切换中会出现“事件统计”入口。

### 1. 商业价值分析

#### 功能说明
- 支持多时间维度统计：每天、每周、每月、每季度、每年
- 提供价值趋势图和事件趋势图
- 显示详细的数据表格，包括转化率等指标

#### API接口
```
GET /visitor/rest/v1/analytics/business-value
```

#### 参数说明
- `websiteId` (可选): 站点ID
- `period` (必填): 时间维度 (daily|weekly|monthly|quarterly|yearly)
- `startDate` (可选): 开始日期 (格式: YYYY-MM-DD)
- `endDate` (可选): 结束日期 (格式: YYYY-MM-DD)

#### 访问页面
```
/visitor/analytics/panel
切换到"商业价值"标签页
```

### 2. 实时大屏展示

#### 功能说明
- 实时数据展示（10分钟/30分钟粒度）
- 自动刷新功能（每30秒）
- 价值趋势图和事件趋势图
- 变化百分比显示

#### API接口
```
GET /visitor/rest/v1/analytics/dashboard
```

#### 参数说明
- `websiteId` (可选): 站点ID
- `interval` (可选): 时间间隔，10或30分钟，默认10
- `hours` (可选): 获取最近N小时的数据，默认24

#### 访问页面
```
/visitor/analytics/dashboard  (大屏展示页面)
/visitor/analytics/panel      (切换到"实时大屏"标签页)
```

#### 参数说明

/visitor/analytics/panel

### 4. 数据变化百分比

#### 功能说明
- 显示每个时刻相比前一时刻的变化百分比
- 支持10分钟和30分钟粒度

#### API接口
```
GET /visitor/rest/v1/analytics/change-percentage
```

#### 参数说明
- `websiteId` (可选): 站点ID
- `interval` (可选): 时间间隔，10或30分钟，默认10
- `hours` (可选): 获取最近N小时的数据，默认24

### 5. A/B测试管理

#### 功能说明
- 创建A/B测试配置
- 查看测试列表
- 查看测试数据和对比结果
- 自动判断获胜变体

#### API接口

##### 创建A/B测试
```
POST /visitor/rest/v1/analytics/ab-test/create
```

请求体：
```json
{
  "testId": "test_001",
  "name": "首页按钮颜色测试",
  "description": "测试不同按钮颜色对转化率的影响",
  "websiteId": 1,
  "variantA": {"color": "blue"},
  "variantB": {"color": "red"},
  "trafficSplit": "50:50",
  "status": "active",
  "startDate": "2025-01-01 00:00:00",
  "endDate": "2025-01-31 23:59:59"
}
```

##### 获取A/B测试列表
```
GET /visitor/rest/v1/analytics/ab-test/list
```

参数说明：
- `websiteId` (可选): 站点ID
- `status` (可选): 状态筛选 (active|paused|completed|draft)

##### 获取A/B测试数据
```
GET /visitor/rest/v1/analytics/ab-test
```

参数说明：
- `websiteId` (可选): 站点ID
- `testId` (必填): 测试ID
- `variant` (可选): 测试变体 (A|B)

#### 访问页面
```
/visitor/analytics/panel
切换到"A/B测试"标签页
```

## 数据模型

### A/B测试模型 (AbTest)

#### 字段说明
- `test_id`: 测试ID（唯一标识）
- `website_id`: 站点ID
- `name`: 测试名称
- `description`: 测试描述
- `status`: 状态 (active|paused|completed|draft)
- `start_date`: 开始时间
- `end_date`: 结束时间
- `variant_a`: 变体A配置（JSON格式）
- `variant_b`: 变体B配置（JSON格式）
- `traffic_split`: 流量分配比例（如：50:50）

#### 状态说明
- `active`: 测试进行中
- `paused`: 测试暂停
- `completed`: 测试已完成
- `draft`: 草稿状态

## 使用示例

### 示例1: 获取每日商业价值数据
```javascript
fetch('/visitor/rest/v1/analytics/business-value?period=daily&websiteId=1')
  .then(res => res.json())
  .then(data => {
    console.log('总价值:', data.data.total_value);
    console.log('总事件数:', data.data.total_events);
  });
```

### 示例2: 创建A/B测试
```javascript
fetch('/visitor/rest/v1/analytics/ab-test/create', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    testId: 'button_color_test',
    name: '按钮颜色测试',
    websiteId: 1,
    variantA: { color: 'blue' },
    variantB: { color: 'red' },
    trafficSplit: '50:50',
    status: 'active'
  })
})
  .then(res => res.json())
  .then(data => {
    console.log('创建成功:', data);
  });
```

### 示例3: 获取实时大屏数据
```javascript
fetch('/visitor/rest/v1/analytics/dashboard?interval=10&hours=24')
  .then(res => res.json())
  .then(data => {
    console.log('当前价值:', data.data.current_period.value);
    console.log('变化百分比:', data.data.change_percentage);
  });
```

## 注意事项

1. **站点ID**: 如果不提供站点ID，系统会使用默认值0或从SERVER变量获取
2. **时间格式**: 日期格式为 YYYY-MM-DD，时间格式为 YYYY-MM-DD HH:MM:SS
3. **A/B测试数据**: A/B测试数据存储在PixelAdditional表的total_event_data字段中，需要包含testId和variant字段
4. **自动刷新**: 大屏展示页面支持自动刷新，默认每30秒更新一次
5. **图表库**: 使用Chart.js 4.4.0版本，通过CDN加载
