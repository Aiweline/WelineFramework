# SEO模块队列化架构说明

## 架构改进

SEO 将“任务登记”与“搜索平台/Feed 实际处理”分开。登记仍是数据库写入，
是否影响生产者由事件的 failure 策略决定；不能概括为“所有 SEO 入队都与生产者成败无关”。

## 核心改进

### 1. 性能优化

**之前的问题**：
- Store保存时直接触发SEO处理
- 包含Feed收集、关键词提取、数据库写入等耗时操作
- 阻塞主流程，影响用户体验

**现在的方案**：
- Store保存时仅将任务入队（轻量级操作）
- 实际处理由Cron任务异步执行
- Store Observer 当前捕获入队异常；Website ResourceChange 则是同步 critical 登记，失败必须回滚站点保存

### 2. 任务队列表

**表名**: `weline_seo_task`

**核心字段**：
- `task_type`: 任务类型（feed_generate, push_urls, keyword_extract）
- `subject_type`: 主体类型（store, website等）
- `subject_id`: 主体ID
- `payload`: 任务数据（JSON格式）
- `status`: 任务状态（pending, processing, done, error, cancelled）
- `priority`: 优先级（1低，5普通，10高）
- `attempts`: 尝试次数
- `max_attempts`: 最大尝试次数
- `scheduled_at`: 计划执行时间

**特性**：
- 支持任务优先级
- 自动重试机制（失败后延迟重试）
- 任务状态跟踪
- 错误信息记录

### 3. 生产者 Observer

**文件**: `Observer/StoreSaveAfter.php`

**改进**：
- 不再直接处理SEO逻辑
- 仅将任务信息写入队列表
- 检查重复任务，避免重复入队
- 实际 Feed 处理由 Cron 执行

**Website 资源线文件**: `Observer/ResourceChanged.php`

- 订阅 `Weline_Framework::resource_changed` v1，仅处理 `resource_type=website`。
- Observer 为 `delivery="sync" failure="critical"`；在 Website 主库事务内登记任务。
- 当前 URL 与 previous URL 都固定绑定 `ResourceChange.website_id`，`0` 是合法默认站。
- 只调用 `UrlSubmitService::enqueueTargets()`；不调用 sitemap 同步服务，不做外部网络推送。
- 任务登记返回 errors 时抛出，不把失败降级为 warning。

### 4. 任务处理器

**文件**: `Service/TaskProcessor.php`

**功能**：
- 统一处理各种SEO任务
- Feed生成处理
- URL推送处理
- 关键词提取处理
- 错误处理和重试

### 5. Cron任务

#### FeedGenerator（Feed生成任务）

**执行频率**: 每10分钟
**功能**: 
- 消费 `feed_generate` 类型的任务
- 批量处理（每次100个）
- 生成Feed并更新SEO主体和关键词

#### UrlPusher（URL推送任务）

**执行频率**: 每5分钟
**功能**:
- 消费已登记的 `push_urls` 任务
- 每次最多取 50 个任务
- 支持多平台推送

## 数据流

```
Store 保存 --StoreSaveAfter--> feed_generate DB 任务
Website ResourceChange --sync/critical--> enqueueTargets --> push_urls DB 任务
URL 变更/重写补偿 -------------------------------> push_urls DB 任务
                                                    |
                    +-------------------------------+----------------+
                    |                                                |
            FeedGenerator（每10分钟）                       UrlPusher（每5分钟）
                    |                                                |
              TaskProcessor                                    TaskProcessor
                    |                                                |
            SeoSubject/Keyword                                  SearchEngine
```

## 任务类型

### 1. feed_generate（Feed生成）

**触发时机**: Store 保存后
**处理内容**:
- 收集Feed数据
- 创建/更新SEO主体
- 提取关键词
- 保存关键词

### 2. push_urls（URL推送）

**触发时机**: Website ResourceChange、普通 URL 变更或 URL rewrite 补偿扫描登记后
**处理内容**:
- 收集需要推送的URL
- 按平台分组
- 批量推送到搜索引擎

### 3. keyword_extract（关键词提取）

**触发时机**: 手动触发或特定场景
**处理内容**:
- 从文本中提取关键词
- 保存关键词到数据库

## 性能优势

1. **副作用分层**: 生产者只登记 DB 任务，搜索平台请求由 Cron 执行
2. **批量处理**: Cron任务批量处理，提升效率
3. **异步执行**: SEO处理在后台异步执行
4. **可扩展**: 支持任务优先级和重试机制
5. **可监控**: 任务状态可追踪，便于监控和调试

## 配置建议

### Feed生成频率

- **当前**: `FeedGenerator::cron_time()` 为每10分钟
- 如要调整，必须修改 Cron 定义、评估任务积压与锁超时，并同步本文档

### URL推送频率

- **当前**: `UrlPusher::cron_time()` 为每5分钟
- 如要调整，必须修改 Cron 定义并同步本文档，不要依赖“每天2点”的历史口径

### 批量大小

- **Feed生成**: 每次100个任务
- **URL推送**: 每次最多 50 个 `push_urls` 任务；单任务内 URL 分块由入队服务决定

## 监控和维护

### 查看待处理任务

```sql
SELECT * FROM weline_seo_task 
WHERE status = 'pending' 
ORDER BY priority DESC, created_at ASC;
```

### 查看失败任务

```sql
SELECT * FROM weline_seo_task 
WHERE status = 'error' 
ORDER BY updated_at DESC;
```

### 手动重试失败任务

当前模块没有发布专用的后台或 CLI 重试入口。未达 `max_attempts` 的失败任务会自动回到
`pending` 并按 `attempts * 5 分钟` 延迟；达到上限后进入 `error`。如要提供人工重试，
应先实现带 ACL、状态检查和审计的正式入口，不要把直接 SQL 更新当作已发布能力。

## 注意事项

1. **任务去重**: Observer会检查是否已存在相同任务，避免重复入队
2. **重试机制**: 任务失败后会自动重试，最多尝试3次
3. **延迟重试**: 失败后延迟重试（尝试次数 * 5分钟）
4. **超时处理**: Cron任务有超时限制，防止长时间阻塞

## 后续优化建议

1. **任务优先级**: 可根据业务需求调整任务优先级
2. **批量优化**: 可根据服务器性能调整批量大小
3. **监控告警**: 可添加任务积压告警机制
4. **性能统计**: 可添加任务处理性能统计
