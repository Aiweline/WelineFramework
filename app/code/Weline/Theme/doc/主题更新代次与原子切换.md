# 主题更新代次（Theme Update Batch）与原子切换

> 目标：`theme:upgrade` 不再需要维护模式。构建阶段写入**新代次目录**（静态资源 + 模板产物），
> 全部就绪后**只改一个指针**，切换立即生效；旧代次整目录保留，可秒级回滚。
>
> 本文只描述「主题更新代次」，与「主题发布版本（Theme Version / 发布）」是两条独立的轴。

## 1. 两条轴，不要混

| 轴 | 语义 | 产物 | 谁改 |
|---|---|---|---|
| **发布版本（Theme Version, V/R）** | 设计/编辑侧对主题内容的版本 | 布局实体源码、页面配置 | 主题编辑器 / 发布动作 |
| **更新代次（Theme Update Batch, TU）** | 运行时「当前生效的一套静态资源 + 已编译模板」 | `pub/static/<batch>/…` + `generated/theme-layout-entities/<batch>/…` + 编译产物 | `theme:upgrade` |

一条 更新代次可以覆盖**多个**发布版本（例如一次升级里同时重建 formal 与 draft 的产物），
但任一时刻每个 `(website, theme, area)` 只有 **一个当前代次**。

## 2. 现状（为什么现在需要维护模式）

`php bin/w theme:upgrade` 当前顺序（`Theme/Console/Theme/Upgrade.php:90-140`）：

1. `StaticAssetMode::publishForThemeUpgrade()` —— 把主题静态资源直接发布到**当前** `/static/<build>/` 下；
2. `ThemeLayoutEntityUpgradeSolidifyService::cutoverFromThemeCommand()` —— **purge 旧实体**，再原地重固；
3. 按布局清 FPC/CDN。

第 1、2 步都会改动**正在被请求使用**的字节，中途窗口里页面可能 404/半成品，所以只能开维护模式把它遮住。

已有但没被用起来的两个钩子：

- `Framework/Deploy/StaticBuildId`：静态前缀 `/static/<build_id>`，读 `pub/static/.build.json`，10s 进程内缓存
  —— **指针语义现成**；
- `ThemeLayoutEntityPaths::rootOverride` 与 `DeployStagingSession::themeLayoutEntitiesRoot()`
  —— **模板产物根可替换**，天然支持「写到别处」。

## 3. 目标形态

```
pub/static/
  .build.json                     # 部署构建号（框架级，不动）
  tu-20261022-015300-ab12cd/      # ← 主题更新代次 A（当前）
  tu-20261022-021500-7f31ae/      # ← 代次 B（已构建未切换 / 或回滚目标）
generated/theme-layout-entities/
  tu-20261022-015300-ab12cd/...
  tu-20261022-021500-7f31ae/...
var/theme-updates/
  tu-20261022-021500-7f31ae/batch.json      # 清单 + 校验结果
```

**渲染期**：`(website, theme, area)` → 指针 → `batch_id` →
① 静态前缀 `/static/<batch_id>/`；② 模板产物根 `<entity_root>/<batch_id>/…`；③ FPC key 含 `batch_id`。

**切换**：改一行指针（+ 单调递增 `epoch`），不需要 purge，也不需要维护模式。

## 4. 数据模型

```sql
-- 代次登记
CREATE TABLE theme_update_batch (
  id            INT PRIMARY KEY AUTO_INCREMENT,
  batch_id      VARCHAR(64) NOT NULL UNIQUE,   -- tu-YYYYMMDD-HHMMSS-rand
  website_id    INT NOT NULL DEFAULT 0,
  theme_id      INT NOT NULL,
  area          VARCHAR(16) NOT NULL DEFAULT 'frontend',
  static_ns     VARCHAR(128) NOT NULL,         -- 相对 pub/static 的命名空间（= batch_id）
  entity_root   VARCHAR(255) NOT NULL,         -- 相对 generated/theme-layout-entities 的根
  status        VARCHAR(16) NOT NULL,          -- building|verified|current|superseded|failed
  manifest_json LONGTEXT NOT NULL,             -- 见 §6 校验清单
  created_at    DATETIME NOT NULL,
  verified_at   DATETIME NULL,
  promoted_at   DATETIME NULL,
  KEY idx_theme_area (theme_id, area, status)
);

-- 指针（每 website+theme+area 一行）
CREATE TABLE theme_update_pointer (
  website_id  INT NOT NULL,
  theme_id    INT NOT NULL,
  area        VARCHAR(16) NOT NULL DEFAULT 'frontend',
  current_batch_id  VARCHAR(64) NOT NULL,
  previous_batch_id VARCHAR(64) NULL,
  epoch       BIGINT NOT NULL,                 -- 单调递增；切换即 +1
  updated_at  DATETIME NOT NULL,
  PRIMARY KEY (website_id, theme_id, area)
);
```

**运行期缓存键**（写入 `Env` 的 runtime config，随现有配置广播下发；Worker 侧 ≤10s 生效，
与 `StaticBuildId::CACHE_TTL_SECONDS` 对齐）：

```php
'theme_update_current' => [
  '{website_id}|{theme_id}|{area}' => [
      'batch_id' => 'tu-20261022-015300-ab12cd',
      'static_ns' => 'tu-20261022-015300-ab12cd',
      'entity_root' => 'tu-20261022-015300-ab12cd',
      'epoch' => 42,
  ],
],
'theme_update_epoch' => 42,
```

## 5. 命令行（`theme:upgrade` 语义调整）

| 命令 | 行为 |
|---|---|
| `theme:upgrade -t hanfu` | **默认** = 构建新代次 → 校验 → 切指针（不再 purge，不再维护模式） |
| `theme:upgrade -t hanfu --build-only` | 只构建，产出 `batch_id` 与校验报告，不动指针 |
| `theme:upgrade --promote <batch_id>` | 把手动/流水线构建好的代次切为当前 |
| `theme:upgrade --rollback -t hanfu` | 指针回退到 `previous_batch_id` |
| `theme:upgrade --list -t hanfu` | 列代次、状态、创建时间、是否当前 |
| `theme:upgrade --keep 3` | GC：保留当前 + 最近 N 个，删除更早代次目录 |
| `theme:upgrade --maintenance` | **仅应急**：强制走旧的就地流程（如磁盘不足、需原地迁移 DB schema） |

`-l/--layout`、`-o/--option`、`-s/--scope`、`-a/--all` 保持现有含义，只作用于「本次构建写入哪个代次、覆盖哪些布局」。

## 6. 构建与校验（构建期不改任何线上字节）

1. 生成 `batch_id`；建 `pub/static/<batch>/` 与 `generated/theme-layout-entities/<batch>/`；
2. 静态资源发布进 `<batch>/`（复用 `StaticAssetMode`，把目标根从「当前 build 目录」改为「代次目录」）；
3. 布局实体固化进 `<batch>/`（`ThemeLayoutEntityPaths` 以 `rootOverride=<batch 根>` 构造，或 `DeployStagingSession` 等价机制），
   纯 PHTML + 语言编译产物都落在代次根内；
4. 写 `var/theme-updates/<batch>/batch.json`：

```json
{
  "batch_id": "tu-20261022-015300-ab12cd",
  "themes": [3], "areas": ["frontend"],
  "layouts": {"total": 37, "by_type": {"homepage": 3, "category": 4, "...": 0}},
  "entity_files": 128,
  "static_files": 2411,
  "static_manifest_digest": "sha256:...",
  "entity_manifest_digest": "sha256:...",
  "verify": {
    "ok": true,
    "checks": [
      {"name": "entity_count_match", "ok": true},
      {"name": "static_refs_resolvable", "ok": true, "sampled": 40},
      {"name": "no_uncompiled_taglib", "ok": true},
      {"name": "no_placeholder_leak", "ok": true},
      {"name": "render_smoke", "ok": true, "pages": ["/", "/products", "/category/women/mamian"]}
    ]
  }
}
```

**校验红线**（任一失败 → 代次 `failed`，指针不动）：
- 期望布局数 == 产物数（按 `-l/-o` 过滤后的期望集合）；
- 采样静态引用（head CSS/JS + widget-assets）在 `<batch>/` 下全部存在；
- 产物内无未编译 `{{ }}` / `@lang(` / `<w:` 残留；
- 采样页面在**代次沙箱**里渲染 200（可用 preview 通道：`/~preview/…` 指到该代次）。

## 7. 切换（原子、O(1)）

```php
DB::transaction(function () use ($batch) {
    // 1) 指针行：current=新, previous=旧, epoch=epoch+1
    // 2) theme_update_batch: 新→current，旧→superseded
    // 3) Env 写 theme_update_current[key] + theme_update_epoch（触发 Worker 配置刷新）
});
```

- 不 purge FPC：FPC key 已含 `batch_id`（或 `epoch`），旧条目自然过期（`freshTtl` 内仍可命中旧 body，
  但旧 body 引用的 `/static/<旧 batch>/` 仍在磁盘上，不会 404）；
- 旧代次至少保留一个（`previous_batch_id`）以支持回滚；
- 回滚 = 再切一次指针（`epoch+1`），无需重建。

## 8. 渲染期接入点（按现有代码）

| 环节 | 现有位置 | 需要改成 |
|---|---|---|
| 静态 URL 前缀 | `Framework/Deploy/StaticBuildId::current()` + `StaticBuildPublisher` | 主题资源走 `batch.static_ns`；非主题资源（Framework/前端基础 JS）继续用部署 build id |
| 主题资源 `?v=` | `Framework/View/TraitTemplate::themeStaticVersion()`（`theme_static_versions[scope\|theme\|version]`） | 优先读 `theme_update_current` 的 `batch_id`；保留旧 map 作兼容 |
| 布局产物根 | `ThemeLayoutEntityPaths::root()` | `root()` 前插入代次层：`<root>/<batch>/…`；`rootOverride` 已支持 |
| 当前版本解析 | `SolidifiedControllerTemplateResolver::resolveRequestIdentity()` | 不变（仍按发布版本 V/R 解析），只是根目录换成代次根 |
| FPC key | 现有布局/语言/货币维度 | 追加 `theme_update_epoch`（或 `batch_id`） |
| Worker 感知 | `Env` runtime config 广播 + 10s 缓存 | 复用，无需新机制 |

## 9. 维护模式还需要吗

- **不需要**：构建期不碰线上字节；切换是单事务指针 + epoch 变更。
- 保留 `--maintenance` 作为**应急**开关，用于：
  - 需要原地迁移 DB schema / 实体目录结构（一次性）；
  - 磁盘不足，必须复用旧目录时。
- `maintenance:status` 里的「系统升级锁」应只与 `setup:upgrade`（DB schema）绑定，不再由主题更新占用。

## 10. 落地步骤（建议原子任务）

1. **T1 数据层**：`theme_update_batch` / `theme_update_pointer` 建表 + Model；`ThemeUpdateBatchService`
   （create/verify/promote/rollback/list/gc）；单测覆盖指针事务与 epoch 单调。
2. **T2 静态进代次**：`StaticAssetMode` 增加「目标代次命名空间」参数；产出 `<batch>/`；
   `ThemeUpdateStaticResolver` 给主题资源产出 `/static/<batch>/…`。
3. **T3 模板进代次**：`ThemeLayoutEntityPaths::root()` 支持代次层；固化写入 `<batch>/`；
   渲染期按指针取根；`TraitTemplate::themeStaticVersion()` 优先代次。
4. **T4 校验器**：§6 四条红线 + `batch.json`；失败即 `failed`。
5. **T5 CLI 改造**：`theme:upgrade` 默认 = build→verify→promote；新增 `--build-only/--promote/--rollback/--list/--keep`；
   去掉默认的 purge 与维护模式。
6. **T6 FPC/缓存**：FPC key 加 `epoch`；`ThemeRuntimeCacheCleaner` 在 promote 后只清「指针相关」的极小集合。
7. **T7 回滚演练与 GC**：连续升级 3 次 → 回滚 1 次 → `--keep 2` 清旧代次；确认旧 `/static/<old>/` 仍可访问至 GC。

## 11. 验收（机器可判定）

```bash
# 1) 构建不改线上
before=$(curl -s http://host/ | sha256sum)
php bin/w theme:upgrade -t hanfu --build-only | tee /tmp/b.json   # 打印 batch_id
after=$(curl -s http://host/ | sha256sum); [ "$before" = "$after" ]   # 必须相等
grep -q '"ok": true' var/theme-updates/<batch>/batch.json

# 2) 切换瞬时生效且零 5xx（切换窗口内 200 次请求）
php bin/w theme:upgrade --promote <batch>
seq 200 | xargs -P8 -I{} curl -s -o /dev/null -w '%{http_code}\n' http://host/ | sort | uniq -c   # 只允许 200

# 3) 回滚
php bin/w theme:upgrade --rollback -t hanfu
curl -s http://host/ | grep -q '<旧代次的静态前缀>'   # 指针已回退

# 4) 维护模式全程未开启
php bin/w maintenance:status | grep -q 'Maintenance mode: Close'
```

## 12. 风险与取舍

- **磁盘**：代次目录并存，需 `--keep` 与容量告警；一次 hanfu 全量约 `pub/static` 主题部分 + 128 个实体文件（量级可接受）。
- **多站点共享**：同一主题被多站点绑定时，同一批代次目录可复用，但指针按 `website_id` 分开。
- **与部署构建号（`.build.json`）的关系**：部署构建号仍管「框架/模块静态」，主题代次只管「主题 + 实体产物」，
  两者互不覆盖；URL 形如 `/static/<batch>/Weline/hanfu/...` 与 `/static/<build>/Weline/Framework/...` 并存。
- **一致性窗口**：`epoch` 变更到 Worker 全部刷新（≤10s）之间，新旧代次同时被访问 —— 因为两个目录都在，
  页面与资源始终自洽；FPC 也因 key 含 epoch 不会混用。
- **首次落地**：为兼容现有站点，首次执行时把「当前 `/static/<build>/` + 现有实体根」登记为
  `batch_id=legacy-<build>`，指针指向它，之后再升级走代次流程。

## 14. T5 进展与已知缺口（2026-10-22 续）

### 已接入
- `StaticBuildId::versionedPath($path)`：**按路径**判定主题自有资源（`/Weline/<theme_prefix>/`、`/Weline/Theme/`）
  → 用当前代次前缀；其余（Framework/模块静态）仍用部署构建号。`theme_prefix` 由构建期从主题 `path`
  写入 `batch.json` → 指针值。
- `ThemeUpdateRuntime`：读指针文件 `var/theme-update/current.json`（≤10s TTL），提供
  `staticPrefixForPath()` / `entityRoot()` / `cacheGeneration()`；无主题上下文时若该区域仅一个代次则直接采用。
- 缓存代次：`KeyBuilder` / `StorefrontCacheKeyContext` 的 `static_generation` 改为 `cacheGeneration()`
  （代次生效时用批次ID）。
- 实体根：`ThemeLayoutEntityPaths::root()` 在无强制根时优先当前代次的 `entity_root`。
- 切换后失效：`promote()`/`rollback()` 末尾调用
  `ThemeRuntimeCacheCleaner::clearAllThemeRelatedCaches($themeId, 'theme_update_promote|rollback')`。

### 实测
- 构建：`tu-…73b908` 4/4 校验通过；批目录 `pub/static/<batch>`（38k+ 硬链接）与
  `generated/theme-layout-entities/<batch>`（712 文件）就位。
- 指针：promote/rollback 均单事务 CAS，epoch 单调（已到 10），指针文件 208B。
- 站点：首页 200、pageErr 0、主题扫描 hits=0、单测 16/16。
- 线上实体根未被批构建写入（theme 3 目录 mtime 仍为 16:02，批构建在 18:00 之后）→ `forceRoot()` 隔离开关有效。

### 已知缺口（下一步）
1. **实体 HTML 里烘焙的静态前缀不会随代次变化**：`solidify` 在「digest 未变」时会跳过写入，
   批内实体多为线上快照，其中 `/static/<旧代次|部署构建号>/` 已写死。因此页面会出现「批次前缀 + 部署前缀」混用，
   并残留 1 个 404。修法二选一：
   - 构建期对批内实体做**前缀重写**（`/static/<old>/(Weline/(<theme_prefix>|Theme)/…)` → `/static/<batch>/…`）；
   - 或给固化流水线加 `force` 选项（清输入 digest）后用 `StaticBuildId::override($batch)` 重烘。
2. **FPC 以进程内为主**：`x-weline-fpc: HIT` 时不执行渲染期逻辑；需确认 `static_generation` 是否进入该层缓存键，
   否则切指针后必须依赖 §14 的定向失效。
3. `theme:upgrade` 仍是就地 purge+固化；待 1、2 收口后改为 build→verify→promote。

## 15. 收口（2026-10-22，已可用）

### `theme:upgrade` 默认就是「最后翻指针」
```bash
php bin/w theme:upgrade -t hanfu            # 默认：构代次 → 校验 → 翻指针（不 purge、不开维护）
php bin/w theme:upgrade -t hanfu -l homepage
php bin/w theme:upgrade -t hanfu --inplace  # 兼容旧行为（就地 purge+固化，需维护模式）
php bin/w theme:update rollback -t hanfu    # 秒级回滚
php bin/w theme:update status -t hanfu      # 当前/回滚目标/epoch/代次列表
php bin/w theme:update gc -t hanfu --keep 2 # 回收历史代次（保护 current/previous）
```

### 最终形态
| 环节 | 位置 |
|---|---|
| 批次静态 | `pub/static/<batch>/`：主题子树（`Weline/<theme_prefix>`、`Weline/Theme`）真实硬链接；其余顶层目录符号链接到部署构建树（保证任意 URL 可解析、零额外空间） |
| 批次模板 | `generated/theme-layout-entities/<batch>/`：固化产物 + 线上快照；构建期 `ThemeLayoutEntityPaths::forceRoot()` 隔离，`ThemeUpdateRuntime::forceBatch()` 让**编译产物烘焙本批次前缀** |
| 指针 | `theme_update_pointer`（CAS by epoch）+ `var/theme-update/current.json`（≤10s TTL，Worker 无需重载） |
| 渲染 | `StaticBuildId::versionedPath()` 按路径选前缀（主题资源→批次，其余→部署构建号）；实体根优先代次根 |
| 缓存 | `static_generation` 用代次；翻指针后自动做「主题相关缓存 + 店面 FPC 按布局」定向失效 |
| 回滚 | 指针换回 previous（epoch+1），旧目录仍在 |

## 16. 发布流程接入（2026-10-22）

编辑器「发布」成功后不再需要人工跑升级：

1. **发布打脏标记**（两条发布路径都已接入）：
   - `ThemeLayoutVersionService::publishVersion()`（旧版布局发布）
   - `LayoutWorkspace::publishTargetVariant()`（Scoped 目标变体发布）
   → 成功后调用 `ThemeUpdateRuntime::markDirty($themeId, 'publish')`，写
   `var/theme-update/dirty/<themeId>.json`。
2. **消费脏标记**：
   ```bash
   php bin/w theme:update auto -t hanfu            # 有发布变更才重建+切指针；无变更跳过
   php bin/w theme:update auto -t hanfu --dry-run  # 只看决策
   php bin/w theme:update auto -t hanfu --force    # 忽略脏标记强制重建
   ```
   行为：构建新代次 → 校验 → 翻指针 → 清除脏标记。构建失败则保留脏标记，不会切换。
3. **建议调度**：把 `theme:update auto` 挂到发布后的异步任务/定时任务（每次约 40s，不阻塞编辑器请求）；
   编辑器侧若追求"发布即生效"，也可在发布响应返回后立刻触发一次。

实测：
```
无脏标记 → 主题 #3 无发布变更（无脏标记），跳过。
打脏标记 → dry-run：将重建并切换主题 #3 的更新代次（dirty=1 force=0）
执行     → 已切到代次 tu-…b1f2c3（epoch=38），脏标记清除
再跑      → 无发布变更，跳过
```

## 17. 与「开发环境自动固化编译」合并（2026-10-22）

现有实现：`Theme/Cron/LayoutOriginWatch`（cron `* * * * *`，仅 `system.deploy=dev`）
→ `ThemeLayoutOriginWatchService::run()`：按源文件 hash 变更**就地**固化/编译/chrome heal/按布局清 FPC。

合并方式（不重复造轮子）：

| 模式 | 触发 | 行为 |
|---|---|---|
| **dev**（`system.deploy=dev`） | `theme_layout_origin_watch` cron（每分钟）/ `theme:update auto` 手动 | **同一实现**：`ThemeUpdateAutoService` 直接委托 `ThemeLayoutOriginWatchService::run()`，就地刷新（文件即产物，无代次、无指针） |
| **非 dev**（prod 等） | 发布写脏标记 → `theme_update_auto_publish` cron（每分钟）/ `theme:update auto` 手动 | 构建新代次 → 校验 → 翻指针 → 清标记；无标记 1 次 stat 快速跳过 |

配套改动：
- `ThemeUpdateRuntime::markDirty()` 在 dev 模式**不写脏标记**（dev 由就地固化负责，避免无谓代次）；
- 新增 `ThemeUpdateAutoService`（CLI 与 cron 共用同一入口，避免两套逻辑）；
- 新增 cron `Weline_Theme::theme_update_auto_publish`（非 dev，`cron:task:collect` 已注册）。

实测：
```
dev（进程内切 deploy=dev）→ auto 返回 mode=dev（委托 origin watch）
非 dev 有脏标记        → probe cron 类执行：themes=1 promoted=1 failed=0，脏标记清除，epoch 43→45
非 dev 无脏标记        → skip:no_dirty
```

## 18. 按受影响布局增量固化（2026-10-22）

发布时记录「改了哪些布局」，`auto` 只固化这些布局：

1. 脏标记结构升级：
   ```json
   {"at":"…","reason":"scoped_target_publish","layouts":[{"type":"homepage","option":""}],"all":false}
   ```
   - `ThemeLayoutVersionService::publishVersion()` → 记 `pageType`
   - `LayoutWorkspace::publishTargetVariant()` → 记 `pageType + layoutOption`
   - 多个发布合并去重；条目 > 12 个自动置 `all=true`（转全量）
2. `ThemeUpdateAutoService`：`all=false` 时把 `layouts` 作为 `layout_targets` 传给构建；
3. `ThemeUpdateBuildService`：按 `layout_targets` 逐个 `layout_type/layout_option` 固化（`normalizeLayoutTargets()`），
   并写入 `batch.json` 的 `layout_targets` 便于审计。

实测：
```
dirty(layouts=[homepage]) → theme:update auto -t hanfu
  → 已切到代次 tu-…8d618f（epoch=46），耗时 real 23.1s
  → batch.json layout_targets=[{"type":"homepage","option":""}]  ✓
对照：无内容变更时全量 build 亦为 real 23.0s（固化按 digest 跳过，属预期）
     —— 真正差异出现在有内容变更时：只需重烘受影响布局，而非全部布局。
```

## 19. 正确性与运维收尾（2026-10-22）

### T1 预览态不被代次接管
- `StaticBuildId::versionedPath()`：含 `__preview` 的路径**原样返回**，预览静态命名空间不再被构建号/代次前缀改写；
- `ThemeUpdateRuntime`：实体根在预览请求（URI 含 `/~preview/` 或带 `preview_token`）时**不接管**；
- 结论（实测 fresh preview token）：预览页 head CSS/JS、widget-assets 均为
  `/static/__preview/token_…/Weline/hanfu/Weline/Theme/…`；`preview_pv_` 标记在位。
  残留 body 里的批次前缀图片/少量部件资源来自烘焙缓存，`favicon-96.png` 404 为既有形状（本轮前同样存在）。

### T2 promote 后自动 GC
`ThemeUpdateBatchService::promote()` 末尾自动 `gc(keep)`，保留数
`Env.theme_update_keep_batches`（默认 3，不含 current/previous）。
实测：14 个代次 → 一次 promote 后 **5 个**（3 + current + previous）。

### T3 auto 失败退避
构建校验失败时写 `var/theme-update/backoff/<themeId>.json`（默认 5 分钟），
期间 `auto` 直接跳过并保留脏标记；成功 promote 后清除退避。
实测：模拟退避 + 脏标记 → `主题 #3 上次构建失败，退避中（重试时间 …），本次跳过。`，脏标记保留；
清除退避后再次 `auto` 正常切换到新代次（epoch 51）。
