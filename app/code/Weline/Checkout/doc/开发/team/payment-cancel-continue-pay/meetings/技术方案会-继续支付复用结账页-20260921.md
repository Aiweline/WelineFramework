## 2. 需求纠偏：旧 UC1 与用户新意图冲突

### 用户反馈（硬）

- 截图：结账页同时出现「购物车为空」+ 孤立「订单已创建 / Retry payment」双卡，体验不对劲。
- 「继续支付」应进入**完整结账页**（可改地址等信息），不要另造孤立恢复页。
- 实现思路（产品意图）：照用结账页；把该订单对应的 checkout session **临时塞进当前会话**；可改地址；支付完成后**清掉临时 session**，恢复用户原 session。

### 旧规格冲突点（`payment-cancel-continue-pay.md`）

| 旧条文 | 冲突说明 |
|--------|----------|
| P0：主 CTA 接回 `#payment-recovery` / `resumePaymentV2` | 入口可仍落 `/checkout`，但把「recovery 区」当成主 UI 会固化孤立双卡；与「完整结账页」冲突。 |
| UC1 步骤 4：「结账页展示 recovery，可触发 `resumePaymentV2`」 | 将 recovery 区块升为主路径，弱化地址/配送/摘要等完整结账表单。 |
| UC1 步骤 5：**「断言：购物车可空，但 recovery 区可见，非结账空态表单」** | **直接冲突**。旧断言显式允许空车 + recovery 可见；用户判定该组合为错误（空车横幅 + 孤立续付卡）。 |
| 非目标：「不延迟建单后清车；订单已存在；用 recovery 续付」 | 「用 recovery 续付」被理解成 UI 级 recovery 岛，而非「session 临时挂载后的完整结账」。清车策略本身可保留，但前台不得再靠空车态 + recovery 岛交差。 |
| 契约摘要：Continue pay URL = `/checkout#payment-recovery?…` | Hash 触发 recovery UI 与「完整结账 + 临时 session」目标冲突；URL 形态待产品确认（见 §6）。 |

### 纠偏结论（草案）

1. **作废**旧 UC1「可空车 + recovery 区可见」作为成功断言。
2. 继续支付成功态 = **完整结账页可用**（至少：收货/地址可展示可改、摘要/行项目有来源、可发起续付），**不得**以空车横幅为主视觉。
3. 支付动作仍走 **`resumePaymentV2`（复用已有 `order_uuid`）**，禁止再 `submitV2` 建单；UI 不得为此另开平行页。
4. Session：**临时挂载订单侧 `CheckoutSession`（`quote_token`）→ 付完（或显式退出续付）卸载并恢复用户原活跃 session**。

## 3. EARS 修订草案（When / shall）

> 下列替换/增补权威 spec 中与「落地形态」相关的 EARS；未点名的 P0′ 历史保留、后台合并、Express abandon 禁止假闭环等条文**默认保留**。

### 修订 / 新增

- When 买家从取消页或账户侧点击「继续支付」且目标订单仍未付，系统 shall 打开**同一套**店面 `/checkout` 完整结账体验，并将该订单对应的 `CheckoutSession`（由 `quote_token` 标识）**临时设为当前活跃结账会话**；shall **not** 导航至独立恢复页或仅展示孤立 recovery 双卡。
- When 临时活跃会话已挂载且订单未付，系统 shall 允许买家在结账页查看并修改地址等信息（修改后的生效范围见 §6 产品确认），且续付提交 shall 走 `resumePaymentV2` 绑定既有 `order_uuid`，shall **not** 调用 `submitV2` 新建订单。
- When 续付链路中购物车实体已空（建单后清车），系统 shall **not** 以「购物车为空，无法结账」类空态作为主路径主视觉；shall 基于临时 `CheckoutSession` / 订单上下文渲染完整结账所需内容（行项目来源策略见 §6）。
- When 该笔订单支付成功（或续付流程被明确结束且产品确认需回退），系统 shall 清除临时挂载的 checkout session 绑定，并恢复买家进入续付前的原活跃 session（若无原 session 则回落到站内默认结账/购物车策略，不得残留孤儿临时绑定）。
- When 「继续支付」能力不可达（无有效 `quote_token` / session 非 `submitted` / 订单已付或已取消等），系统 shall 降级为明确非续付引导（如返回购物车/订单详情），shall **not** 裸链空 `/checkout` 制造双卡幻觉。
- When 店面结账页渲染 type 切换器，系统 shall 仅展示 **CheckoutTypeProviderRegistry** 中 `isAvailable` 的类型；shall **not** 在 Checkout 核心写死业务 type 列表。支付域 Provider shall 提供标准结账与继续支付；批发等能力 shall 由对应业务模块自行注册 Provider。虚拟产品、下载类等 type shall 允许后续模块以同一抽象注册并裁剪结账步骤（如无运输地址）；**本需求迭代不实现这些 Provider**。

### 建议废止或改写的旧 EARS 语义

- 旧：主 CTA「指向可恢复支付链（含 `#payment-recovery`）」——改为「指向完整结账 + 临时 session 挂载契约」；`#payment-recovery` 不再作为成功体验的必需 UI 形态（实现期可内部兼容，验收以完整结账为准）。
- 旧 UC1「购物车可空但 recovery 可见」——废止。

## 4. 可执行主路径 UC 草案

### UC-CP-1 取消后继续支付 → 完整结账（主成功）

| 字段 | 内容 |
|------|------|
| 角色 | 店面买家（登录或游客，与建单身份一致） |
| 前置 | 已 `submitV2` 建单并跳转网关；订单未付；存在可解析的 `quote_token` + `order_uuid`；对应 `CheckoutSession.state = submitted` |

**步骤**

1. 买家在网关取消，回跳取消确认页（既有 success/cancel 落地）。
2. 点击主 CTA「继续支付」。
3. **证据点 · 入口**：落地 URL 为店面 `/checkout`（允许携带绑定参数；**不得**进入非结账平行页）；可解析 `quote_token` 与 `order_uuid`。
4. 系统将订单侧 `CheckoutSession` **临时挂载**为当前活跃结账会话（浏览器会话层可见：后续结账 Query 使用该 `quote_token`）。
5. **证据点 · 完整结账**：页面呈现完整结账主结构（地址区可交互，非仅 recovery 岛）；**不得**同时以空车横幅作为主路径主文案。
6. **证据点 · 地址可改**：买家修改收货地址（或等价地址字段）并保存/应用成功（UI 可见更新）；临时 session / 订单上下文反映变更意图（持久化边界见 §6-Q1）。
7. 买家确认支付方式并继续支付 → 调用 `resumePaymentV2`（请求含既有 `order_uuid` / `quote_token` / idempotency 契约）。
8. 网关完成支付（或测试替身成功）。
9. **证据点 · 付完 session 恢复**：临时挂载解除；买家原活跃 checkout session（进入续付前）恢复；临时 `quote_token` 不再作为默认活跃会话。
10. 订单侧可观察为已付（或进入既有成功页契约）；**不得**再 `submitV2` 产生第二张业务订单。

**期望结果**：完整结账可改址续付；无「空车 + 孤立双卡」；付完 session 回滚。

**备选 / 异常**

- A1：临时挂载失败 → 明确错误/降级 CTA，不展示空车+双卡。
- A2：订单已付/已取消 → 不进入续付挂载。

### UC-CP-2 账户「继续支付」同构挂载

| 字段 | 内容 |
|------|------|
| 角色 | 登录顾客 |
| 前置 | 账户订单组 `pending`；CTA 可达 |

**步骤**

1. 打开账户订单列表，点击「继续支付」。
2. **证据点**：同 UC-CP-1 步骤 3–5（`quote_token` / `order_uuid` / 完整结账 / 非空车主视觉）。
3. 可选：改址后 `resumePaymentV2`（同主路径）。
4. 付完后 **证据点 · session 恢复**（同 UC-CP-1 步骤 9）。

### UC-CP-3（保留）续付新建尝试且历史不丢

- 行为同旧 UC2：第二次 `resumePaymentV2` 后 `weline_payment_transaction` ≥2 行；后台合并可见。  
- **不因本纠偏删除**。

### UC-CP-4（保留）Express abandon 无假闭环

- 同旧 UC4。

## 5. 非目标

- 不新开平行「支付恢复页 / 迷你结账壳 / 仅 Retry 双卡页」。
- 不把本纠偏扩展为 PaymentFacadeV2 Intent 编排 cutover。
- 不撤销「建单后清车」的库存/车侧策略本身（只纠前台续付体验与 session 挂载）。
- 不在账户列表做完整支付时间线（仍仅 CTA）。
- 不在本澄清阶段改业务码或冻结类名级补丁步骤（how 交架构席）。
- 不要求游客/登录身份在续付中途随意切换（身份一致性保持既有结账门禁）。
- 不在 Checkout 核心内嵌批发/其它业务 type 分支（业务 type 一律模块 Provider 注册）。
- **本迭代不做**：虚拟产品结账 type、下载类产品结账 type 及其专属流程（无运费地址等）；架构预留扩展位，实现延后。

## 6. 待产品确认（XOR · 3～5 题）

### Q1. 续付中「可改地址」的持久化边界？

- **A.** 仅更新临时 `CheckoutSession` / 展示层；支付尝试仍按原订单地址快照（改址不回写订单）。
- **B.** 改址写回未付订单配送地址，再 `resumePaymentV2`。
- **C.** 改址触发运费/税重算且写回订单；失败则阻断续付。

### Q2. 建单后购物车已空时，完整结账行项目从哪来？

- **A.** 只读渲染订单/session 快照行项目（车仍空，但不显示空车主态）。
- **B.** 将订单行临时水合回当前购物车（付完再按策略清空）。
- **C.** 车空则禁止改配只允许只读摘要 + 支付（与「完整可改址」可能冲突，若选 C 需同时收窄 EARS）。

### Q3. 「继续支付」URL 契约？

- **A.** 仍用 `/checkout#payment-recovery?quote_token&order_uuid…`，但前端改为挂载完整结账（recovery 岛降级或隐藏）。
- **B.** 改为 `/checkout?continue_pay=1&quote_token=…&order_uuid=…`（或等价 query），废除对外承诺 `#payment-recovery` 主路径。
- **C.** 短链 `/checkout/continue/{order_uuid}` 服务端 302 到 B，对外隐藏 token 细节。

### Q4. 买家当前已有进行中的结账 session（车内另有商品）时？

- **A.** 强制 stash：压栈保存当前 session，挂载订单 session；付完/退出弹栈恢复。
- **B.** 阻断：提示先完成或放弃当前结账，再继续支付。
- **C.** 丢弃当前 draft session，直接挂载订单 session（不恢复）。

### Q5. 续付完整结账上是否允许更换支付方式？

- **A.** 允许改 method，仍 `resumePaymentV2` 新 Attempt。
- **B.** 锁定建单时支付方式，仅允许重试同一 method。
- **C.** 仅钱包/卡内细分可变，method_code 不可变。

## 6c. 汇审纠偏落盘（2026-09-21）

- **继续支付不是 CheckoutType**；是 `payment_mode=continue_pay` 绑定，挂在订单原 Type 的 session 桶上。
- 切换器候选项 = 已有桶；≥2 桶才显示 ▾；单桶无 tab。
- 桶主键 `bucket_id`；同会话最多一个续付桶；`standard`↔`toc`，`tob`↔`tob`。
- 权威 spec 已同步：`doc/开发/spec/payment-cancel-continue-pay.md`。

## 6b. 产品增量（2026-09-21 · 用户口述 · 已采纳进设计）

> 来源①：结账页兼容「继续支付」与标准结账，可切换。  
> 来源②：零售 / 批发一并进统一 type；非当前项收入下拉，仅外露当前命中。  
> 来源③（同日硬约束）：**type 必须抽象可扩展**——其它模块以「加类型」方式注册；Checkout 壳**禁止**写死业务 type 枚举。
> 来源④：结账 type **很多**且可跨模块注册（例：虚拟产品——无运输地址，订单侧已支持，是一整套流程）；Checkout 模块须**抽象支持**此类 type。**本迭代**：先落地支付域 `standard`/`continue_pay` + B2B `tob`；虚拟/下载类 type **先不做**，只留扩展位。

### 硬意图

1. **同一 `/checkout` 壳** + **统一 type 切换器 UI**（当前命中外露 + ▾ 下拉其它）。
2. **抽象扩展（硬）**：结账 type = **Provider 注册集合**，不是 Checkout/Payment 内硬编码 `{continue_pay,toc,tob}`。
   - **支付域模块**（Checkout/Payment 侧）自己提供：`standard`（标准结账）与 `continue_pay`（继续支付）。
   - **批发模块（B2B）**自己提供：`tob`（批发）——Checkout **不得**内置批发分支当一等公民枚举。
   - 未来模块同理：`extends` / Registry 加 Provider 即可出现在下拉；未注册则不出现。
3. UI：只外露当前命中；箭头展开其它已注册且 `isAvailable` 的 type；`continue_pay` 命中时额外醒目条 + 主 CTA「继续支付」（chrome 由 Provider 声明，非壳写死）。
4. 多桶会话：各 type 可持有自己的 session/meta；切换只改活跃 `type_code` 指针；付完/卸挂后 Provider 报告不可用则从列表消失。
5. 若仅 1 个可用 type：可收起箭头，只读外露标签。

### 设计冻结（相对 §6 · 本增量已定）

| 题 | 冻结 | 依据 |
|----|------|------|
| Q3 URL | **A** → 落地完整结账且激活支付域 `continue_pay` Provider | 勿另造页 |
| Q4 session | **按 type_code 多桶 + 活跃指针**（桶语义由各 Provider 定义） | 多 type 可切换 |
| UI | **当前命中外露 + ▾**；禁止全量并排常驻 | 用户明确 |
| 扩展方式 | **抽象 Registry + Provider**；业务 type 由各模块自注册 | 用户明确：可加类型、谁提供谁负责 |
| 批发 | **B2B Provider 注册**，非 Checkout 硬编码 | 用户明确 |

### 抽象契约草案（架构落笔前 · framework_first）

> 类名仅为方向，正式命名交架构席；须对齐仓库既有 `*ProviderInterface` + `*ProviderRegistry` + `extends` 扫描模式。

| 契约 | 职责 |
|------|------|
| `CheckoutTypeProviderInterface` | `code()`、`label()`、`sortOrder()`、`isAvailable(context)`、激活/停用钩、`resolveSession`、提交门闩（`submit_mode`）、可选 chrome；**流程能力声明**（例：是否需要收货/运输地址、是否需要配送方式、摘要/行项目策略）——供壳按声明显隐步骤，禁止壳猜业务 | `resumePaymentV2`）、可选 chrome（醒目条/主 CTA 文案） |
| `CheckoutTypeProviderRegistry` | 聚合各模块 Provider；按 availability + sort 产出下拉；解析活跃 type |
| Checkout 壳 UI | **只认 Registry 列表**；禁止 `if (tob)` / `if (continue_pay)` 业务枚举（醒目条也走 Provider chrome） |
| FE 状态 | `active_type_code` + `sessions[type_code]`（不透明桶）；切换 → 通知对应 Provider + 刷新 `getData` |

### 示例注册归属（非封闭枚举 · 仅首批预期）

| type_code（例） | 提供方模块 | 说明 |
|-----------------|------------|------|
| `standard` | **Payment/Checkout（支付域）** | 标准结账；店面文案可呈「零售」或「标准结账」 |
| `continue_pay` | **Payment/Checkout（支付域）** | 继续支付；adopt 未付订单 session 后 `isAvailable=true` |
| `tob` | **Weline_B2B（批发模块）** | 批发；门禁/信用/押金由 B2B Provider 自理 |
| `virtual`（例） | 未来虚拟商品模块 | **本迭代不做**；预期：无运输地址等流程裁剪；订单侧已支持虚拟，结账 type 后接 |
| `download`（例） | 未来下载类模块 | **本迭代不做** |

> Checkout 核心**禁止**把上表写成 `enum`；可增减；未安装 B2B 则下拉无「批发」。

### 架构映射（framework_first · 解耦）

| 层 | 做法 |
|----|------|

## 8. 耦合提示 / 需求纠偏（框架审视摘要）

- **耦合风险**：把 `#payment-recovery` UI 岛当成产品能力会与结账空车 SSR 抢主视觉 → 应用 session 挂载解耦「车空」与「可结账」。
- **框架候选**：`CheckoutSession` + Store + `quote_token` 活跃绑定；续付 API 既有 `resumePaymentV2`；URL builder（`ContinuePaymentRecoveryUrlBuilder`）需随 Q3 改契约而非新页面。
- **禁止**：平行结账页、仅 FE 假恢复、续付再 `submitV2`。
- **禁止**：Checkout 核心硬编码 `continue_pay`/`tob`/`toc` 业务枚举；type 必须由模块 Provider 注册（支付域提供标准+续付，B2B 提供批发）。

## 9. 领域探查回填（2026-09-21 · 只读）

席位：[探查继续支付 session](a44ad8a3-e544-436d-be1c-a637625eb967)

### 现状铁证

1. `showPaymentRecovery()` **故意** `form.hidden=true`，hash 入口跳过 `loadCheckoutWithRetry()` → 孤立卡是设计，非偶然。
2. 空车竞态：`announceCheckoutOrderCreated` → 清车 → `render` 用 `emptyState.hidden=!cartIsEmpty` **覆盖** recovery 对 empty 的隐藏（同页失败路径尤甚）。
3. **无** stash/swap/restore previous quote 服务；仅有 FE `adoptQuoteTokenFromUrl`（**quoted** 遗弃续结账）与 guest `rememberGuestSession`。
4. `resumePaymentV2` **不收地址**；未付改址现成能力仅 `ExpressUnpaidOrderAmend`（Express 语义），toc 续付未接。
5. `CheckoutSessionAccessService` 只做能力校验，不是「塞进当前用户会话」。

### 架构对接契约草稿（冻结前）

| 动作 | 挂载点 | 说明 |
|------|--------|------|
| `adoptContinuePaySession` | `CheckoutQueryProvider` | Access 等价校验 + stash 当前 quote → adopt 目标 `quote_token`；返回订单快照供填表 |
| `amendUnpaidCheckoutAddress` | 同上；复用/泛化 `ExpressUnpaidOrderAmend` | 改址写回未付订单 + 重报价；金额变则新 payment idempotency |
| `resumePaymentV2` | 保持 | 仅支付重试；改址必须先 amend |
| Event | `continue_pay::adopt/release` 登记 `event.php` | 审计/清车策略；禁止旁路改金额 |
| FE | 续付模式不调 `showPaymentRecovery` 藏 form；`activeContinuePay` 禁止 empty 抢显 | 付完/离开：clear adopted + restore stash |

### 风险（须进契约）

- `submitLocked` 身份硬门：guest/登录错配 → `ERROR_IDENTITY`
- URL 双轨勿混：`ContinueCheckoutUrlBuilder`（quoted）≠ recovery（submitted）
- 禁止平行 Provider / 平行 cookie 存 quote；权威仍 `weline_checkout_session`
