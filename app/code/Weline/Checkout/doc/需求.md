## 当前有效需求

### `REQ-CHECKOUT-0001` 服务端权威 Checkout V2 提交

- 来源与确认：现有 `checkout-v2.md`、`CheckoutGroupSubmitService` 与本次正式商城要求，2026-08-17 建立基线。
- 目标版本：`1.4.4`
- 背景/问题：订单金额、Scope、商品和库存不得由浏览器决定。
- 用户与运营场景：用户冻结报价并提交后，系统以同一 quote token 和幂等键创建或回放同一 CheckoutGroup/Orders。
- 业务逻辑：购物车重新定价、运费/税/库存/订单均由服务端冻结；同 token+同幂等键只回放，同 token+不同键冲突；订单创建后购物车清理为身份绑定的 best-effort，不得把已创建订单伪报为未下单。
- 范围：`freezeQuote`、`submitV2`、CheckoutSession、OrderFacade、Cart 清理。
- 非目标：不接受客户端成交金额、订单行、币种、Scope 或 customer_id。
- 数据/权限/安全：跨模块仅使用发布接口、Event 或 QueryProvider；不得依赖其他模块内部具体类。
- 兼容/迁移：保持既有 quote/session/order 幂等语义；无本次 Model Schema 变更。
- 验收标准：伪造事实被拒绝；重放不重复订单；订单已创建后的支付异常仍返回原 group/order 身份。
- WebUI/E2E：商品→购物车→结账→提交，重复点击/刷新不会创建第二组订单。
- 运营与支持影响：订单和支付结果必须可区分，客服不得把待支付误判为未下单。
- 依赖与风险：依赖 Cart、Shipping、Inventory、Order、Payment 的发布边界。

### `REQ-CHECKOUT-0002` 订单创建后的支付三态与恢复闭环

- 来源与确认：用户要求正式商城支付闭环，并于 2026-08-17 以“继续”确认建议的三态契约。
- 目标版本：`1.4.4`
- 背景/问题：订单事务先提交，支付可能成功、等待 Provider 动作或失败；当前统一抛错会丢失订单身份并诱发重复下单。
- 用户与运营场景：用户提交后能明确看到已支付、待处理/需跳转或支付失败；失败可基于原订单安全重试，而不是再次下单。
- 业务逻辑：
  1. 顶层 `success=true` 仅表示订单组已创建/回放成功；支付结果由 `payment.outcome` 区分 `paid`、`pending`、`failed`。
  2. `paid`：订单已收到支付成功通知，进入成功页。
  3. `pending`：若 Provider 返回安全跳转则继续该动作，否则进入明确待处理状态；不得显示“结账成功”冒充已支付。
  4. `failed`：保留 group/order/quote token 与原订单幂等键，提供基于同一已提交 CheckoutSession 的支付重试；支付尝试使用新的支付幂等键，不创建新订单。
  5. 订单创建后清理当前购物车，阻断相同商品被误提交为第二张订单；恢复状态通过 URL fragment/浏览器会话保存，业务请求继续走 `Weline.Api.resource('checkout')`。
  6. 登录订单按当前 customer+website 验证；游客成功页必须持有与该已提交 Session 匹配的高熵 checkout capability token，不能只凭 order UUID 读取。
- 范围：支付结果归一化、提交/恢复 Query 操作、结账恢复 UI、成功页访问校验、服务端与浏览器回归。
- 非目标：本版本不接 PayPal，不实现报价 PDF/CRM，不改变 Payment Provider 内部协议。
- 数据/权限/安全：金额和订单 owner 只从 Order 投影读取；不向浏览器暴露原始 Provider secrets；重试 token 不放入服务端请求 query，恢复 fragment 不由服务器接收；错误文案不可泄露内部异常。
- 兼容/迁移：`payment.paid` 保留供既有消费者兼容，同时新增结构化 outcome/action/recoverable 字段；无 Schema 迁移。
- 验收标准：三态均保留 group/order；失败重试不创建第二组订单；游客不能只用 order UUID 查看订单；fake_card 成功进入成功页。
- WebUI/E2E：主路径 fake_card；待处理/跳转；失败后刷新并重试；重复提交；登录与游客成功页授权。
- 运营与支持影响：订单已创建但未支付必须可在订单列表识别；用户看到明确的继续支付/待处理提示。
- 依赖与风险：当前本地 fake_card 只覆盖即时成功，pending/failed 分支需聚焦测试和可重复 E2E 控制场景证明。

### `REQ-CHECKOUT-0003` BinQuery 前端结账与可访问状态反馈

- 来源与确认：现有 `checkout-ui.md` 及用户此前明确要求使用 binquery；2026-08-17 对支付状态展示补充确认。
- 目标版本：`1.4.4`
- 背景/问题：前端不能通过直接 Ajax/controller 形成第二业务 API，也不能用含混消息掩盖真实状态。
- 用户与运营场景：用户在结账页选择配送/支付并看到加载、空车、提交、待处理、失败恢复和成功跳转状态。
- 业务逻辑：所有业务请求走 `Weline.Api.resource('checkout')`；服务端生成商品/方式 HTML；JS 只负责交互、状态和导航；文案可翻译且状态使用 `aria-live`。
- 范围：Checkout 默认模板、Query descriptor、i18n 和 Browser 验收。
- 非目标：不在主题中硬编码业务字段或直接请求 Controller。
- 数据/权限/安全：Provider URL 仅接受服务端支付结果并限制到允许的 http/https 跳转；不使用 native alert/confirm/prompt。
- 兼容/迁移：保留现有主题继承入口。
- 验收标准：业务请求扫描通过；控制台无新增错误；桌面/移动端状态与按钮可见可用。
- WebUI/E2E：真实 WLS 9514 操作结账主路径和恢复分支。
- 运营与支持影响：可根据明确提示区分待处理与失败。
- 依赖与风险：需确认运行时已加载新模板/worker，不能用缓存页面验收。
