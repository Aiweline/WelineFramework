# 1688 汉服商品分类与导入实施说明

> 用途：交给其他智能体或开发人员，完整复现 1688 汉服供应商商品的识别、分类、导入、图片处理、EAV 规格构建和前端验收工作。

## 1. 目标与硬性要求

从指定 1688 供应商店铺扫描全部商品，只导入真实汉服实物，并在本地商城形成可销售的完整商品。

每款导入商品必须具备：

- 正确的供应商、品牌和本地分类。
- 语义明确、稳定且可访问的商品地址。
- 完整标题、价格、详情和 SEO。
- 已本地化的主图、相册图、规格图和详情图。
- 主图、相册图、规格图和详情图均无工厂名 / `shop*.1688.com` / 促销底栏等水印；发现水印必须当场识别并清理，禁止带水印发布。
- 基于“汉服属性集”的 EAV 属性与真实 SKU 组合。
- 颜色轴只保留真实颜色；误入颜色的款式、角色、图款、配件必须分流到对应规格轴（该分款式就分 `style_type`）。
- 每个规格对应的 SKU、价格、库存状态和规格图片。
- 前端切换颜色或款式后，商品主图跟随切换。
- 分类页和详情页可正常访问。

硬性禁止：

- 禁止把产品规格或属性写入 `type_config_json` 或其他自由 JSON 字段。
- 禁止根据标题虚构颜色、尺码、价格、库存或 SKU 组合。
- 禁止把“仅上衣 / 套装 / 图一 / 角色名 / 配件”等非颜色值留在 `color` 轴充数。
- 禁止带着水印的商品图、规格图或详情图发布上架。
- 禁止导入清装、民国服装、新中式、汉元素、改良服装、演出服、配件或定制服务。
- 禁止查看或操作订单、支付、结算、收款等无关功能。
- 禁止创建测试订单或进入支付流程验证商品。

## 1.1 原始整体计划与当前进度

### 原始目标

最初目标不是只完成一家供应商，而是：

1. 读取本地既有的汉服分类、品牌和供应商目录。
2. 按本地品牌逐个到 1688 查找对应的官方店、工厂店或可信供应商。
3. 补齐供应商名称、店铺地址、工厂页和详细地址。
4. 扫描每个确定供应商的全部商品分页。
5. 只导入符合本文资格规则的真实汉服实物。
6. 为每款商品导入完整 EAV 规格、SKU、价格、库存、主图、相册图、规格图、详情图和 SEO。
7. 每个供应商都完成全店对账和前端验收。
8. 最后按品牌检查是否都有可售商品覆盖，并进行跨供应商去重。

因此，“当前供应商完成”不等于“原始全部品牌计划完成”。

## 3. 总体处理流程

```text
扫描店铺全部分页
→ 提取 offer ID 和详情链接
→ 抓取商品详情、SKU、图片
→ 判断是否为合格汉服实物
→ 识别朝代、形制、商品组成、人群和场景
→ 映射本地分类
→ 匹配供应商与品牌
→ 绑定汉服属性集
→ 补建缺少的 EAV 属性选项
→ 创建或更新商品主记录
→ 创建或更新真实 SKU 组合
→ 下载并绑定主图、相册图、规格图和详情图
→ 识别并清理水印（有水印当场处理，不带水印发布）
→ 纠正 EAV 轴：颜色脏值分流到款式/角色/图款/配件
→ 清理并保存商品详情
→ 生成短 SKU、语义化 handle 和 SEO
→ 执行发布前完整性门禁
→ 发布商品
→ 使用真实前端验收
→ 全店对账和审计
```

“是否允许导入”“归入哪个分类”“怎样生成规格”是三个独立阶段。必须先通过汉服资格判断，再进行分类和入库。

## 4. 店铺扫描和来源去重

### 4.1 遍历全部分页

对店铺“全部商品”逐页读取：

- 当前页码和总页数。
- 商品标题。
- 商品详情链接。
- 1688 offer ID。
- 列表主图和价格。
- 店铺内部分类。

本供应商扫描时店铺显示 212 条商品、8 页。不能只采集店铺首页推荐或当前首屏。

### 4.2 唯一来源键

使用以下组合识别同一来源商品：

```text
supplier_id + source_platform + source_offer_id
```

示例：

```text
53 + 1688 + 824496857539
```

不能使用标题作为唯一键，因为卖家会修改标题，也可能存在标题相似但实际不同的商品。

### 4.3 详情页必须提取的内容

```text
source_offer_id
source_url
source_title
source_category
shop_name
brand_name
main_images[]
detail_html
detail_images[]
sku_properties[]
sku_combinations[]
price_ranges[]
product_status
```

每个来源 SKU 还需提取：

- 来源 SKU ID。
- 属性组合。
- 单价。
- 库存或可售状态。
- 对应规格图片。
- 是否有效。

读取优先级：

1. 详情页实际 SKU 数据。
2. 页面初始化状态中的属性与 SKU 映射。
3. 页面可见的规格选择器。
4. 无法取得真实组合时停止导入并记录失败，绝不自行构造笛卡尔积。

## 5. 汉服资格判断

### 5.1 识别数据来源

将以下内容合并用于判断：

- 商品标题。
- 1688 来源分类。
- 商品属性。
- SKU 属性名称和值。
- 详情正文。
- 店铺自定义分类。
- 商品图片只作为模糊场景的辅助证据。

识别前进行：

- 全角转半角。
- 英文字母统一小写。
- 清除重复空格。
- 统一同义词写法。
- 保留朝代、形制、服装部件以及排除关键词。

### 5.2 判断优先级

```text
强制排除证据
> 来源明确商品属性
> 具体汉服形制词
> 完整标题
> 详情正文
> 1688 店铺分类
> 图片推断
```

强制排除证据优先级最高。标题含有“汉服”并不能覆盖排除条件。

### 5.3 强制排除规则

#### 清代和民国服装

出现以下明确特征时排除：

```text
晚清、清朝、清宫、清代、清女、少奶奶、格格服、旗装、旗袍、宫女服、民国、民国风
```

示例：

```text
原创大院罗衣少奶奶服装锦绣古董清女重工马面刺绣晚清服饰汉服
```

虽然包含“马面”和“汉服”，但同时出现“少奶奶、清女、晚清”，结果必须是：

```text
exclude_qing_costume
```

#### 现代改良类

严格排除：

```text
汉元素、新中式、现代改良、改良汉服、汉洋折衷、国潮改良、中式通勤、现代禅意
```

标题明确写“新中式马面裙”时，即使包含“马面裙”，也不导入。

#### 演出、影楼和角色服装

严格排除：

```text
cosplay、cos服、影楼服、摄影服、舞台服、表演服、影视服、剧组服、角色扮演、古装写真
```

“古装”“国风”本身不能证明商品是汉服。

#### 服务类商品

严格排除：

```text
来图定制、来样定制、加工定制、打版、代加工、贴牌加工、小单定制、汉服加工、服装加工、定金、补差价、专拍链接
```

示例：

```text
汉服加工定制来图来样马面裙定制支持小单定制
```

结果：

```text
exclude_custom_service
```

#### 配件类商品

商品主体仅为下列内容时排除：

```text
发簪、假发、发包、头饰、耳饰、项链、腰带、宫绦、鞋、扇子、伞、包、袜子、披帛、胸针、单独配饰
```

如果这些只是完整汉服套装内的附带配件，主体仍是服装，则可以保留。

#### 其他非汉服服装

默认排除：

```text
唐装、中山装、民族服装、禅茶服、瑜伽服、武术服、僧服、现代连衣裙、现代衬衫、现代西装
```

特别区分：

- `唐制` 可能是唐代形制汉服。
- `唐装` 通常是现代中式服装，默认排除。
- `古装`、`国风`、`民族服装`都不是汉服资格证据。

### 5.4 正向汉服证据

通过强制排除后，还必须具有强正向证据。

强形制词包括但不限于：

```text
齐胸襦裙、齐腰襦裙、交领襦裙、对襟襦裙、坦领襦裙、袄裙、褙子、直裾、曲裾、马面裙、圆领袍、道袍、曳撒、飞鱼服、贴里、披风、比甲、诃子裙、旋裙、百迭裙、破裙、宋裤、飞机袖、晋襦、半臂、大袖衫
```

朝代与结构的组合证据：

```text
唐制 + 齐胸／诃子／坦领／半臂
宋制 + 褙子／飞机袖／宋裤／旋裙
明制 + 马面裙／袄裙／圆领袍／曳撒／飞鱼服
晋制或魏晋 + 交领／大袖衫／晋襦
```

仅出现“唐风、宋风、明风”不能自动通过，必须结合具体形制或服装结构。

### 5.5 实物商品条件

允许导入的商品还必须同时满足：

- 有明确商品价格。
- 至少有一个真实 SKU。
- 有商品主图。
- 有服装规格或尺码。
- 不是定金、加工、打版或补差价链接。

### 5.6 模糊商品

以下情况标记为 `pending_manual_review`，不自动发布：

- 标题只有“古风女装”或“国风服装”。
- 标题只有“古装汉服”，没有具体形制。
- 标题与图片明显冲突。
- 标题写汉服，详情写影楼演出服。
- 标题写唐制，详情展示现代唐装。
- 来源分类是汉服，但图片为清装或现代服装。

严格模式下宁可暂不导入，也不能将非汉服混入商城。

## 6. 本地分类识别和映射

### 6.1 本地分类树为权威

1688 店铺分类只能提供辅助证据，不能直接复制。导入前必须读取本地分类树，通过分类 `code` 或 `slug` 匹配，不能写死数据库 ID。

错误：

```php
$categoryId = 17;
```

正确思路：

```php
$category = findCategoryByCode('hanfu-form-mamianqun');
```

不同环境的分类 ID 可能不同，而分类编码应保持稳定。

### 6.2 分类维度

分类识别拆为：

- 根分类：汉服。
- 朝代：汉制、魏晋、唐制、宋制、明制等。
- 形制：襦裙、褙子、马面裙、袄裙、圆领袍等。
- 商品组成：单上衣、单裙、两件套、三件套、混合款式。
- 人群：男式、女式、儿童、亲子、中性。
- 场景：日常、节庆、婚礼、成人礼等，仅在来源有明确证据时绑定。

主分类优先使用最具体的形制分类，朝代、人群和场景作为附加分类。

### 6.3 朝代分类规则

| 识别证据 | 朝代分类 |
|---|---|
| 汉制、汉代、曲裾、直裾 | 汉制 |
| 晋制、魏晋、晋襦、大袖衫 | 魏晋 |
| 唐制、齐胸、诃子、坦领、半臂 | 唐制 |
| 宋制、褙子、宋裤、飞机袖、旋裙 | 宋制 |
| 明制、马面裙、袄裙、曳撒、飞鱼服 | 明制 |

规则：

- 无法确定朝代时不要编造朝代分类。
- “马面裙”通常可绑定明制和马面裙形制。
- “褙子”来源明确写宋制时绑定宋制；否则只绑定褙子形制。
- “圆领袍”跨多个朝代，必须结合来源标题和详情。

### 6.4 形制分类规则

优先匹配最长、最具体的词：

```text
具体形制 → 服装组合 → 服装部件 → 通用汉服套装
```

例如“齐胸襦裙”必须优先匹配完整词，不能提前命中宽泛的“襦裙”。

| 识别结果 | 本地形制分类 |
|---|---|
| 齐胸襦裙 | 齐胸襦裙 |
| 齐腰襦裙 | 齐腰襦裙 |
| 交领襦裙 | 交领襦裙 |
| 坦领襦裙 | 坦领襦裙 |
| 宋制褙子 | 褙子 |
| 明制袄裙 | 袄裙 |
| 马面裙单裙 | 马面裙 |
| 圆领袍 | 圆领袍 |
| 飞鱼服 | 飞鱼服 |
| 曳撒 | 曳撒 |
| 直裾 | 直裾 |
| 曲裾 | 曲裾 |
| 无法识别具体形制但已确认是真实完整汉服 | 汉服套装 |

不能因为识别不到形制，就随意归入马面裙或襦裙。

### 6.5 商品组成判断

根据真实 SKU 款式值识别：

| SKU 内容 | 商品组成 |
|---|---|
| 只有上衣 | 单上衣 |
| 只有裙子 | 单裙 |
| 上衣＋裙子 | 两件套 |
| 上衣＋裙子＋披帛 | 三件套 |
| 同时销售单件和套装 | 混合款式商品 |

例如同一商品有：

```text
白色仅上衣
红色单裙
白色上衣＋红色裙子
```

该商品属于混合款式商品。不要把每个款式擅自拆成独立商品，应该通过 EAV 款式和真实 SKU 组合表达。

### 6.6 人群判断

证据优先级：

1. 标题明确标注。
2. 来源商品属性明确标注。
3. 详情尺码和模特说明。
4. 图片只作为辅助，不能仅凭模特性别决定。

可识别：男式、女式、儿童、亲子、中性。

### 6.7 场景分类

只有来源明确时才绑定日常、节庆、婚礼、毕业、成人礼、团体活动等场景。

- 正常汉服用于节庆或活动，可以绑定场景。
- 商品本质是舞台表演服时应直接排除。
- “拍照好看”不等于影楼服。
- 场景分类不能替代形制分类。

### 6.8 主分类和附加分类

推荐：

```text
主分类 = 最具体的形制分类
附加分类 = 朝代 + 人群 + 场景
```

示例：

```text
商品：宋制飞机袖褙子女款日常汉服
主分类：褙子
附加分类：宋制汉服、女式汉服、日常汉服
```

```text
商品：明制织金马面裙单裙
主分类：马面裙
附加分类：明制汉服、女式汉服
```

如果系统只允许一个分类，选择最具体的形制分类。

### 6.9 分类冲突示例

| 标题 | 结果 | 原因 |
|---|---|---|
| 晚清少奶奶重工马面裙汉服 | 排除 | 晚清、少奶奶是强制排除证据 |
| 新中式国风马面裙日常套装 | 排除 | 新中式是强制排除证据 |
| 宋制飞机袖褙子女日常汉服 | 导入 | 宋制＋飞机袖＋褙子构成强证据 |
| 汉服加工定制来图打版 | 排除 | 服务类商品 |

## 7. 品牌处理

品牌识别顺序：

1. 1688 商品明确的品牌属性。
2. 店铺或工厂页面明确展示的品牌。
3. 本地品牌别名表。
4. 已确认的供应商品牌。
5. 无法确认时标记为无品牌，不能编造。

品牌规范化：

- 去除首尾空格。
- 统一大小写和全角半角。
- 移除“旗舰店、厂家、有限公司”等非品牌后缀。
- 使用品牌别名匹配已有记录。

例如供应商公司全名为“曹县花朝记服饰有限公司”，确认品牌为“花朝记”时：

- 商品品牌保存“花朝记”。
- 供应商仍保存完整公司名称。

## 8. 供应商处理

导入商品前先按以下信息 upsert 供应商：

```text
supplier_code
1688 店铺 URL
1688 工厂 URL
公司主体名称
```

商品需要同时建立：

```text
product → supplier
product → source platform
product → source offer ID
product → source offer URL
```

不能只在商品详情文字中写供应商名称。

## 9. EAV 属性和规格

### 9.1 属性集

每款商品必须绑定“汉服属性集”，不能长期停留在“未分组属性”。

汉服属性集建议包含：

- 描述属性：朝代、形制、人群、面料、工艺、图案、领型、袖型、下装类型、套装组成、季节、场景。
- 可生成规格的属性：颜色（`color`）、款式/类型（`style_type`）、角色（`character`）、图款（`look_ref`）、配件（`prop`）、尺码（`size`）。

只有真正参与 SKU 组合的属性才设为规格属性。

### 9.1.1 颜色脏值分流（该分款式就分款式）

1688 常把“颜色分类”写成整段非颜色文案。导入时必须用 `Sample/Hanfu1688/ColorAxisClassifier` 判定每个选项标签，**不得**全部塞进 `color`：

| 判定结果 | EAV 轴 code | 显示名 | 典型标签 |
|---|---|---|---|
| 真实颜色 | `color` | 颜色 | 红色、浅蓝、米白 |
| 款式/组合/衣片 | `style_type` | 类型 | 仅上衣、红衣+白裙、三件套、女款短袖、飞天款 |
| 角色名 | `character` | 角色 | 关羽、诸葛亮、虞姬 |
| 看图选款 | `look_ref` | 图款 | 如图、图一、图二 |
| 配件/附赠 | `prop` | 配件 | 鞋套、胡子、竹简、古书 |

硬规则：

1. **该分款式就分款式**：含“仅上衣 / 单裙 / 套装 / 上衣+裙 / 男女款 / A款B款 / 系列名+衣片”等，一律进 `style_type`，不要伪装成颜色。
2. 同一来源 SKU 组合若同时出现颜色与款式语义，分别落到对应轴；`combination_key` 使用分流后的轴，例如 `size=s|style_type=...` 或 `color=...|style_type=...|size=...`。
3. **分流轴互斥不得整轴丢弃，矩阵须合并为单轴**：1688「颜色」选项经 `ColorAxisClassifier` 拆到 `color` / `style_type` / `character` / `look_ref` / `prop` 后，各标签对单条 SKU 互斥。`OfferEavMapper` 必须：
   - 分类判定仍按标签分流（该分款式就进 `style_type` 等）；
   - **规格矩阵**上把同源互斥的分流族选项合并为**一条**可切换轴（优先 `style_type`，有颜色+类型混排时轴显示名为「颜色/类型」），保证每个 `combination_key` 含全部已选规格轴，满足发布校验 `variant_combination_axes_mismatch`；
   - **禁止**因「未全覆盖」把分流轴整轴删掉后只剩 `size=*`（曾导致鑫耀 #311 前台无类型）。
4. 已误入颜色的历史选项，用 `scripts/remediate-misfiled-color-options-to-axes.php --dry-run` 预览，确认后 `--apply`；目标是 `residual_misfiled_color = 0`。
5. 分流时改写商品属性值与 Offer `combination_key`，**禁止**把脏标签写进 `type_config_json`。
6. 前端验收必须能按分流后的轴切换（例如切换 `style_type` 后主图与 URL 同步变化）。
7. 导入门禁：来源「颜色」多值且分类器产出 `style_type`（或角色/图款/配件）时，最终 axes 不得仅含 `size`；单测 `OfferEavMapperTest::testKeepsColorAndStyleTypeAxesWhenSkuLabelsAreMutuallyExclusive` 为契约。
8. **重导/轴重塑安全**：
   - `hanfu1688CanonicalVariantCatalog` 只按 option `value`/`id` 做身份映射，**禁止**按截断拼音 `code` 映射（`bai-xiao-xiu` 曾把「水蓝」误绑到「浅黄」→ `variant_combination_value_not_allowed`）。
   - 导入挂 `global_offer_uuid` 须 **combination_key 与 sku 同时命中**；SKU 迁轴交给 `ProductVariantMatrixService::reconcile`（可忽略目标 key 上 stale draft 的错误 uuid）。
   - `mediaRows` 规范化变体图 combination 必须传 `productId`，才能吃到 ensure 别名。
   - `writeProductAxisValues` 写入新轴后须 `writeCleared` 清掉未再出现的 color-family 轴（遗留 `color`）。
   - CREATE：`offerSpecs` 须在 generate 前按 ensure 别名重映射 `sku_overrides` keys（轴值已变中文、override 仍为来源 code 时会 `variant_sku_override_unknown_combination`）。
   - 非规格 `hanfu_*`：`hanfu1688AlignProductValuesToSharedEav` 按定义 label 对齐截断拼音 code 到共享 EAV identity；`canonicalOption` 也可按 label 命中。

伪代码（分流族轴）：

```text
redistribute color options → color / style_type / character / look_ref / prop
for each variant axis definition:
  hits = SKUs whose specification matches an option on this axis
  if axis is shared (size…):
    keep iff hits == all SKUs
  else if axis is redistributed color-family:
    keep iff hits >= 1
for each SKU:
  combination = matched shared axes + matched color-family axis (0..n labels present)
  combination_key = encode(combination)  // e.g. color=…|size=s  OR  size=s|style_type=…
```

### 9.2 属性选项补建

对每个来源属性值执行：

```text
规范化显示值
→ 查询 EAV 属性
→ 查询属性选项
→ 已存在则复用
→ 不存在则在汉服属性集对应属性下新增
→ 返回 option_id
```

例如来源出现 `XXXL130-140斤`，属性集中没有该选项，则创建：

```text
属性：尺码
显示值：XXXL130-140斤
代码：3xl-130-140
排序：位于 XXL 后
```

绝对不能因为属性值不存在，就把它写进 JSON。

### 9.3 尺码值规范化

| 来源显示值 | 前端显示值 | 内部短码 |
|---|---|---|
| S80-90斤 | S80-90斤 | S |
| M90-100斤 | M90-100斤 | M |
| L100-110斤 | L100-110斤 | L |
| XL110-120斤 | XL110-120斤 | XL |
| XXL120-130斤 | XXL120-130斤 | XXL |
| XXXL130-140斤 | XXXL130-140斤 | 3XL |

前端展示完整值，SKU 使用短码。不能把完整尺码简化成仅 S、M、L，导致体重范围丢失。

可合并的同义写法：

```text
XXXL130-140斤
3XL 130-140斤
XXXL（130-140斤）
```

不可错误合并：

```text
L100-110斤
L110-120斤
```

### 9.4 SKU 组合

只能按 1688 实际存在的组合创建规格，不能根据属性值数量自行做笛卡尔积。

来源只有：

```text
款式 A + S
款式 A + M
款式 B + S
```

本地只能创建这 3 个组合。

每个规格记录保存：

- 商品 ID。
- 来源 SKU ID。
- 短 SKU。
- 价格。
- 库存或可售状态。
- EAV 属性组合键。
- 规格图片关联。
- 状态和排序。

组合键必须由 EAV `attribute_id` 和 `option_id` 构成，不能是自由 JSON 文本。

### 9.5 短 SKU

推荐格式：

```text
供应商简称-来源商品尾号-款式短码-尺码短码
```

示例：

```text
HZJ-857539-ZLG-S
HZJ-857539-ZLG-M
HZJ-753369-HQX-L
```

要求：

- 唯一、稳定、可读。
- 建议不超过 36 个字符。
- 不把完整中文标题转换成超长拼音。
- 不把全部属性名称拼入 SKU。
- 同一来源 SKU 重新同步时保持本地 SKU 稳定。

来源 SKU ID 单独保存在来源映射字段中。

## 10. 商品主记录和规格保存顺序

每款商品以独立事务处理：

1. 根据供应商和 offer ID 查找来源映射。
2. 新建或更新商品主记录。
3. 设置品牌、供应商和分类。
4. 设置汉服属性集。
5. 补齐缺少的 EAV 属性选项。
6. 保存商品级 EAV 属性值。
7. 创建或更新真实 SKU 组合。
8. 保存规格价格、库存和状态。
9. 下载主图、相册图、规格图和详情图。
10. 建立媒体角色和规格图片关联。
11. 清理并保存商品详情。
12. 生成语义化 handle。
13. 保存完整 SEO。
14. 执行发布前完整性门禁。
15. 检查通过后发布。

任一步骤失败：

- 不发布不完整商品。
- 回滚当前商品数据库写入。
- 清理当前任务新增的孤立文件。
- 不影响已经导入成功的其他商品。

## 11. 图片导入与规格切图

### 11.1 媒体角色

至少区分：

| 角色 | 用途 |
|---|---|
| `main` | 商品主图 |
| `gallery` | 商品相册图 |
| `variant` | 款式／颜色规格图 |

详情图由清理后的商品详情 HTML 按原顺序引用本地媒体地址。

### 11.2 本地目录与文件名

建议目录：

```text
pub/media/product/1688/{offer_id}/
```

建议文件名：

```text
main-{hash}.jpg
gallery-01-{hash}.jpg
variant-{option_code}-{hash}.jpg
detail-01-{hash}.jpg
```

使用图片内容哈希去重，避免同一图片因 URL 参数不同被重复下载。

### 11.3 图片下载验证

每张图片必须检查：

- HTTP 请求成功。
- 文件不为空。
- MIME 类型确实是图片。
- 能读取图片尺寸。
- 不是 1688 错误占位图。
- 本地媒体 URL 返回 200。

### 11.3.1 水印识别与当场处理

1688 工厂图常带公司名、`shop*.1688.com`、红条促销底栏或半透明双行水印。**有水印就直接处理，不得带水印上架。**

适用范围：主图、相册图、规格图、详情图（凡进入 `pub/media/catalog/hanfu` 或商品详情 HTML 的本地图）。

识别信号（满足任一即视为命中）：

- OCR 读出工厂名、供应商全称、`1688.com`、`shop` + 店铺号。
- 底部全宽红条 / 白条徽章 / 促销价签条带。
- 半透明双行文字压在服装主体下方。

处理顺序：

```text
从 FileAsset source_url 重下源图（优先）
→ 识别水印区域
→ 能干净裁掉水印带时用 crop_scale（裁后还原目标尺寸）
→ 半透明/复杂残留再用修复模型（如 LaMa）
→ 原地替换 live 文件并更新 sha256 / 宽高 / metadata
→ OCR 或像素复扫确认无工厂名与 1688 域名硬残留
→ 删除隔离原图副本
```

硬规则：

1. 导入链路或导入后审计一旦命中水印，必须当场清理；不能只记日志继续发布。
2. 清理后必须复扫；仍有硬残留则商品保持未发布或回退该媒体。
3. 证据落在 `var/hanfu-1688/watermark-scan/`（命中清单、apply 结果、复扫报告）。
4. 参考实现：`var/hanfu-1688/apply-product-watermark-cleanup-20260905.php` 及同目录后续 rescan/apply 产物；全胜等难例优先 `crop_scale`，避免半透明水印修出鬼影。
5. 分类图不在本规则强制范围；商品 catalog / detail / variant 图必须覆盖。

### 11.4 规格图片映射

1688 通常将图片绑定到“颜色”或“款式”，不是尺码。

处理步骤：

1. 读取款式属性值及来源图片。
2. 下载图片到商品本地媒体目录。
3. 创建 `variant` 媒体记录。
4. 将图片关联到对应 EAV 款式／颜色选项。
5. 将包含该选项的全部 SKU 组合关联到该图。
6. 前端切换款式时使用当前规格图。
7. 切换尺码但款式不变时继续使用同一款式图。
8. 没有规格图时才回退到主图。

例如：

```text
蓝色上衣 + S → 蓝色规格图
蓝色上衣 + M → 蓝色规格图
蓝色上衣 + L → 蓝色规格图
```

前端图片回退顺序：

```text
当前 SKU 的规格图
→ 当前款式 option 的规格图
→ 商品主图
```

只下载图片但不建立 EAV 选项或 SKU 关联，不算规格图片导入完成。

## 12. 商品详情导入

需要保留：

- 商品介绍。
- 面料说明。
- 形制说明。
- 尺码说明。
- 洗涤说明。
- 模特信息。
- 商品细节。
- 全部有效详情图片。

1688 详情图片可能位于：

```html
<img src="...">
<img data-src="...">
<img data-lazyload-src="...">
<source srcset="...">
```

处理步骤：

1. 读取原始详情 HTML。
2. 删除脚本、iframe、广告和推荐商品。
3. 提取所有详情图片 URL。
4. 下载到本地。
5. 用本地媒体 URL 替换原 URL。
6. 保留图片原始顺序。
7. 保存清理后的 HTML。
8. 在真实前端检查详情渲染。

建议允许标签：

```text
p、div、span、h2-h6、ul、ol、li、table、thead、tbody、tr、th、td、strong、em、br、img
```

删除：

```text
script、iframe、form、input、button、object、embed、外部客服链接、追踪属性、事件属性
```

不能只生成“Available Colors”和“Available Sizes”表格代替真实详情。

## 13. 标题、handle 和 SEO

### 13.1 标题清理

删除批发噪声词：

```text
厂家直销、源头工厂、支持一件代发、现货批发、跨境专供、新款爆款
```

必须保留真实的朝代、形制、款式名、品牌和商品组成。

### 13.2 Handle

推荐格式：

```text
品牌简称 + 核心形制 + 系列名 + offer 尾号
```

示例：

```text
huazhaoji-songzhi-beizi-857539
huazhaoji-mingzhi-mamianqun-753369
```

要求：

- 语义明确。
- 全站唯一。
- 长度适中。
- 不使用完整标题拼音。
- 不使用纯 `hanfu-1688-ID`。
- 品牌前缀只出现一次。
- 同一商品更新时保持稳定。
- 修改旧 handle 时应建立旧地址跳转。

### 13.3 SEO 字段

每款商品填写：

- SEO 标题。
- Meta description。
- Meta keywords。
- 页面 H1。
- 图片 alt。
- Canonical URL。
- 系统支持时填写 Open Graph 标题、描述和图片。

SEO 标题示例：

```text
花朝记宋制飞机袖褙子女款汉服｜日常汉服
```

SEO 描述示例：

```text
花朝记宋制飞机袖褙子女款汉服，提供多款颜色及 S 至 XXXL 尺码选择，适合日常穿着、传统节庆与汉服活动。
```

关键词必须来自真实信息，例如：

```text
花朝记、宋制汉服、褙子、飞机袖、女式汉服、日常汉服
```

图片 alt：

- 主图：商品名称＋主图。
- 相册图：商品名称＋展示图。
- 规格图：商品名称＋款式值。
- 详情图：商品名称＋细节图。

## 14. 幂等更新和下架处理

重新运行导入时：

- 不重复创建商品。
- 不重复创建供应商或品牌。
- 不重复创建同名 EAV 选项。
- 不重复下载相同图片。
- 更新来源价格、库存、详情和图片映射。
- 保留稳定的商品 ID、SKU 和 handle。
- 来源商品下架时停用对应商品，不直接删除历史数据。
- 来源 SKU 消失时停用对应规格，不继续出售。

建议维护独立导入日志：

```text
supplier_id
source_offer_id
status: imported / updated / excluded / failed / pending_manual_review
reason
evidence
source_snapshot_hash
scanned_at
imported_at
```

该日志用于同步追踪，不得代替正式 EAV 商品属性。

## 15. 发布前完整性门禁

只有全部满足时才发布：

```text
是合格汉服实物
AND supplier_id 存在
AND 品牌已正确匹配或明确无品牌
AND 主分类存在
AND attribute_set = 汉服属性集
AND 至少一个在售 SKU
AND 每个 SKU 有 EAV 组合
AND 每个 SKU 有短 SKU
AND 每个 SKU 有价格
AND 主图存在
AND 相册图存在
AND 详情正文存在
AND 详情图片已本地化
AND 规格图片映射完整
AND 主图/相册/规格/详情图无水印残留
AND 颜色轴无误入款式/角色/图款/配件
AND handle 唯一且语义明确
AND SEO 完整
AND type_config_json 为空
```

任何一项失败，商品保持未发布并记录具体原因。

## 16. 第一款商品强制验收

不能先批量导入，再回头检查前端。正确方式是先完成一款商品闭环：

1. 商品成功发布。
2. 分类页可见。
3. 商品详情 URL 返回 200。
4. 主图和相册图正常显示，且无工厂名 / 1688 水印。
5. 商品详情及详情图片完整，详情图同样无水印。
6. EAV 规格正常显示；款式在 `style_type`（或角色/图款轴），真实颜色才在 `color`。
7. 所有真实规格组合可以选择。
8. 切换款式后主图真实变化。
9. 切换规格后 SKU、价格和库存正确变化。
10. URL 查询参数与当前 EAV 选择一致。
11. 没有 JSON 规格数据。
12. SKU 长度符合限制。
13. SEO 标签完整。
14. 页面具备正常购买入口，但不进入订单或支付流程。

之前实际验收中，选择不同款式后图片路径发生变化，同时 URL 更新为类似：

```text
?size=s&style_type=zhang-le-gon
```

这才证明 EAV 选择、URL 状态和图片映射真实生效。只检查数据库里存在图片字段不算验收通过。

## 19. 核心伪代码

```php
foreach ($storePages as $page) {
    foreach ($page->offers as $offerSummary) {
        $offerId = $offerSummary->offerId;
        $raw = $offerExtractor->extract($offerId);

        $eligibility = $hanfuClassifier->classify($raw);

        if (!$eligibility->allowed) {
            $importLog->exclude(
                supplierId: $supplierId,
                offerId: $offerId,
                reason: $eligibility->reason,
                evidence: $eligibility->evidence
            );
            continue;
        }

        $categories = $categoryClassifier->classify($raw);
        $supplier = $supplierResolver->resolve($raw);
        $brand = $brandResolver->resolve($raw, $supplier);

        $normalized = $normalizer->normalize(
            raw: $raw,
            categories: $categories,
            supplier: $supplier,
            brand: $brand
        );

        $media = $mediaImporter->downloadAndVerifyAll($raw);
        $media = $watermarkCleaner->detectAndClean($media); // 有水印当场处理

        $database->transaction(function () use ($normalized, $media) {
            $attributeSet = $attributeSetResolver->get('汉服属性集');

            // 颜色脏值先分流：该分款式就进 style_type
            $skuProperties = $colorAxisClassifier->reaxisMisfiledColors(
                $normalized->skuProperties
            );

            $eavOptions = $eavResolver->resolveProductOptions(
                $attributeSet,
                $skuProperties
            );

            $product = $productImporter->upsert(
                $normalized,
                $attributeSet
            );

            $variantImporter->syncActualSourceCombinations(
                product: $product,
                sourceVariants: $normalized->variants,
                eavOptions: $eavOptions,
                media: $media
            );

            $mediaImporter->attachProductMedia($product, $media);
            $descriptionImporter->save($product, $normalized->localizedDescription);
            $seoGenerator->save($product, $normalized);
            $auditor->assertPublishable($product);
            $productImporter->publish($product);
        });

        $frontendAuditor->verifyProduct($offerId);
        $importLog->complete($supplierId, $offerId);
    }
}
```

伪代码中的中间对象只在程序内存中传递。最终规格必须落入 EAV 属性、选项、SKU 组合和媒体关联，不能将整个中间对象写入商品 JSON。
