§摘要与关键决策

结论一：后台目前没有任何 AI 入口。商品优化依赖仓库外的 AI 技能 SOP（app/code/Weline/Product/doc/ai/skills/ecommerce-product-optimize/SKILL.md），运营无法在后台完成「生成 → 审核 → 应用」闭环。

结论二：商品列表与编辑页存在 14 项结构性可用性问题（新建面板常驻挤压、12 列表格在 1440 下只露出 6 列、媒体用 UUID 展示、站点文案是裸表单、悬浮助手遮挡操作区等）。在这些问题之上直接叠加 AI 入口，只会放大混乱，所以整改必须先于或同波于 AI 上线。

结论三：V1 采用「AI 生成草稿 → 人工逐字段审核 → 确认后写穿既有 save 通道 → 快照可回滚」。不引入内容版本层，不做无审核自动应用。

关键决策

决策选择理由 / 被否方案

1需求背景

1.1 问题描述

商品模块已具备完整的后台编辑能力（12 个页签、单写入口、发布诊断、审计），但「把商品写得好」这件事仍停留在人工阶段，且没有后台入口：

  • 入口割裂：现有 AI 优化能力以技能文档存在（doc/ai/skills/ecommerce-product-optimize/SKILL.md），执行依赖外部 Agent，运营在后台看不到、也不会用。
  • 质量不可控：没有字段级对比、没有采纳/驳回记录，AI 生成内容一旦写入线上就无法追溯与回退。
  • 后台本身难用：列表页左侧常驻「新建商品草稿」表单占掉约一半宽度；表格 12 列总宽约 1568px（不含勾选与操作列），1440 屏只能看到前 6 列；媒体表用 UUID 当文件名。AI 入口如果直接挂在这样的页面上，等于把新功能塞进一个已经拥挤的壳里。

1.2 目标用户

用户群体量化特征核心痛点本需求提供的能力
单店运营1–3 人，SKU < 500上新慢，文案与主图全靠手工；英文商品名与中文详情混杂列表/编辑页一键优化、批量优化
多站运营≥ 2 个 Website同一商品要按站点改写文案与图片，重复劳动按 Website + locale 生成草稿，互不覆盖
内容审核 / 店长每日审核 ≥ 20 个商品没有统一审核台，改动靠口头确认待审核列表 + 字段级 diff + 采纳/驳回
实施 / 开发者负责接模型与站点交付换模型要改代码；失败无错误码模型绑定可视化、错误码与任务日志

不同角色对 AI 优化的诉求不同：运营要快，审核要准，实施要可配置。策略按分群拆分，避免把「一键优化」做成所有人都用同一个按钮。

用户分群分群特征（量化）策略手段预期效果（量化）难度优先级
单店运营1–3 人；SKU < 500；日均上新 ≤ 10 列表行内一键优化 + 单商品配置抽屉；默认全选文案四项，图片默认 3 候选 单商品操作步数相比 T0 下降 ≥ 50%（M3）；任务 P95 ≤ 90s 中P0
多站运营≥ 2 Website；同款跨站复用 任务按 Website + locale 隔离；批量按站点分批；草稿不跨站复用 多语言覆盖商品数 +30%（以有目标语言草稿的商品计） 中P1
审核 / 店长日审核 ≥ 20 个商品 审核中心左队列右对比；字段级 diff；驳回原因枚举；批量采纳 20 个商品审核 ≤ 30 分钟；采纳率 ≥ 60%（M1） 中P0
实施 / 开发者负责接模型、换供应商 场景适配器 + 模型绑定页；单次覆盖；错误码与任务日志 接入新模型 ≤ 0.5 人天（不改业务代码） 低P1
品牌 / 店主关心成本与质量 配额与成本日志；采纳率/回滚率看板 月度 AI 成本可解释到「站点 × 任务类型」；超预算前置拦截 中P2

策略红线：① 任何分群都不能跳过人工审核；② 图片策略必须保留原图；③ 不按「是否付费用户」做能力阉割，V1 只做站点级配额。

4方案设计

4.1 能力边界

V1 做：

  • 商品文案优化：名称、短描述、详情、SEO 标题/描述/关键词
  • 商品图片优化：主图/图库候选生成（3 张），人工选图
  • 单商品 / 批量一键优化
  • 待审核列表、字段级对比、采纳/驳回、应用、回滚
  • 模型绑定与单次覆盖、权限、配额、审计

V1 不做：

  • 像素级修图、局部重绘、抠图去背景
  • 内容版本分支、定时发布、草稿箱
  • 无人工审核的自动应用
  • 改价格、库存、SKU、发布状态
  • 回写第三方平台（1688 / Amazon 等）

4.2 任务类型 = 模型标签

不新建 ai_model_tag 表。把「任务类型」作为场景适配器的 code，用适配器的 getDefaultModelBindings() 与后台绑定页表达「任务类型 → 模型」。这正是现有 ai_scenario_adapter 的用法（Model/AiScenarioAdapter.php:29,54,56）。

任务类型（运营看到的标签）scenario_codemodality输入输出默认模型解析单次覆盖
商品文案优化product_copy_optimizetext2text 商品快照 + 目标语言 + 风格 + 受众 JSON：name / short_description / description / meta_name / meta_description / meta_keywords adapter binding → ai_default_model(chat)是
商品图片优化product_image_optimizetext2image 原图 asset + 品类 + 卖点 + 场景模板 3 张候选图（MediaManager asset） adapter binding → ai_default_model(image_generation)是
图片可读性诊断product_image_reviewvision / text2text 图片 URL + 规则清单 分数 + 问题项（模糊/水印/主体占比） P2 再定是
多语言翻译优化product_translatetranslation 源文案 + 目标 locale 目标语言字段 P2 再定是

模型解析顺序（从高到低）

  1. 单次覆盖：任务配置里的 model_code（来自 <w:ai:model:select service_type="text2text" />）
  2. 场景绑定：ai_scenario_adapter.default_model / model_bindings
  3. 服务类型默认：ai_default_model（chat / image_generation）
  4. 都没有 → 创建任务阶段就失败，返回 product_ai_model_unbound，不入队、不扣配额，并给出「去绑定模型」的跳转

硬约束：图片任务只接受 text2image 模型。框架已明确图片生成不会回退到 text2text（AiService.php:541-543），后台必须在创建阶段就拦住，不能让用户排队 30 秒后才看到「模型不可用」。

批量限制：单批 ≤ 50 个商品；并发 2；失败项独立重试（新建 job 并记录 retry_of）；超过站点日配额时整批拒绝并提示剩余额度，不做「部分入队」。

4.4 待审核列表与新旧对比

左：队列

  • 筛选：站点、状态（pending / accepted / applied / rejected / expired）、任务类型、时间、操作人
  • 列表项：商品缩略图 + 名称 + 变更字段数 + 生成时间 + 模型
  • 默认排序：待审核优先，其次生成时间倒序
  • 批量入口：全选当前页 → 全部采纳 / 全部驳回

右：对比

  • 商品头：状态、更新时间、当前 locale、发布状态
  • 字段卡片：仅显示有变化的字段；旧值/新值并排
  • 文本 diff：词级高亮（增绿删红）；HTML 按块级归一化后比较
  • 图片卡片：原图 vs 3 候选，显示尺寸/格式/大小
  • 操作：采纳本字段 / 保留原值 / 全部采纳 / 驳回（原因必填）

旧值（线上）

归一化规则（避免假 diff）

  • 文本：trim、全角转半角、连续空白折叠后再比较。
  • HTML：解析为节点树，忽略属性顺序与空白文本节点；只比对可见内容与结构。
  • 数值/枚举：严格比较；空值 → 有值单独标注「新增内容」。
  • 图片：按 asset_id 比较；同图不同尺寸视为不同。

4.5 应用与回滚（关键语义）

必须先对齐的事实：商品内容没有「草稿层」。save 会直接写 EAV 并镜像 weline_product_local（ProductAdminCommandService.php:2416），前台读取的就是这份数据。因此「应用」= 立即上线，不是「存草稿等发布」。

环节规则
应用前校验草稿状态 ∈ {pending, accepted}、未过期；权限含 ai:apply；对每个字段比较「当前值 hash」与草稿 before_hash，不一致 → product_ai_draft_conflict，禁止应用。
应用单次调用 ProductAdminCommandService::execute(ACTION_SAVE)，payload 只含被采纳字段 + 完整的 media_assignments（合并而非覆盖）；local_version 必填（:2867）。
应用后写 weline_product_audit_log（action=ai_apply，含 before/after/request_hash/payload）；draft.status=applied；保存 rollback_json；发布状态不变。
缓存无需额外处理：save 内部已通过 ProductSearchProjectionMutationCoordinatorInterface 失效搜索投影（:606-615）。前台 HTML/对象缓存按既有链路刷新。
回滚应用后 7 天内可用。再次走 save，payload 取 rollback_json；同样做冲突检测；写 audit（ai_rollback）。
图片应用候选图先注册为 MediaManager 资产；应用时把 asset 加入 media_assignments。设为「主图」时，旧主图降为 gallery 第一位（可配置为移除关联，但资产不删除）。

为什么不改发布状态：save 与 publish 是两个独立命令（ProductAdminCommandService.php:81-84）。AI 只改内容，发布/下架仍由运营显式操作；这样也避免「AI 应用把草稿商品意外发布」。

4.6 图片优化流程

  1. 选原图：默认取当前主图；没有主图则要求先上传，不允许凭空生成主图。
  2. Prompt 五段式：主体描述 / 产品锁定（服装类锁定轮廓与版型）/ 场景与光线 / 构图与画幅（1:1、长边 ≤1600px、WebP）/ 禁止项（不得改 Logo、不得加文字水印、不得改变结构）。
  3. 生成：一次 3 张候选；失败单张不拖垮整单，返回 partial=true 与失败数。
  4. 入库：候选图作为新媒体资产，object key 含内容哈希，不覆盖原图（沿用现有 SOP 的 ai-lock-{sha16} 思路）。
  5. 选择：审核页并排预览；选 1 张设主图或加入图库；未选候选 7 天后清理（可配置保留）。
  6. 标记：资产元数据写 ai_generated=true、source_asset_id、prompt_hash，便于追责与批量清理。

4.7 状态机

Job

queued→ running→ succeeded failed cancelled

failed 可重试 ≤ 2 次；重试创建新 job，retry_of 指向原 job。succeeded 后不可再重试。

Draft

pending→ accepted→ applied→ rolled_back rejected expired superseded

只有 pending / accepted 可应用；applied 不可编辑；expired / superseded 只能重新生成。过期 = 创建后 7 天；superseded = 检测到线上字段已被他人修改。

10.1 术语表

术语定义
任务类型 / 模型标签运营看到的「文案优化 / 图片优化」等标签，底层对应 ai_scenario_adapter 的 scenario code 与模型绑定。
AI 草稿（draft）AI 生成、尚未应用的字段级结果，存于 weline_product_ai_draft，不影响线上。
应用（apply）把草稿写入线上商品内容，调用既有 save 命令；不改变发布状态。
回滚（rollback）用应用前快照把字段恢复；7 天窗口内可用。
superseded草稿对应的线上字段已被他人修改，草稿失效。
COW 媒体写时复制媒体行（cow_source_media_id），本次仅沿用，不改造。
搜索投影商品内容变更后需要失效的搜索/列表投影；由既有协调器处理。
