## 2.0.0 冻结基线

`WLS2-FREEZE-2026-08-13-B` 只替换当时的 byte/verification baseline。冻结后：

> 本节定义产品范围，不代表所有需求均已完成。当前实现与验收状态统一见 [WLS 当前能力与验收状态](WLS当前能力与验收状态.md)。

- 产品需求仅为 `REQ-SERVER-0001`–`REQ-SERVER-0008`，并包含 2026-08-11 已确认的“首项目在安全前置满足时由 `auto` 建立宿主独立网关，否则退纯 WLS”语义。
- 权威工程计划中的 `REQ-001`–`REQ-040` 只能分解上述八项需求，不得增加新的产品行为。
- `2.0.0` 的缺陷编号截止 `DEF-271`，测试编号截止 `TEST-138`。只有冻结时已有证据、可复现、直接违反本页需求且等级为 P0/P1 的重大缺陷可进入冻结阻断表。
- 冻结后不再开展开放式扫描、追加审查轮次或“顺手完善”。未进入冻结阻断表的优化、P2/P3 和后续发现统一进入 `2.0.1` backlog。
- 若冻结后出现新的数据丢失、权限绕过或生产服务不可恢复证据，执行者必须停止并交由产品 owner 决定是否变更本基线；不得自行扩大 `2.0.0`。

## 当前有效需求

### `REQ-SERVER-0001` WLS 2.0 Nginx-only 边缘架构

- 来源与确认：用户确认 WLS 2.0 的共享公网入口只使用宿主 Nginx；项目独立运行或降级时使用纯 WLS 高端口入口。
- 业务逻辑：宿主 Nginx 与纯 WLS 是仅有的两种现行边缘数据面。共享入口由 WLS 2.0 锁定的宿主 Nginx 提供；纯 WLS 由项目自行持有和运行。
- 范围：实现、配置、依赖、安装、探测、恢复、测试与文档均只围绕宿主 Nginx和纯 WLS。
- 非目标：不提供第三种反向代理或独立协议边缘实现。
- 兼容/迁移：WLS 1.x 项目 Nginx 在显式提升前保持原状；WLS 2.0 项目可在共享网关和纯 WLS 之间按既定状态机迁移。
- 验收标准：发布包只包含宿主 Nginx和纯 WLS 所需的可执行入口、依赖与配置。
- WebUI/E2E：无独立 UI；通过 CLI/runtime 真实启动和进程/依赖清单验证。

### `REQ-SERVER-0002` 宿主级 Nginx 共享网关

- 用户与运营场景：同一宿主的多个 WLS 2.0 项目共享 80/443，不争抢端口。
- 业务逻辑：WLS 2.0 项目发布合同要求最终发行物携带目标平台的完整签名 Gateway/Nginx 包；发布后必须满足，开发树和未被最终组装消费的 overlay 不算已携带。`--edge=auto` 先加入可信、兼容且 ready 的网关；不存在时，只有 80/443 无外来 listener、平台权限/守护条件满足且项目包通过生产签名、profile 和组件校验，首个项目才可自动建立宿主网关并注册自身。`--edge=gateway` 必须完成加入或首次建立，否则退出；`--edge=wls` 不操作网关。
- 数据/权限/安全：首次建立在独立 root-only `package-bootstrap.lock` 下进行；竞争者沿同一绝对 deadline 等待，取锁后重查可信状态，不能重复 stage。坏签名、profile 不匹配或项目分发路径任一级 symlink 必须在创建宿主锁前拒绝。包安装到宿主 A/B 槽并由 systemd system unit、macOS LaunchDaemon 或 Windows Service 管理；未完成安全安装、权限封印和数据面 ready 不得报告成功。
- 生命周期：网关一经建立即是宿主基础设施，不属于首项目；停止、迁移或删除首项目不得删除平台服务或宿主槽。首次自动建立不授权自动 upgrade、repair、rebootstrap、promote，也不授权接管未知服务。
- 非目标：不操作未知 80/443 owner，不提供多宿主高可用，不自动修改 DNS/防火墙/负载均衡。
- 验收标准：引导项目停止或迁移后网关和其他租户继续服务；未知端口 owner 不被停止或修改。

### `REQ-SERVER-0003` 项目事实源与可迁移性

- 业务逻辑：项目 UUID、域名期望状态、证书源、续签记录和 generation 始终由项目管理。网关只生成宿主派生路由状态与内容寻址证书快照。
- 兼容/迁移：项目迁移不携带宿主 enrollment；可在新宿主重新注册，或直接以纯 WLS 读取同一证书源独立运行。
- 安全：证书读取必须 no-follow，防止符号链接穿越，校验私钥/SAN/有效期/权限/摘要，发布仅引用宿主快照。
- 验收标准：子项目从网关注销后仍可在新宿主或 `edge=wls` 下使用自有证书运行。

### `REQ-SERVER-0004` `wls-edge/2` 路由、证书与租约安全

- 业务逻辑：支持 register/renew/heartbeat/drain/unregister；generation 和摘要提供幂等与 CAS；heartbeat 不得修改配置。多项目域名冲突、伪造 generation、未授权 enrollment、SNI/Host 不一致必须 fail closed。
- 状态：`PENDING_BACKEND → PENDING_CERTIFICATE → ACTIVE → DRAINING → STALE → REMOVED`。后端身份和公开路由必须经真实探针验证后才能 ACTIVE。
- 安全：未知域名不得落入首个项目；网关清洗伪造 Forwarded/连接级头；后端使用按 gateway epoch + master launch 绑定的能力。证书稳定读取在单次观察内以 `st_dev + st_ino` 防替换；持久清单跨系统重启只绑定路径、摘要、大小、inode、owner/group、mode 与 link count，不能把可能随重启重分配的 `st_dev` 当作持久身份。
- 验收标准：冲突、重放、越权、请求走私和跨租户流量均被可重复测试拒绝。

### `REQ-SERVER-0005` 网关自动恢复与安全回滚

- 业务逻辑：区分控制面降级和数据面中断。数据面健康时只接管控制器，不 reload。真实数据面连续失败后，按身份验证重启、配置 LKG 回滚、A/B 二进制回滚、状态重建和熔断/退避执行。
- 安全：自动恢复只能操作清单中通过 PID、可执行摘要、slot、epoch 和 generation 验证的进程/世代。损坏状态要隔离，不可 fail open。
- 恢复：发布与重引导均持久化阶段，在任一崩溃点可决定性继续或回滚；回滚旧世代只有经身份与健康观察后才重新开放。
- 验收标准：控制器崩溃不中断健康 Nginx；Nginx、坏配置、坏二进制、损坏状态和连续崩溃均有无假绿恢复证据。
- 依赖与风险：普通 A/B 升级使用不可变稳定 Launcher 恢复旧槽；但替换稳定 Launcher/CA 的整代 rebootstrap 在 `COMMITTED` 后还需独立 Recovery Guardian、5 分钟试用期和单调 generation-head。当前 24 小时旧代仅是认证恢复源，该阻断未闭合前不得声称 rebootstrap 提交后可自动回滚。

### `REQ-SERVER-0006` 纯 WLS 独立/降级运行

- 业务逻辑：显式 `edge=wls` 完全不接触网关。`edge=auto` 在首次建立条件不满足（包括未知 owner 占用 80/443、无平台权限、缺失/无效发行包或守护建立失败），或已运行网关数据面连续不可用 90 秒时，在同一 Master 中提供项目自持 TLS 高端口入口。
- 端口/网络：自动高端口在 20000–29999 内稳定分配，以宿主锁和真实 bind 为准。默认仅 loopback，不自动改 DNS/防火墙/LB，必须报告真实地址与限制。
- 切回：网关路由恢复 ACTIVE 并连续健康 30 秒后切回，高端口继续排空 300 秒后关闭。仅控制器故障而 Nginx 数据面健康时不得降级。
- 证书：纯 WLS 使用项目同一证书源与 generation；无效证书不替换当前 TLS 上下文，不隐式生成生产自签名证书。
- 本地启动权限：正确的系统 hosts 映射必须先只读验收，不得因文件不可写而误报；缺失时，交互式 POSIX `server:start` 只允许由系统 `sudo` 获取一次授权并复用票据，密码不得进入 WLS 输入、日志或持久状态。同一会话内仅最小 hosts 编辑与当前本地开发 CA 的 macOS/Linux 信任库同步可提权；macOS 必须按当前 CA 精确指纹写入 System/Login Keychain、清理同名旧根证，并用站点叶证书验证系统信任链，不得用自签根证验证自身。单次启动的配置/hosts/CA 信任副作用只能求值一次。
- 验收标准：多项目同时降级获得不同地址；项目可独立迁移运行；恢复后按 30/300 秒状态机切回。

### `REQ-SERVER-0007` WLS 1.x 显式提升与兼容

- 业务逻辑：WLS 1.x 项目保持原状，不自动加入 2.0 网关。旧 `adapter=wls`/`--no-nginx` 映射到 `edge=wls`；旧 `adapter=nginx` 先保持 legacy。
- 提升：仅当前 80/443 原项目升级后可由管理员显式 promote，经影子验证、公告维护窗、受控端口交接和失败回滚完成。
- 非目标：不承诺所有平台都能对不支持 socket activation/句柄继承的旧 owner 做绝对无缝交接。
- 验收标准：成功提升和每一个失败指令点都有可重复回滚证据。

### `REQ-SERVER-0008` 正确性、三平台与百万请求门禁

- 验收范围：安全、多项目隔离、路由/证书、恢复、reload/drain、SSE、WebSocket、H1/H2，以及 macOS/Linux/Windows 平台服务与重启恢复。H3 只有真实 QUIC 通过时才声明支持。
- 数据库：持久化、锁、事务和完整 Gateway 门禁使用 PostgreSQL；SQLite 不能代替生产语义证据。
- 性能：Nginx 网关与纯 WLS 各执行当前源码下精确 1,000,000 次防假绿请求，证明响应身/状态、零串租户和进程稳定；旧代码压测不能替代。
- 运行安全：测试使用唯一 `ai-test-*` 实例和 `>=9502` 的端口；不触碰 9501、宿主现有 80/443 owner 或未知进程。
- 完成定义：新鲜代码复审通过后，再按聚焦→PostgreSQL 完整目录→真实运行时→百万请求→三平台的顺序验收；任一环节未证明则 WLS 2.0 不可声称 release-ready。

### `REQ-SERVER-0009` 匿名首页 READY receipt 进程快路径

- 来源与确认：用户要求先审查真实首页 QPS 持续低下且会排队/超时的原因，修复后以 10,000 次真实首页请求形成结论；不以百万请求替代本轮性能迭代。
- 业务逻辑：Worker 在 READY 阶段已验证的匿名首页 receipt 必须保留 `cache_key + identity_digest`，并仅从当前 Worker 的 Process L1 返回缓存响应；不得丢弃证明字段后重建 Store/Channel 变体，也不得每次重入 App/Router。
- 安全边界：只允许同 scheme/host/effective-port、根路径、无 Cookie、GET/HEAD、HTML Accept 且 HTML quality 大于 0 的请求消费精确 receipt；`cache_key` 必须与 SHA-256 `identity_digest` 常量时间绑定。失配、过期或 Process L1 缺失时必须终止 Worker 快路径并返回普通 Framework 路径，不得再进入通用查找或读取 Shared L2，也不得放宽无请求级 Storefront 版本快照的通用预路由门禁。
- 语义：GET 仅在 gzip quality 大于 0 时复用进程内 gzip 格式化响应；格式化响应必须随同键 payload 替换、过期或淘汰而失效，且 TTL 不得超过 payload；HEAD 保留与 GET 一致的响应头但不发送 body；非 HTML、授权头、私有 Cookie、预览/编辑和非根路径不允许进入该快路径。
- 性能验收：在唯一 `ai-test-*` 实例和 `>=9502` 端口上，使用 HTTP/2、4 个物理 lane、32 并发、gzip 对真实 `/` 执行精确 10,000 次；要求 10,000/10,000 成功、0 错误、Worker 不重启，并且响应证明 Process FPC HIT 且 `UrlParser=0`/`UrlParserApply=0`。实测 QPS/P50/P95/P99 作为同机修复前后证据，不冒充跨机 SLA。

### `REQ-SERVER-0010` 本地化首页统一键精确进程快路径

- 来源与确认：用户要求继续优化首页，同时明确禁止为了速度丢弃语言、货币、Store、Channel 或路由顺序语义；`/USD/`、`/en_US/`、`/USD/en_US/`、`/en_US/USD/` 均须保持可缓存且功能完整。
- 统一解析与键：语言/货币只能由 `State::resolveLocalizationFromPathSegments()` 解析，Website 目录前缀只能由 `State::stripWebsitePathPrefix()` 按完整路径段边界剔除；receipt 必须在 Framework 已冻结 `StorefrontCacheKeyContext` 后，从既有统一 FPC key 捕获。统一 key 继续包含精确完整 URI、语言、货币、Website、Store、Channel、scope mode、context/cache version 与 namespace fingerprint；不得把两种组合顺序合并为同一 visitor-facing URI key。
- 快路径边界：仅匿名、无 Cookie、GET/HEAD、HTML 且路径解析后没有业务剩余段的本地化首页可消费精确 Process L1 receipt。同 scheme/host/effective-port、规范化查询、`cache_key`/SHA-256 identity 和当前 payload 必须同时匹配；失配、过期、淘汰或清缓存后返回 Framework，不得由 Worker 重建 Store/Channel，也不得回退读取 Shared L2。
- 生命周期：receipt 数量必须有界，并随对应 Process payload 的替换、过期、淘汰、显式删除与 `clearProcessCache()` 一起失效。首个已完成 Framework FPC 命中/发布负责登记；此前的冷请求仍执行完整路由与作用域解析。
- 验收：四种路径逐一验证状态/正文/语言货币维度，两个组合顺序证明 key 不同；再以唯一 `ai-test-*`、端口 `>=9502`、HTTP/2、4 lanes、32 并发、gzip 对本地化首页执行精确 10,000 次，要求零错误、四 Worker 稳定且热响应 `UrlParser=0`/`UrlParserApply=0`。
