## `2.0.10` — Worker READY 租约确认短暂锁竞争有界重试

- 需求 ID：`REQ-SERVER-0018`
- 真实 RED：在 Master PID `28905` 在线、实例最终仍可自愈到 `5/5` 的前提下，串行滚动热重载稳定暴露新 Worker 的公开租约确认遇到 `Timed out acquiring the WLS state lock.`。原实现立即以 `public_lease_confirmation_failed` 拒绝 Worker，造成 READY 批次停在 `1/2`、约 87 秒后超时退出，再由 Master 自检补齐容量；这才是本轮日志里的真实热重载稳定性缺陷，和回环 Host 的 421 不是同一个问题。
- 根因：公开租约确认需要获取 WLS 状态锁，但 READY 路径没有区分短暂锁竞争与租约身份/代际/监听证明失败；一次竞争就进入不可信 Worker 销毁路径。
- 修复：在 `ServiceOrchestrator` 内增加严格包装，只对精确的状态锁超时 `RuntimeException` 做最多三次确认，退避为 50ms、100ms；确认成功前不接纳 READY。第三次仍失败继续抛出，身份不匹配等其他错误不重试，现有 fail-closed 证明链保持不变。
- 自动验收：新增用例先因方法不存在得到 RED，修复后聚焦重试行为 `1 test / 8 assertions`、READY 顺序与重试组合 `2 / 17` 通过；该测试文件排除一个与本修复无关、工作树既有的 managed identity 断言后为 `119 / 549` 通过。实现、测试与 Worker PHP lint 及 scoped diff check 通过。聚焦/文件级测试会用默认 WLS 日志器记录夹具中的预期失败分支，因此最终错误日志 115–148 行均带 `[PHPUnit]`，不属于在线 Master 新故障；在线故障证据仍严格限定为 105–114 行，崩溃日志保持 891 行。
- 已知非本轮阻断：该测试文件全量仍有一个既有 managed identity cache 断言失败；`GatewayProtocolSecurityTest` 的 133 个用例在环境初始化阶段因 `macOS boot identity is unavailable` 全部 error、0 assertions；`NativeGatewayBrokerTest` 30 个用例均因当前环境条件 skip。这些结果没有被冒充为 Master 修复通过证据。
- 激活状态：修复位于 Master 已加载的 `ServiceOrchestrator` 类中，现有 PID `28905` 不会通过 Worker 滚动热重载重新载入它。为遵守 Master 持续在线边界，本轮未擅自重启默认 Master；当前实例已由旧逻辑自愈并保持 `5/5`，源码修复需在下一次受控 Master 生命周期加载后再做真实滚动热重载 GREEN 验收。

## `2.0.9` — 本机回环别名安全跳转默认站点

- 需求 ID：`REQ-SERVER-0017`
- 用户现象：直接访问 `http://127.0.0.1:9555/...` 或 `http://localhost:9555/...` 时显示 `421 Misdirected Request`，容易被误认为 WLS/Master 已掉线。
- 诊断：421 是原生 HTTP Host admission 的预期失败关闭；回环 Host 不属于 serving manifest 的站点域名。Master 与 4 个 Worker 实际持续在线，问题是缺少只面向本机入口的默认站点引导。
- 修复：仅接受精确 `127.0.0.1:<当前监听端口>` 与 `localhost:<当前监听端口>`，从 Worker 启动时不可变的 `WLS_PUBLIC_ORIGIN` 取得目标；目标必须是 HTTPS、同监听端口、无凭据/查询/片段、无业务路径，并再次命中当前 serving manifest 中证书状态为 active 且 route_id 非空的路由，才返回 308。请求路径和查询参数沿用既有净化逻辑完整保留。
- 安全边界：错误端口、无端口回环 Host、派生 localhost 名称、任意未知或畸形 Host 继续返回 421；不改变 TLS SNI/证书选择。`https://127.0.0.1:9555` 无法在证书校验前做 HTTP 跳转，仍应使用规范域名。
- 自动验收：`worker_ssl.php` PHP lint 与 diff check 通过；`ProjectServingManifestStoreTest`、`PureWlsServingManifestRecoveryContractTest` 共 `45 tests / 2149 assertions` 通过，只有项目既有 PHPUnit deprecation 提示。
- 真实验收：RED 阶段两个回环入口均为 421；首次滚动热重载耗时 8 秒后，两个入口均返回 308 到 `https://p05113ef3.weline.test:9555` 并精确保留路径/查询。错误端口、未知 Host 与 `foo.localhost` 仍为 421；两组各 20 次并发请求全部 308。规范 HTTPS 首页为 HTTP/2 200、证书校验结果 0，促销主题页按未登录状态正常 302，健康检查 200。Master PID 全程保持 `28905`，最终实例 `5/5`。后续为独立检查 Master 热重载而执行的串行压力复核新增了在线错误日志 105–114 行，暴露 `REQ-SERVER-0018` 的状态锁竞争误杀；后续 115–148 行均为测试夹具的 `[PHPUnit]` 预期失败分支日志，崩溃日志仍为 891 行。该后续缺陷不影响本节回环跳转验收，但已单独记录，未沿用“无新增错误”的旧结论。

## `2.0.8` — Worker 硬内存压力安全退役

- 需求 ID：`REQ-SERVER-0016`
- 用户现象：用 `http://127.0.0.1:9555/...` 打开促销后台出现 `421 Misdirected Request`，担心 WLS/Master 不稳定。
- 诊断：421 来自纯 WLS 的 Host/SNI 失败关闭策略，不是 Master 掉线；正确公网入口为 `https://p05113ef3.weline.test:9555`。历史日志另发现真实稳定性缺陷：Worker 在 512MB 硬压力下仍由内存守卫先调用 `gc_collect_cycles()`，GC 工作区申请会让守卫自身 OOM。该时段同时存在 `fresh_test`、`worker_test`、`network_test`、`first_call_test`、`error_test`、`fix_verify` 与 QueryBin 批量探针；Master PID 一直存活并持续补齐 Worker。

- 自动验收：目标测试先以 `cycle_collection_skipped=null` 有效失败，再转绿；`WorkerResponseMemoryGuardCompactionTest` `8 tests / 50 assertions`、`WorkerResponseMemoryGuardTest` `17 / 22`、`WlsRuntimeResetQuarantineTest` `1 / 5` 全部通过；实现与测试文件 PHP lint 通过。PHPUnit 仅报告项目既有 deprecation 提示。

## `2.0.6` — TLS 数据面隔离不再结束 Master 控制面

- 需求 ID：`REQ-SERVER-0014`
- 现象：证书事务未返回 exact terminal ACK 后，Orchestrator 以 `tls_reload_fail_stop_unverified` 停掉整 Master；另有 STOP 收到 `Unauthorized control command` 后仍显示连接关闭/接受成功。
- 根因：证书安全 containment 把 TLS 数据面与 Master 控制面视作同一故障域；STOP 流只解析进度文案，没有先处理 `command_result.success=false`。
- 修复：保留 manifest/ACK/listener/进程租约 fail-closed 合同，失败时置 TLS quarantine 并冻结 TLS spawn/resurrection，Master IPC 持续在线；状态暴露 `tls_serving_quarantined`；STOP 否定回执与接受前 EOF 均返回失败。
- 运行验收：两个修改 PHP 文件 lint 通过；既有聚焦测试 58/58、StopCommand 测试 79/79 通过；独立 `9519` TLS 实例返回 HTTP 200，隔离回执为 `quarantined=true/zero_serving=true/master_control_plane_preserved=true`，Master PID 与控制端口保持不变且 Worker 未复活；显式 STOP 后 `9517`–`9519` 与控制端口均无监听。

## `2.0.4` — 首页预热失败不得拖垮 WLS 启动

- 需求 ID：`REQ-SERVER-0012`
- 现象：Worker READY 前门禁 in-process 渲染首页时，模板 `E_COMPILE_ERROR`（不可捕获）会杀死进程 → Master `WLS_STARTUP_FAIL_FAST`。
- 产品结论：业务预热失败属正常；只要 Worker 存活并发 READY，WLS 不得因首页未 hot 报启动失败。Session/Memory/TLS 等基础设施预热仍可硬失败。
- 修复：`wls.worker.ready_gate_homepage_fail_open` 默认 `1`；fail-open 时 READY 前跳过 in-process 首页渲染（延后到 deferred warmup）；Master 以 warning 接纳非 hot；`worker_ssl`/`worker`/`worker_ssl_event` 对业务预热 Throwable fail-open。
- 严格模式：显式设 `ready_gate_homepage_fail_open=0` 才恢复旧的 in-process 证明门禁。

## `2.0.1` — 匿名首页 READY receipt 快路径回归

- 需求 ID：`REQ-SERVER-0009`
