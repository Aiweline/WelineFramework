# Weline_Server 开发日志

## 2026-09-24 — `server:start -clean -f` 假阴性跳过 stop（2.0.82）

- 现场：`php bin/w server:start -clean -f -p 9555 -c 4 -r` 直接报「无法强制清理实例：启动/生命周期锁仍被占用，或仍有本实例受管进程存活」，且**没有**先走 stop -f 提示。
- 根因链：
  1. Master 命令行仅有 `--name=`、无 `--launch-id=`，但 pid_index 记录带 `launch_id`；`Processer::doesPidMatchRecordedIdentity` 把「cmdline 无 launch-id」当成不匹配 → `ServerInstanceInfo::isMasterRunning()` 假阴性。
  2. IPC `getStatus` 超时 → `isInstanceRunning()` 假阴性。
  3. `prepareForcedCleanStart` 仅靠上述两项判断 `needsStop`，跳过 stop；此时 gateway agent（`certificate_retirement_replay`）仍占用 lifecycle flock，且 Master 租约/受管 PID 仍在 → `forceCleanupInstance` 正确拒绝。
  4. 即使纠正 needsStop 后，`server:stop -f` 仍因取不到 lifecycle 锁（被同实例 `certificate_retirement_replay` 卡住）直接返回，Master 残留。
- 修复：
  - Framework `launchIdMatchesCommandLine`——cmdline 未广告 launch-id 时不以索引 launch_id 否决 name 匹配；
  - Server `hasForceCleanBlockingPresence`（租约/受管 PID/控制端口/lifecycle·start flock）并入 `-clean -f` 的 stop 判定；
  - `Stop::acquireStopLock(..., force)` 在 `-f` 下可中止同实例后台占锁任务（禁抢 start/stop/reload/force-clean/stale-cleanup）后再取锁。
- 回归：ProcesserTest launch-id 用例；CleanupTransactionTest blocking presence；PureWlsServingManifestRecoveryContractTest 契约断言。
- 版本：Server `2.0.81` → `2.0.82`；Framework `2.5.173` → `2.5.174`。

## 2026-09-23 — `server:start -clean -f` 强制清理并启动（2.0.80）

- 用户意图：`-f` 与 `-clean` 同用时应强制执行，覆盖仍在线、锁探测不确定、端点 JSON 损坏；不能继续只打印「先 stop 再 -clean」。
- 语义分界：纯 `-clean` 仍 fail-closed、不发进程信号；`-clean -f` 先对本实例做 `server:stop -f`（若仍在线/Master 存活），再 `forceCleanupInstance()`：先走安全离线事务，失败后才退役损坏端点/sidecar，仍拒绝「可证明持有」的 lifecycle/start flock 与本实例存活受管进程，不误杀他实例。
- 帮助与契约测试同步；新增损坏端点强制清理与持锁拒绝单测。
- 版本：`2.0.79` → `2.0.80`。

- 现象：证书事务未返回 exact terminal ACK 后，Orchestrator 以 `tls_reload_fail_stop_unverified` 停掉整 Master；另有 STOP 收到 `Unauthorized control command` 后仍显示连接关闭/接受成功。
- 根因：证书安全 containment 把 TLS 数据面与 Master 控制面视作同一故障域；STOP 流只解析进度文案，没有先处理 `command_result.success=false`。
- 修复：保留 manifest/ACK/listener/进程租约 fail-closed 合同，失败时置 TLS quarantine 并冻结 TLS spawn/resurrection，Master IPC 持续在线；状态暴露 `tls_serving_quarantined`；STOP 否定回执与接受前 EOF 均返回失败。
- 运行验收：两个修改 PHP 文件 lint 通过；既有聚焦测试 58/58、StopCommand 测试 79/79 通过；独立 `9519` TLS 实例返回 HTTP 200，隔离回执为 `quarantined=true/zero_serving=true/master_control_plane_preserved=true`，Master PID 与控制端口保持不变且 Worker 未复活；显式 STOP 后 `9517`–`9519` 与控制端口均无监听。

## `2.0.4` — 首页预热失败不得拖垮 WLS 启动

- 需求 ID：`REQ-SERVER-0012`
- 现象：Worker READY 前门禁 in-process 渲染首页时，模板 `E_COMPILE_ERROR`（不可捕获）会杀死进程 → Master `WLS_STARTUP_FAIL_FAST`。
- 产品结论：业务预热失败属正常；只要 Worker 存活并发 READY，WLS 不得因首页未 hot 报启动失败。Session/Memory/TLS 等基础设施预热仍可硬失败。
- 修复：`wls.worker.ready_gate_homepage_fail_open` 默认 `1`；fail-open 时 READY 前跳过 in-process 首页渲染（延后到 deferred warmup）；Master 以 warning 接纳非 hot；`worker_ssl`/`worker`/`worker_ssl_event` 对业务预热 Throwable fail-open。
- 严格模式：显式设 `ready_gate_homepage_fail_open=0` 才恢复旧的 in-process 证明门禁。

## 2026-09-13 — SessionStore 同时识别有效内存与已分配内存压力

- 问题证据：共享 Memory 服务在 256MiB 限额下出现 5 次 OOM，分配点包含协议解码、读缓冲拼接与写缓冲复制；只读 STATS 样本显示 live 约 176MiB、allocated 约 236MiB，而既有高水位为 192MiB。旧 `SessionStore` 仅检查 live，不能识别这个分配余量不足的状态。
- 实现：复用现有 `evictIfNeeded` 与 `relieveMemoryPressure` 入口，同时检查 live / allocated；仅 allocated 达高水位时先调用 `gc_mem_caches()` 归还可释放的空闲页，压力仍在才执行有限 LRU。此类单次淘汰最多为当前键数的 10%（至少 1 个），不等待 allocated 下降而持续清空缓存；live 压力仍按原低水位回收。低压路径直接返回，不运行 allocator 回收或 LRU。
- API：`relieveMemoryPressure(int $reserveBytes = 0)` 保持既有无参调用兼容；可选临时分配预留通过降低本次目标水位复用同一压力入口，不改变配置限额。本轮调用方不需要接入该参数；缓冲区减少复制的修复由 `SessionServer` 独立处理。
- TDD：新增 `Test/Unit/Session/Server/SessionStoreMemoryPressureTest.php`。旧实现先出现 allocated-only、外部持有数据时的有限淘汰、临时预留 3 个预期失败；修复后使用正式 `app/bootstrap_phpunit.php` 通过 5 tests / 17 assertions，另覆盖低压无额外回收与既有 live 低水位行为。
- 验收边界：本节是源码与定向测试证据，未调整内存限额、未重启共享服务；实际运行与网站请求由主任务统一验收，不能据此宣称所有 OOM 或请求耗时已经解决。
