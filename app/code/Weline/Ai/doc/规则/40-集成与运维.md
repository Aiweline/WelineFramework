## 1. 壳 + Provider 同构（`shell_provider_business_isomorph`）

适用范围：万能支付、货源代发、对接供应商 / 支付方式、「业务写在 Controller」味道的实现。

| 允许 / 必须 | 禁止 |
|------|------|
| **Extends Provider 一文件**按能力接口实现；壳**只编排** | 在壳 Controller/Service **重写**某供应商 API/凭证解析/履约/目录/支付生命周期 |
| 对接交付 = **Provider + 配置模板** | 为每个供应商新写一套业务控制器；绕过 Provider 接口硬编码网关 |
| 退款走 `Provider.refund` + 壳 Ledger | 壳碰卡号；密钥明文；回调非纯函数 |

**支付域必上场专席**（`payment_engineer_for_payment_work`，**强制**）：

- `Team:支付开发工程师:` + `payment_development`（`weline-payment-development`）；
- **禁止**支付域只派后端 / 通用 Provider 不上场支付开发工程师；
- **`payment_browser_e2e_closed_loop`**：改完**必须**拉起 `Team:测试:` 用**真 Browser** 过触及支付全流程并留证据，才允许 review pass；
- **禁止**只改代码不拉测试席、不用真浏览器过全流程就宣称过手。

权威：[支付开发.md](../../../../../../dev/ai-command/ai/支付开发.md)、[payment-shell.md](../../../Payment/doc/payment-shell.md)、[provider-development.md](../../../Payment/doc/provider-development.md)、[dropship-shell.md](../../../Dropship/doc/dropship-shell.md)、[provider-development.md](../../../Dropship/doc/provider-development.md)。

## 2. 图片：选图 vs 出图（`image_explicit_width_height_css`）

| 场景 | 做法 | 禁止 |
|------|------|------|
| **选图**（已有素材选择） | `<w:file-manager>` 或 `WelineMedia`；Theme 部件 `media_image` 用 `value_mode=file-image` + `usage=1` | 把 `file:image` 当选图器 |
| **出图**（动态业务图） | `<w:file:image>` 设 `width`+`height` 或 `aspect_ratio`（HTML 占位防 CLS）+ 主题 CSS `max-width:100%;height:auto` | 只写响应式 CSS 不写 HTML width/height；无尺寸裸 `<img>`；裸 `<img src>` 替代 `<w:file:image>` |
| **格式与体积**（所有网页图，含上传/主题/CMS/博客/商品） | 终态 WebP；按展示尺寸出派生图并压缩；详见 §4 | 原图直接进 `pub/media` / 页面；大 JPG/PNG 长期交付 |

验证：源码含 width/height 或 aspect_ratio；主题 `.w-file-image` / foundation `height:auto`；店面图 `Content-Type: image/webp` 且体积在 §4 预算内。权威：[file-image-cls-尺寸与响应式.md](../../../FileManager/doc/file-image-cls-尺寸与响应式.md)、[选图与出图分工](../../../FileManager/doc/file-manager-选图与file-image出图.md)、[weline-image-pipeline.md](../../../Product/doc/ai/skills/ecommerce-detail-suite/companions/weline-image-pipeline.md) §6.5。

## 4. 所有网页图默认 WebP + 压缩（`web_images_webp_compressed`）

适用于**所有网页栅格图**：AI 生图（GenerateImage / MediaManager AI 画图 / 主图·Banner·Hero / 管线导出）与普通上传（主题 assets、CMS、博客配图、商品图、营销图）。

| 允许 / 必须 | 禁止 |
|------|------|
| **终态落盘 `.webp`**；`output_format=webp`；返回 png/jpg 须**转码后再交付**（`cwebp -q 80` / Pillow / GD `imagewebp`）；落盘后路径与库引用一致 | 原图直接进 `pub/media` / 页面；默认交付大 PNG/JPG；生图工具返回 PNG 却不转码就当终态；`pub/media` 长期留 jpg/png 店面图 |
| **按展示尺寸出派生图**：重采样到实际显示尺寸（视网膜 ≤2×，**禁止放大**）；长边：内容/商品 ≤1600px，Hero/Banner ≤2560px | 用相机原图/AI 原图尺寸直接上页面；靠浏览器缩放大图 |
| **体积预算**（清晰度优先下取最小）：内容/商品 ≤200KB，缩略图/卡片 ≤80KB，Hero ≤350KB，图标/Logo ≤30KB；编码后目检 | 为「无损」把页面压成几 MB；压到糊字、糊边仍交付 |
| PNG 仅：用户明示 / 确需非 WebP 透明 / `favicon`·`ico` / 平台硬性 | 用 PNG/JPG 当默认店面图格式 |

原图只作**源文件**保留，不进公开目录、不直接引用。运行时落点：MediaManager `AiDrawService`（默认 webp + `ensurePreferredRasterFormat` 后处理）、Ai `AiService` 身份资产默认 `output_format=webp`。权威：[weline-image-pipeline.md](../../../Product/doc/ai/skills/ecommerce-detail-suite/companions/weline-image-pipeline.md) §6.5。

## 8. WLS 托管 Nginx 支持 FPM 回源（`wls_managed_nginx_supports_fpm_origin`）

托管 Nginx 的 `wls.edge.nginx.origin_mode` 有两档：

| 模式 | 回源 | Worker / Session / Memory |
|------|------|---------------------------|
| **`wls`（默认）** | `proxy_pass` → loopback Workers | 需要 |
| **`fpm`** | `fastcgi_pass` → 本机 php-fpm → `{BP}/pub/index.php` | **不需要**；可全停 |

| 允许 / 必须 | 禁止 |
|------|------|
| 用 `php bin/w server:origin:set fpm\|wls`（可选 `--fpm-listen=`）切换 | 自造平行切换路径；把手改 live conf 当 `origin_mode` 真相源 |
| FPM = **协助部署**：仍走**项目隔离**托管 Nginx | 向系统 `/etc/nginx` 注入站点 |
| 切到 `fpm` 后停业务平面并保留 Nginx（`server:stop --keep-nginx`；`origin:set` 已自动做） | 假定「WLS 只能 Workers 回源」 |
| 切回 `wls` 后**手动** `server:start` | 指望 `origin:set wls` 自动拉起 Worker |
| TLS / Local CA / Host 目录与 WLS 回源**同路径** | `origin_mode=fpm` 时丢掉证书，或回退 `server_name=_` + localhost 叶证 |
| — | `server:start` 静默改 `origin_mode` 或静默安装 Nginx |

权威：[WLS模式部署指南.md](../../../Server/doc/WLS模式部署指南.md)「回源模式：WLS Workers vs PHP-FPM」。宿主镜：`~/.cursor/rules/wls-managed-nginx-supports-fpm-origin.mdc`。

## 9. 口令「主题更新」对站柜关系卡后拷贝再升级（`theme_update_matches_site_cabinet`）

用户把「主题更新 / 更新某主题 / 发布主题 / 发布某主题 / theme update」当作**上传皮肤**的口令时（不是在改 CSS）。「发布主题」与「更新主题」是同一口令：

| 必须 | 禁止 |
|------|------|
| 读本机网站柜各站 `websites/<site>/关系.md`，把口令里的主题名或站点别名**唯一**匹配到一张卡；拷贝前用同目录 `server.md` 核对应用根 | 凭记忆、SSH 别名碰撞、或公网 HTML 猜主机；`server.md` 与关系卡应用根不一致仍拷 |
| 卡上同时写明主用 SSH Host、应用根、主题注册名、本机主题目录，才算匹配完成 | 应用根未核验、或写明无生产 Host 时仍去 SSH / 拷到别的站 |
| 只把该主题目录 `rsync`/`scp` 到 `{应用根}/app/design/{Vendor}/{theme}/`，**默认无 `--delete`** | 把 A 站主题拷进 B 站应用根；`rsync --delete` |
| 目标机 `php bin/w theme:update -t <theme>`（世代切换：构建新代次→校验→翻指针；**不开关维护模式**）；仅新主题首次注册 / 新布局 / 模块注册面有变时，才先补 `setup:upgrade` | 只在本机 `theme:update`、不拷贝，就当成已经上线；把主题更新放进 `maintenance:enable/disable` 窗内 |
| 探活走 SSH 上的 `127.0.0.1` + `Host` | 从 Agent 本机 curl 公网域名 |

无站柜关系卡的本机 design 目录不是站点，对不上就停手。

口令「发布」在 `maintenance:disable` 之后也走本条：关系卡写明了主题才拷贝（无 `--delete`），再 `theme:update`（不得放进维护窗）。单独说「发布主题 / 更新主题」时只走本条，不提交、不推仓、不做核心更新。口令「提交」的 `theme:update` 只重新发布线上已有主题，不上传 `app/design`。

例子（不是规则正文）：「更新汉服主题」对到主题名为 hanfu 的那张关系卡，而不是 SSH 别名 `hanfu`。

宿主镜：`~/.cursor/rules/theme-update-matches-site-cabinet.mdc`。站柜动作细则：`websites/SKILL.md` 模式 D。

## 10. WLS 自启/健康单元只认代码生成（硬 · `wls_autostart_units_generated_and_probed`）

`/usr/local/sbin/weline-wls-p<hash>-*.sh` 与 `/etc/systemd/system/weline-wls-*` 是 `LinuxSystemdAutostartPlanner` 的**生成物**，禁止手改；生成物过期就重新生成（脚本 + 单元 + 指纹），再 `bash -n` + `systemctl daemon-reload` + `reset-failed`。

| 已实测的过期形态 | 后果 |
|---|---|
| 旧 `run_w` 把参数拼进 `bash -c "…"` | 内层拿不到 `$PROJECT/$PHP` → `exec: : not found` / 引号 EOF → systemd `exit 2/127`，站点重启后起不来 |
| 健康探针端口写死（曾 `9510`，实际 `16420`/`16314`） | 永久 `missing :<port>` → 每 5 分钟判 unhealthy 并反复 `systemctl start` |
| 健康脚本探针沿用旧端口 | 站点在跑也被判死，日志噪音掩盖真故障 |

| 允许 / 必须 | 禁止 |
|---|---|
| 起站且要单元状态一致：先 `server:stop <inst>`，再 `systemctl start <unit>` | `systemctl enable --now <oneshot 自启单元>`（会立刻执行一次 `server:start` 撞运行中实例；实测瞬时 502 + worker 重建） |
| 探活只用 `server:status` / `curl 127.0.0.1:<port>` | 拿 `server:start` 当探活 |
| `server:start` 前确认运行时产物新鲜（`framework:compile` / `setup:upgrade` 已跑完） | 编译产物过期仍起站（会报「WLS 运行时产物预检失败：框架编译产物缺失或已过期」并拒起） |

## 11. 过载机先取宿主证据，再谈前端优化（硬 · `host_pressure_before_frontend_tuning`）

「LCP 重 / 站点慢」先取机器证据：`uptime`（load vs `nproc`）、`/proc/pressure/cpu`、`/proc/pressure/io`、`ps -eo pcpu --sort=-pcpu`、各站 worker 数。

| 判定 | 动作 |
|---|---|
| load ≈ 3×核数 且 PSI `some` > 50%（实测 8 核 load 30+、cpu some 71%、io some 48%） | 属宿主资源竞争，TTFB 20–50s 不靠前面的 CSS 优化解决；先收敛 worker/cron 配额再复测 |
| 过载期间 | **禁止**跑全量静态同步（`deploy:upgrade` 起 `pool=N` 复制全模块；实测把 load 22→34、io some 48→73，三站一起拖到不可用）；卡死即 `kill` 并保留现场、事后如实说明 |
| 单页验证 | 走源站 loopback（`127.0.0.1:<port>` + `Host`）；本机 curl 公网域名可能经 VPN/代理（`198.18.x.x` 假 IP、`SSL_ERROR_SYSCALL`），不得据此判定站点不可用 |

## 12. 备份前先读技能、只留一个版本、先查空间（硬 · `backup_requires_skill_keep_one_and_space_precheck` · 2026-10-29 用户指定）

**任何备份动作**（站点库 dump / 部署快照 / `var/backup` tar / 库拷贝 / release 保留 / cron 定时备份）写盘**之前**必须按序过三步：

| 步 | 要求 | 命令/依据 |
|---|---|---|
| ① 读技能 | 先读 {`weline-server-housekeeping`、`weline-deploy`、`websites/<site>/SKILL.md` + `server.md`、[deploy-backup-retention-and-disk-guard.md](../../Deploy/doc/开发/spec/deploy-backup-retention-and-disk-guard.md)}，按条款定路径/命名/保留数 | `skill weline-server-housekeeping` / `skill weline-deploy`；柜子文件原文 |
| ② 只留一个版本 | 快照/部署备份**只保留上一个版本**；同名备份不得多代堆积 | 柜子「保留策略」；删除须列清单 |
| ③ 先查空间 | `df` 目标卷余量 ≥ 预估产物体积（留安全余量）；不足则**先按清理技能清完再备份** | `df -h <卷>`；`weline-server-housekeeping` dry-run → 清单 → 删 |

**禁止**：不读技能自造备份路径；同一备份堆多版本；盘将满仍硬备份；备份把盘写满导致 PostgreSQL/WLS 起不来；未经柜子许可删生产备份。

**事故依据（2026-10-29 aiweline.com）**：cron 驱动的 `amayum/var/backup/deploy/*.tar.gz`（单次 891,588,608 B）把 40G 盘重新写回 0 余量 → PostgreSQL `FATAL: could not write init file: No space left on device` 被打死 → WLS 起不来 → 店面 502。**盘满 = 服务中断**，不是存储细节。
