# 规则 10 · 工程流程与验收

> 分册正文。上位索引 [AI硬规则索引.md](../AI硬规则索引.md)。动作**顺序**权威是 [AI工程交付流程.md](../AI工程交付流程.md)；本册只规定各阶段的**硬门禁条文**（做什么 / 禁止什么 / 怎么验证）。

## 0. 阶段总览

```text
0 会话引导        ensure → prepare_project → 遵守 hard_constraints
1 定位与需求确认  需求.md / 用户确认 / 会话笔记（临时）
1b 澄清与用例规格 doc/开发/spec/{slug}.md（EARS + UC；feature 硬）
1c 宿主计划模式   Agent 自行 Plan Mode；简单可 skip（仍须验收）
2 扩展点选型      扩展点选型.md → 文档索引 / doc/event / Query / Hook
3 计划拆解        会话计划笔记（仍在 Plan Mode）→ 自审通过后切 Agent
3b 工程团队       非简单：一席一智能体 / SESSION / contracts+deps / 对齐冻结
4 实现            计划自审通过后切回 Agent；宿主原生编辑 + TDD
5 复审            架构/缺陷/安全 + 每触发专席合规复审（fail→返工）
6 分层测试        单测 → 运行时 → WebUI；UI 须先 UI+原型过签
7 收口            文档对齐 + 门禁表 + 交付地址 + 汇审
```

## 1. 需求澄清与用例规格（`requirement_clarify_use_case_spec`，硬门槛）

写码前必须执行 [需求澄清与用例规格.md](../../../../../../dev/ai-command/ai/需求澄清与用例规格.md)（或 `get_skill(requirement_clarify_use_case|weline-req-clarify)`）。

- `work_kind=feature`：落盘归属模块 `doc/开发/spec/{feature-slug}.md`，含澄清记录、用户故事、≥2 条 EARS（WHEN/IF…SHALL）、≥1 用例（主成功路径可映射 `type=e2e` / Browser WB-OP），每条 UC **必须**填写映射 acceptance id，`status` 升至 `ready-for-plan` 后才进入审视与架构。
- `non_feature`：可 `clarify_status=skipped` + ≥24 字理由。
- **禁止**一句话需求直接改 PHP/phtml。规格须含澄清记录 + 用户故事 + EARS + UC。

### 1.1 需求用例闭环验收（`requirement_use_case_closed_loop_acceptance`，硬门槛）

**用户口径**：任何会改变产品行为的用户工程需求，都必须用例闭环验收——不限于 `work_kind=feature` 标签。**闭环一定是实际真机测试闭环**（本机 Browser WB-OP 和/或正式 Playwright e2e），禁止仅用 unit/CLI/runtime 探针冒充 UC 闭环。

| 要求 | 禁止 |
|------|------|
| 行为性需求先冻结 `UC-*`（feature → 归属模块 `doc/开发/spec/{slug}.md`；不能 skip 的行为性 non_feature 亦须最小 UC + `covers_use_cases`） | 一句话改码、无 UC 宣称完成 |
| 规格/SESSION 中每条 `UC-*`（主成功必计；已写入的备选/异常同样计）由计划 `acceptance[].covers_use_cases` 覆盖 | 孤儿 UC；仅有任意 e2e PASS、未覆盖 UC |
| **每条 UC 须真机闭环**：covering 项为 `type=e2e`（正式 runner）或 `type=browser` WB-OP（真机点选+可截图则 WB-VIS）；非 simple 优先 e2e；simple 仍须 Browser | 纯 unit/curl/CLI/runtime/CDP evaluate 单独闭环 UC |
| 宣称完成 / 汇审前：覆盖项全部 `passed`+非空**真机** evidence（遵守真实业务通路） | 甩用户关用例；未闭环却写「已完成」；探针 PASS 冒充真机闭环 |
| 未闭环只报「代码已改，需求用例闭环验收未完成」 | — |
| 纯文档/门禁/基建 `non_feature` + clarify skipped（理由≥24）→ N/A；内容运营豁免 | — |

## 2. 需求分析与框架审视（硬门槛）

每条用户需求提出后**立即**先完成 **`request_grade` 分级**（专业工程视角），再对 `engineering` 需求走：澄清规格 → 隐形需求分析 → `work_kind` 判定 → 框架审视 → **架构级参与**（禁止贴补丁）。

| 规则 id | 要求 |
|---------|------|
| `requirement_engineering_grade_gate` | **每条需求**须用专业工程视角判定 `request_grade=engineering\|content_ops\|chat`；`engineering` 必须架构级参与（mechanism+owning_module+not_to_do），**禁止**当补丁/热修捷径；误判会改码却走 chat/content_ops → 必须重判 |
| `requirement_scan_architecture_smell_gate` | 工程需求讨论/分析与扫码时：**AOCI 参与**；扫描需求相关与周边逻辑时**顺带**标架构级 vs 补丁级隐患；疑点用 MCP 读模块 `doc/` 索引对比正确做法；汇报「架构隐患/周边发现」由**用户决定**是否顺带处理——禁止静默扩 scope |
| `requirement_feature_kind_gate` | （仅 `engineering`）必须判定 `work_kind=feature\|non_feature` |
| `requirement_implicit_analysis_skill_decision` | 分析当前环境**隐形需求**（已有 Taglib/API/Model/Provider 表、映射页、拉取/同步、耦合风险等）写入 `implicit_requirements`；禁止「无」式空分析 |
| `requirement_cross_layer_impact_gate` | goal/requirements 命中**实体+字段+变更信号**（如「给订单增加类型」）时 `plan.impact_surfaces` 必填：`subject` + `layers`（`schema_model`/`service_api`/`admin_ui`/`storefront_ui`/`i18n`/`tests_e2e` 等）；`schema_model` 与至少一侧 UI 须 `in_scope` |
| `ui_skill_surface_signal_gate` | 有页面/布局/CSS/主题/.phtml 等视觉信号时**强制** `ui_skill_decision=participate`，禁止错误 skip；`skip` 仅无视觉信号且须写 `ui_skill_rationale`（≥24 字） |
| `feature_add_requires_current_ui_review` | 在既有 Web UI 表面加功能：设计前必须先打开/截取**当前页**并按 [审图](../../../../../../dev/ai-command/theme/审图.md) 审现图再定位置；现页已乱须连同现页重设计 |
| `feature_ui_keep_simple_top_tabs` | 页面分组默认**顶部 Tab**（一屏一个主职责）；次要块用点击展开卡片；密页须同需求改成 Tab |
| `requirement_framework_scrutiny` | 字面需求不合理（耦合写法、有 Taglib 仍手写控件、发明事件、错误分层、过度设计）时**禁止原样照做**，须给更合理做法并写入 `plan.requirement_scrutiny`，同时改写 `plan.requirements` |
| `architecture_first_for_requirements` | 计划须有 `plan.architecture` 必填（≥40 字，`trivial` 亦必填，可由 design 派生） |
| `architecture_design_structured` | `plan.architecture_design` 必填：`mechanism`/`owning_module`/`reuse`/`invent`/`not_to_do`/`req_map`，优先从 `framework_candidates` 选型 |
| `architecture_grade_change_only`（**严重·上下文携带**） | **任何**编码改动（含热修/性能）必须是框架**架构级**修改：动手前写明 mechanism + owning_module + not_to_do；业务数据/路径只落归属模块 Provider·contribution·活索引·env；**禁止**「想怎么写就怎么写」、在 Runtime/编排层硬编码 slug/演示路径。上下文若已看不到本规则/`hard_constraints`，须**重新** `prepare_project` 再改码 |
| `framework_decoupled_only` | 禁止耦合写法；`plan.coupling_findings` 必填（无则「无」/「无耦合」） |
| `runtime_orchestrator_no_business_hardcode` | 见 [规则/30 §6.1](./30-后端与数据.md)：`WlsRuntime` 等编排层零业务硬编码 |

**另必填**：`plan.scrutiny_basis`（`checklist`≥2 + `doc_paths`≥1；仅写「合理」不够）、`plan.requirements`≥1、`acceptance`≥1 且**至少 1 条 `type=unit`**、`dev_tasks`、可选 `scope_paths`/`forbidden`/`risk`/`workflow_phase`。

汇报须含「**需求纠偏**」「**耦合提示**」与「**架构隐患/周边发现**」小节（无调整/无耦合/无隐患也要写明；周边隐患是否一并修由用户裁决）。

**上下文携带（硬）**：`architecture_grade_change_only` / `hard_constraints` 必须经由 `prepare_project` + MCP `mcpInstructions` + alwaysApply coldstart 留在工作上下文；压缩丢失 → 重新 prepare，禁止凭记忆改码。

## 3. 宿主计划模式与计划正文（硬门槛）

### 3.1 `host_plan_mode_for_planning`

进入本阶段（澄清规格 `ready-for-plan` 之后、扩展点选型/架构映射/分章计划期间）**默认必须启用宿主 Plan Mode**。Cursor：**Agent 自行** `SwitchMode` → `target_mode_id=plan`（**禁止**停下来请用户「点击/进入计划模式」），在 Plan Mode 内完成 `architecture_design`、扩展点、章节/`dev_tasks`、`acceptance`；**禁止**在计划阶段改业务 PHP/phtml/CSS。计划正文写完后走 §3.1b，**不再**以「用户明确批准实现」为开工门禁。

**简单需求可跳过**：同时满足时可记 `plan_complexity=simple` + `plan_skip_rationale`≥24 字——单模块、无新建扩展点发明、无多章计划、约 ≤2 小时/单表面、前后端架构无歧义。**跳过计划 ≠ 跳过验收**（`requirement_acceptance_always`）。同一条件走**监工**，不叫团队，对外每句以 `监工:` 开头。

### 3.1b 计划完成后自审再开发（`plan_complete_self_review_then_implement`）

计划正文完成后（含用户已自行切入 Plan Mode 的情形）：

1. **Agent 立即自审**该计划（遵守 `plan_review_three_lenses`：工程化 `plan_review_requires_code_evidence` + 架构 `scheme_requires_architecture_review` + 影响面/AOCI `plan_review_requires_impact_surface`；各视角须实际调用规定工具；证据在前；「是否通过」置尾）——**禁止**把「请你审计划 / 请批准后再开始」当作下一步；
2. **`通过` 或 Agent 可自行消化的 `有条件通过`**：同连续性 `SwitchMode` → `agent`（已在 agent 则继续）并开始实现——**禁止**停等用户点 Build / 批准计划 / 「点击计划才开始」；
3. **`不通过` 或条件需要用户做产品/架构裁决**：停手汇报证据与缺口，不开发；
4. IDE 若对 `SwitchMode` 弹一次模式切换确认，可接受，**不等于**等计划批准；
5. 用户说「先别开发 / 等我看完 / 只要计划」或 Codex opt-in 审批容器路径：仍可等待。

宿主常带：`~/.cursor/rules/plan-complete-self-review-then-implement.mdc`（与 MCP 双写）。

### 3.2 `plan_content_focus_only`

计划正文（Plan Mode / 仓库根 `dev/session/{slug}.md` 会话计划笔记；**禁止**模块 `doc/开发/plan.md`）**只写三块**：

1. **背景**——本题为何、现状缺口；
2. **方案**——要做什么、选定做法（`mechanism`/`owning_module`/`reuse`/`not_to_do` 用短子弹）；
3. **细节**——怎么做：步骤、章节/`dev_tasks`、路径、验收怎么验。

**禁止**：流程目录散文、无关模块巡礼、愿景/价值主张、整套 MCP 工作流复述、旁支功能推销、装饰性总览。必填结构化字段仍要有，但压成上述三节下的短子弹。

### 3.2a 计划审查三视角门禁（`plan_review_three_lenses`）

审查 / 自审 / 点评 / 批准·驳回 / 汇审工程计划时，必须**同时**从以下三个独立视角完成审查，并**实际调用**各视角规定的工具/探测；缺任一视角 → **禁止**给「通过」。

| 视角 | 硬规则 | 必须触发什么 |
|------|--------|--------------|
| **工程化** | `plan_review_requires_code_evidence`（§3.2b） | 读计划正文 + 探测当前磁盘代码（Read/Grep/探索）；验证路径、符号、步骤、验收是否可落地；禁止空想 |
| **架构** | `scheme_requires_architecture_review`（§3.2d） | 核对 `mechanism` + `owning_module` + `not_to_do`≥1；判定架构级 vs 补丁级；禁止热修捷径式方案过审 |
| **影响面** | `plan_review_requires_impact_surface`（§3.2c） | 划定 IOC/爆炸半径与隐患；会话有 AOCI 时**必须先**实际调用 `aoci_search` / `aoci_get_entries`，再级联 Weline MCP → 宿主原生 |

面向用户须**分视角**出示证据（工程化发现 / 架构清单 / AOCI 证据或 `aoci_unavailable` + blast radius 与隐患）；「是否通过」置尾（`user_facing_verdict_last`）。本条是伞规则，**不替代** §3.2b/§3.2c/§3.2d 正文。

宿主常带：`~/.cursor/rules/plan-review-three-lenses.mdc`（与 MCP 双写）。

### 3.2b 审查计划须证据（`plan_review_requires_code_evidence`）

审查 / 点评 / 批准·驳回 / 汇审计划（含 Plan Mode、会话计划笔记、工程团队 `plan_id`、Codex 等产出）时——**工程化视角**（`plan_review_three_lenses`）：

1. **先读计划正文**（背景/方案/细节中的路径、符号、步骤、验收）；
2. **再探测当前磁盘代码**（Read / Grep / 必要探索）——禁止凭记忆或「应该如此」空想；
3. **面向用户先写证据与发现**，证据不足只能写「未探测，暂不结论」；
4. **「是否通过」必须放在全文最后**（`通过` / `不通过` / `有条件通过`）——禁止开篇或中段先下判。

宿主常带：`~/.cursor/rules/plan-review-requires-code-probe.mdc`（与 MCP 双写，见 `global_rules_dual_write_mcp_and_host`）。

本条「是否通过置尾」是更通用硬规则 `user_facing_verdict_last`（面向用户结论置尾，见 [规则/00 §4.2](./00-MCP调用与会话.md)）在计划审查上的特化。

### 3.2c 审查计划须影响面 / IOC（`plan_review_requires_impact_surface`）

与 §3.2a / §3.2b **同时**生效（自审 / 审查 / 汇审工程计划时）——**影响面视角**（`plan_review_three_lenses`）：在代码证据之外，必须做 **IOC（Impact of Change）**——划定**影响面（爆炸半径）**（计划碰到哪些地方、哪里可能出问题）并汇报**隐患**。

级联探测（须标明本回合实际用到的 tier：`aoci` / `mcp` / `native`）：

1. **必须先实际调用 AOCI**（会话有 `aoci` 工具时）：审查回合内 **MUST** 调用 `aoci_search` / `aoci_get_entries`（scoped；**禁止**每次审查都强制整库 Whole-Index Overview）。**禁止**跳过 AOCI、只用宿主 Read/Grep 就宣称已审影响面；
2. **仅当真实 AOCI 调用为空/失败，或 AOCI 不可用**（须写 `aoci_unavailable:<原因>`）→ Weline MCP：`search_project_knowledge` / `resolve_task_context` / `get_indexed_document`；
3. **MCP 也不可用 → 宿主原生**：Read / Grep / 必要探索。

面向用户须先写：AOCI 证据（工具+查询+关键 hit/entry id）或 `aoci_unavailable` → blast radius（模块/路径/符号/契约/测试面）+ 架构级 vs 补丁级隐患；隐患**只汇报、由用户裁决是否扩修**——禁止静默扩 scope。计划点名会改码/改耐久文档，但三级均未得到可用影响面证据 → 只能写「未探测影响面，暂不结论」，**禁止**给通过。

不替代 §3.2b 的代码探测，也不替代计划撰写时实体+字段的 `requirement_cross_layer_impact_gate` / `impact_surfaces`。

宿主常带：`~/.cursor/rules/plan-review-requires-impact-surface.mdc`（与 MCP 双写；`plan-review-requires-code-probe.mdc` 交叉引用本条）。

### 3.2d 任何方案须架构式审查（`scheme_requires_architecture_review`）

与 §3.2a / §3.2b / §3.2c **同时**生效（正式计划审查时为本伞规则的**架构视角**）；并覆盖 **simple 跳过正式计划** 时的口头/简写实现方案：

1. **范围**：Plan Mode / 会话计划笔记 / 工程团队 `plan_id` / Codex 计划，以及任何会改码或改耐久文档的实现方案（含 `plan_complexity=simple`）；
2. **架构式审查清单**：须核对 `mechanism` + `owning_module` + `not_to_do`≥1（多需求时 `req_map`），并判定架构级 vs 补丁级——**禁止**批准或开工「想怎么写就怎么写 / 热修捷径」式补丁方案；
3. **正式计划**：自审/审查须与代码证据、影响面三联；**simple 跳过**：动手前仍须留下紧凑 `architecture_review` + 置尾结论；
4. 结构不全或补丁级 → `不通过` / `有条件通过`，改写为架构级前 **禁止** Write。

宿主常带：`~/.cursor/rules/scheme-requires-architecture-review.mdc`（与 MCP 双写）。

### 3.2e 计划可实施清单（`plan_implementability_checklist`）

在 **仍只写三壳**（`plan_content_focus_only`）的前提下，强化「细节」可落地性——把企业级可行性/NFR/LLD/环境/里程碑/发布回滚**压成短子弹**，**禁止**另开「阶段一～七 / 1～24」成章散文。映射全文见 [计划可实施清单.md](./计划可实施清单.md)。

| 字段（细节下短子弹） | complex / team | simple / 监工 |
|----------------------|----------------|---------------|
| `feasibility` | 必填（一句结论；可指向 spike） | 可并入 `implementability_simple_skip`≥24 |
| `nfr_or_na` / `nfr_na_rationale`≥24 | 必填 | 同上 |
| `lld_or_na` | 有 schema/API 时写要点；否则 N/A≥24 | 同上 |
| `env_ci` | 本机 `*.test.weline.com` + `e2e:run`/契约命令；禁止虚构 Jenkins | 仍建议一句 |
| `milestones_or_na` | 对齐冻结/代码冻结/提测/发布窗口 | 可 skip 集群 |
| `release_rollback_or_na` | 仅触生产/Deploy 时写；否则 N/A | 可 skip 集群 |
| 路径 / `dev_tasks` / `acceptance` / 真机 UC | 仍必填（行为变更时 UC） | 仍必填 |

**自审绑定（硬）**：`plan_complete_self_review_then_implement` 工程化透镜须核对上表；缺必填 → `不通过`（Agent 可当场补全后重审）；缺清单 **禁止** 进入施工。**禁止**把缺清单绑死「align_freeze 不得 pass」（对齐冻结仍只管 UC+contracts+deps）。聊天仍 `user_facing_brief_plain_report`——清单进计划/SESSION，默认不堆聊天。

宿主常带：`~/.cursor/rules/plan-implementability-checklist.mdc`（与 MCP 双写）。

### 3.3 前后端范围（`requirement_fe_be_scope_analysis`）

每条需求须分析并记录 `fe_be_scope=frontend|backend|both|na` 及各侧要点；**禁止**只做一侧却漏该做的另一侧。

### 3.4 验收不可省（`requirement_acceptance_always`）

宣称完成前必须有真实验收证据。**禁止**在验收未跑通前向用户汇报「已完成 / 已修好 / 可验收 / PASS」等完成态（先测后报）；未测收口只能写「代码已改，验收未完成」。触及 Web/UI 时，即使仅 simple 豁免 Playwright e2e，也必须本机 **真机 Web 测试（WB-OP）**：宿主 Browser 导航 → 工具通道 `browser_click`/`browser_fill`/`browser_press_key` 真点选 → **`browser_take_screenshot` 后宿主 Read 截图文件（视觉）**，按审图清单查裁切/溢出/一字竖排/密度挤压（`acceptance_phase_requires_shentu` / WB-VIS）。**禁止**仅用 curl / 契约 / CDP `Runtime.evaluate` / `getBoundingClientRect` 尺寸数字 / DOM 文本抽取 / Network 拦截 / 只 snapshot 不截图 Read / **拍了截图却不 Read** 冒充 Web 或视觉 PASS。可见裁切等 fail 须**同回合修好**再报 PASS。禁止甩给用户测。

### 3.4a UT≠交付 · 真机用例门禁（`real_machine_usecases_not_unit_tests`）

工程计划与需求交付**必须**列出并在本机真机环境**执行**用例（UC）；**真机 UC 是交付门禁**。契约 / PHPUnit / 静态源码契约**只**锁代码写法与不变量，**不得**冒充需求用例验收或「已完成」。禁止计划漏写 UC；禁止只报「N tests passed / 契约绿」就宣称交付。Web/UI 仍须 Browser WB-OP。收口须**持久化**实测命令/HTTP/截图/库盘抽样（默认自存；用户聊天走简述，除非用户要证据）。特例仅作例子（如词典三分区 UC），不得把特例路径写成规则正文。

**真机实测数据（硬，`automation_test_report_durable_evidence`）**：Agent 跑完自动化/真机验收后，必须**采集并持久化**本回合真机/真跑实测数据（HTTP 状态、墙钟/TTFB、leaf `db_q`/`php_ms`、request id、截图路径与 Read 结论、订单号等——有则必留）。默认按 `user_facing_brief_plain_report`：**自存**（Agent Store / `dev/session/`），用户聊天只给简述；用户明示要「证据/深挖」再贴出。**禁止**无持久化证据却宣称冷测/叶税/店面 PASS；拿不到实测只能写「代码已改，验收未完成」（简述口径），**禁止**暗示 PASS。

布局/人性化/吐槽/审图命中时 `ui_skill_decision=participate`，**原型 + frontend-design 必须参与并调整**（禁止只点评）。

### 4.7 计划合规自检（七维）

收口自检须从以下维度判定计划是否合规，返回 `compliance_dimensions` + gaps：

1. **架构层映射**
2. **解耦**
3. **电商合规**（触及站店渠/商品/结账/支付时须写合规要点，并由**电商顾问**参与；非电商可 N/A）
4. **原型设计**（`ui_skill_decision`；participate→prototype+frontend-design+weline-theme-development+shentu）
5. **e2e 用例完整性**（feature→**每章独立完整功能通路 `type=e2e`** + **计划级 `e2e-plan-suite` 组套件**）
6. **计划体量**（单次宜 2–4 小时；过大须拆章节/child）
7. **逻辑闭环**

**章节硬绑定**（`task_plan_compliance_review` / `chapter_ut_rt_wb_dl` / `plan_full_pathway_e2e_suite`）：`dev_tasks` 须有章节细节（id/title 含 `chN`/`章节`/`chapter`）；**每章必须硬绑定 `acceptance_ids`**；feature 章须含**互不共用**的通路 `type=e2e`，组套件单独一条；多需求须 `covers_requirements` 覆盖全部 requirements；**仅当绑定验收全部 `passed`+evidence 后**才允许该章 `done` 并开下一章（至多一个 `in_progress`）；**全部章完成后统一跑计划组套件 e2e 才可 closeout**。

## 5. 实现与复审

- **实现**：先有需求拆解与架构映射，再宿主原生编辑；**TDD** 红→绿→重构；只改任务授权范围；保留用户无关工作区改动。
- **复审（始终三维）**：架构（模块边界、扩展点是否正确）、缺陷（边界条件、错误路径）、安全（凭据、ACL、输入校验、跨站边界）。
- **专席合规复审**：事件/扩展点/Taglib/Hook/Provider/UI/i18n/ACL/Setup/电商顾问/API 等凡 roster 触发，必须各自 pass；产物 `meetings/{席位}-review.md`（可合并为分节）。任一 fail → 点名返工，不得进入验收。
- **UI 复审**（UI in_scope）：功能在页面上完整可用 + 审美过审图/原型标准。
- **i18n 复审**（文案 in_scope）：`@lang` / `__()` / Taglib 用法、源串简中、CSV、`i18n:collect`。

| `browser_strip_automation_flags` | 开验收 Browser / e2e 须抹掉自动化标志 | 带 `navigator.webdriver`/AutomationControlled 去点人机验证，再把 reCAPTCHA 拦截当 pass |
| `browser_operator_non_preemptive` | WB-OP 等为**虚拟操作面**、默认**非抢占后台**：省略 `position`；不与用户抢焦点/鼠标/键盘 | 默认 `position:active`、有头弹窗、系统级键鼠注入抢 IDE/桌面；后台 ≠ 免测 |
| `browser_cache_disabled_on_open` | 每次打开/导航验收页前禁用 HTTP 缓存（Cursor：`Network.setCacheDisabled` 后 `browser_navigate`；验收 URL **必须**带安装级 `w_fpc_pierce=`（`FpcPierceStamp::buildQuerySuffix()`）；本回合改静态须再加 `_wb_nc=` 并抽检正文；**禁止** `browser_cdp` `Page.reload`；禁止仅 `Runtime.evaluate` 冒充 WB-OP；visitor-path HIT 明示标注时可免穿章） | 用默认磁盘缓存验本回合 CSS/JS/HTML 造成假 PASS；缺穿章导致 FPC HIT 假 PASS；用 `Page.reload`「清缓存」导致整窗重载、智能体全灭 |
| `browser_release_after_delivery` | 写完「交付地址」小节后**立即关闭**本回合全部验收 Browser 标签/webview | 留下空转 Renderer（用户明确要求保留可例外并注明） |
| `browser_operator_fail_closed_release` | 打开前 `curl --max-time` 探活；Browser 超时/无 tab/锁死立即 unlock+关全部验收标签；导航重试≤2 | 无限等待卡住的 ide-browser；错误 Host 仍 `browser_navigate`；跨长 shell 持 lock |
| `forbid_user_manual_test_handoff` | Agent 自动跑测自行闭环 | 请用户测试/刷新再试；只做部分章节不测就汇报完成 |
| `requirement_use_case_closed_loop_acceptance` | 规格每条 UC 经 `covers_use_cases` 映射且全部 passed+evidence | 孤儿 UC；有 e2e 无 UC 覆盖仍宣称完成；甩用户关用例 |
| `chapter_ut_rt_wb_dl` | 每章须 **UT → RT → WB → DL** 四段全 pass 才开下一章；含 Web 的章 WB = WB-OP + WB-VIS；截图存 `doc/evidence/ch{N}/` | curl/单测/纯文字替代 Browser 视觉证据 |
| `no_legacy_code_accumulation_on_change` | 改动=**替换**：被取代的旧实现/死代码/旧分支/新旧**双路径**/废弃类·方法·常量·配置键·DI 注册项/孤儿模板·partial·部件 JSON·Hook·Event·路由·迁移·库列/注释掉的代码/未用 `use`·变量·CSS·JS 声明·i18n 词条/重复平行实现，**必须同一变更集内删除归零**，全仓 grep 被删符号零引用（文档/i18n/注册表同步）；跨模块改契约须迁移孤儿消费方；必须保留的旧路径带 `@deprecated` + 原因 + 删除计划，进 `doc/开发日志.md` 与未完成清单 | 改动**只加不删**、旧实现继续留在仓库跑；老逻辑/兼容分支无限期并存；删符号留**悬空引用**；改契约只删一侧留孤儿消费方；**把遗留物藏进「无」未完成清单**；借「清理」删他席/用户未提交脏改、业务数据或无关 TODO；用 `git checkout/restore/clean/stash` 清场 |

未完成对应层级时，只能报告「代码已改，测试未完成」「WebUI 验收未完成」或「真实通路验收未完成」。

**改动前本地验证 + 上线后线上复验（硬门槛，`local_verify_before_change_and_after_deploy`；仅代码/功能逻辑改动，内容运营不适用）**：

- **动手前判定**：先判定本改动是否触及**逻辑**（分支/边界/错误路径/并发/持久化/注册表/接口契约）。纯文案、样式微调与运营内容不触发本门槛（仍走各自门禁）；逻辑改动一律按下面三段顺序执行，不得跳步。
- **① 本地验证前置（改动落地即验，先于一切外发动作）**：以本机工作区真实执行改动逻辑，按 §6.1 最低证据表取证——纯逻辑=聚焦单测真跑 PASS；命令/API/持久化=真实命令或 API 结果 + 必要单测；含页面=WB-OP 视觉(WB-VIS)+逻辑。**本地未 PASS 之前**：禁止 commit/push 用于发布、禁止部署、禁止向用户宣称完成、禁止把验证推给「上线后再看」/CI/用户。未开始验证只能报「修改已完成，验证未开始」并列出待验证清单。
- **② 上线（生产操作，须用户明确授权）**：仅当用户**明示**线上/生产/预发（线上 / 生产 / ssh weline / aiweline.com / 预发）才执行；动线上之前必须已满足 ① 并留存 evidence，同时确认本机优先、不重置数据库、有回滚路径（`runtime_status_query_local_first`）。**本地未 PASS 不得上线。**
- **③ 上线后线上复验（硬，deployed ≠ verified）**：发布完成后必须在**生产环境**对**同一逻辑通路**再跑一次验证并留可独立回查证据（真实 `order_uuid`/`transaction_no`/生产命令结果；含 UI 再走线上 WB-OP）。**部署命令退出码=0 不是验证**；不得用「本地已验证过」替代线上复验。复验未完成或无权限执行时只能报「**已上线，线上复验未完成**」+ 阻塞原因，禁止宣称「已修复/已完成」。

**废弃清理不累积（硬门槛，`no_legacy_code_accumulation_on_change`；仅代码/功能逻辑改动，内容运营不适用）**：

- **改动即替换**：一次改动是**替换**，不是**叠加**。被取代的旧实现必须**同一变更集内**删除——禁止「先留着，以后再删」、禁止「怕出问题先共存」。
- **删除面（本次改动引入或触及的）**：死代码/不可达分支；被取代的老方法·函数·类·Service·常量·配置键·DI/注册项；新旧**双路径**（新路径已生效而旧路径仍在跑，含兼容/回退分支无限期保留）；孤儿模板/partial/部件 JSON/区块/Hook/Event/路由/迁移/无人读取的库列；注释掉的代码块；未用 `use`/变量/属性/参数/CSS 选择器与 Token/JS 模块声明/i18n 词条；同一能力的**重复或平行实现**。
- **收尾核验**：全仓 grep 被删符号**零引用**（调用方、注册、文档、i18n、MCP surface 同一变更集对齐）；跨模块改契约须迁移孤儿消费方（或显式迁移计划），不得只删一侧；涉 Model/路由按 `module_version_bump_gate` 走 `setup:upgrade`。
- **必须保留的旧路径**：显式标注（`@deprecated` docblock / `#[Deprecated]`）+ 原因 + 删除计划，并写入 `doc/开发日志.md` 与收口**未完成清单**；**禁止**让遗留物静默累积，也**禁止**在未完成清单里用「无」掩盖。
- **边界（`preserve_dirty_workspace` 优先）**：本条只约束**本次正在替换的代码**；**不得**以「清理」为名删除他席/用户未提交脏改、无关 TODO/FIXME、数据库行、业务数据或配置，也不授权 `git checkout/restore/clean/stash` 清场。

### 6.3 收口高压线（凡含页面/UI）

1. AI **必须**用**当前宿主可用的真实 Browser**做**真机 Web 测试**（WB-OP）：工具通道真点选 + **截图 + Read 截图审图**（裁切/溢出/密度）；单测 / curl / **仅** CDP `Runtime.evaluate` / 尺寸 metrics / 截图未 Read **不能**替代。
2. **每次打开/导航验收页前必须禁用 HTTP 缓存**。
3. 面向用户的完成/阶段性汇报**末尾必须**有「交付地址」小节（探活过的 http(s) Markdown 链接）。
4. 细则见 [WebUI浏览器验收与交付地址门禁.md](../../../Framework/doc/3-开发/WebUI浏览器验收与交付地址门禁.md)。

### 7.1 本机默认 Host（硬）

`{project_hash}.test.weline.com`（例：`http://p05113ef3.test.weline.com:9555/...`）。

**禁止**把 `*.weline.test`（例 `p05113ef3.weline.test`）当主验收 Host（即使 `/etc/hosts` 也解析）；仅当不存在可用的 `*.test.weline.com` 时才用 `127.0.0.1`。本机常为 http，勿伪造 https。

### 7.2 交付地址分组

- **前台 / 后台主验收**：每行一条可直接打开的 http(s) Markdown 链接。
- **API / Query**：`w_query` 资源名、路由或 `php bin/w http:request` 可复现示例。
- **纯逻辑**：对应表面写 `N/A`，并给出 CLI 命令或接口入口。

交付前须探活；探活失败不得交付可点击死链。写完本小节后执行 **交付后关闭 Browser**（`browser_release_after_delivery`），再结束收口。同步 `doc/开发日志.md`：门禁表、阶段变化、证据路径（含响应式断点证据路径与 URL 清单）。需求变更写入 `需求.md`（需用户确认）。commit / push / 部署仅在有明确授权时执行，且**必须先过本地验证**；涉及线上的变更按 `local_verify_before_change_and_after_deploy` 走「本地 PASS → 授权上线 → 线上复验」三步，缺任一环不得报完成。

## 8. 计划 / 进度汇报（多 todo）

- 对每个 todo 给出路径 / DB / 命令 / Browser 证据。
- 部分完成须列「未完成清单」并写入 `doc/开发日志.md`。
- 虚报完成属硬违规。
