# 规则 10 · 工程流程与验收

> 分册正文。上位索引 [AI硬规则索引.md](../AI硬规则索引.md)。动作**顺序**权威是 [AI工程交付流程.md](../AI工程交付流程.md)；本册只规定各阶段的**硬门禁条文**（做什么 / 禁止什么 / 怎么验证）。

## 0. 阶段总览

```text
0 会话引导        ensure → prepare_project → 遵守 hard_constraints
1 定位与需求确认  需求.md / 用户确认 / 会话笔记（临时）
1b 澄清与用例规格 doc/开发/spec/{slug}.md（EARS + UC；feature 硬）
1c 宿主计划模式   默认 Plan Mode；简单可 skip（仍须验收）
2 扩展点选型      扩展点选型.md → 文档索引 / doc/event / Query / Hook
3 计划拆解        plan.md + task.md（或任务笔记；仍在 Plan Mode）
3b 工程团队       非简单：一席一智能体 / SESSION / contracts+deps / 对齐冻结
4 实现            用户批准后切回 Agent；宿主原生编辑 + TDD
5 复审            架构/缺陷/安全 + 每触发专席合规复审（fail→返工）
6 分层测试        单测 → 运行时 → WebUI；UI 须先 UI+原型过签
7 收口            文档对齐 + 门禁表 + 交付地址 + 汇审
```

## 1. 需求澄清与用例规格（`requirement_clarify_use_case_spec`，硬门槛）

写码前必须执行 [需求澄清与用例规格.md](../../../../../../dev/ai-command/ai/需求澄清与用例规格.md)（或 `get_skill(requirement_clarify_use_case|weline-req-clarify)`）。

- `work_kind=feature`：落盘归属模块 `doc/开发/spec/{feature-slug}.md`，含澄清记录、用户故事、≥2 条 EARS（WHEN/IF…SHALL）、≥1 用例（主成功路径可映射 `type=e2e` / Browser WB-OP），`status` 升至 `ready-for-plan` 后才进入审视与架构。
- `non_feature`：可 `clarify_status=skipped` + ≥24 字理由。
- **禁止**一句话需求直接改 PHP/phtml。规格须含澄清记录 + 用户故事 + EARS + UC。

## 2. 需求分析与框架审视（硬门槛）

每条可执行编码/工程需求提出后**立即**完成：澄清规格 → 隐形需求分析 → `work_kind` 判定 → 框架审视。

| 规则 id | 要求 |
|---------|------|
| `requirement_feature_kind_gate` | 必须判定 `work_kind=feature\|non_feature` |
| `requirement_implicit_analysis_skill_decision` | 分析当前环境**隐形需求**（已有 Taglib/API/Model/Provider 表、映射页、拉取/同步、耦合风险等）写入 `implicit_requirements`；禁止「无」式空分析 |
| `requirement_cross_layer_impact_gate` | goal/requirements 命中**实体+字段+变更信号**（如「给订单增加类型」）时 `plan.impact_surfaces` 必填：`subject` + `layers`（`schema_model`/`service_api`/`admin_ui`/`storefront_ui`/`i18n`/`tests_e2e` 等）；`schema_model` 与至少一侧 UI 须 `in_scope` |
| `ui_skill_surface_signal_gate` | 有页面/布局/CSS/主题/.phtml 等视觉信号时**强制** `ui_skill_decision=participate`，禁止错误 skip；`skip` 仅无视觉信号且须写 `ui_skill_rationale`（≥24 字） |
| `feature_add_requires_current_ui_review` | 在既有 Web UI 表面加功能：设计前必须先打开/截取**当前页**并按 [审图](../../../../../../dev/ai-command/theme/审图.md) 审现图再定位置；现页已乱须连同现页重设计 |
| `feature_ui_keep_simple_top_tabs` | 页面分组默认**顶部 Tab**（一屏一个主职责）；次要块用点击展开卡片；密页须同需求改成 Tab |
| `requirement_framework_scrutiny` | 字面需求不合理（耦合写法、有 Taglib 仍手写控件、发明事件、错误分层、过度设计）时**禁止原样照做**，须给更合理做法并写入 `plan.requirement_scrutiny`，同时改写 `plan.requirements` |
| `architecture_first_for_requirements` | 计划须有 `plan.architecture` 必填（≥40 字，`trivial` 亦必填，可由 design 派生） |
| `architecture_design_structured` | `plan.architecture_design` 必填：`mechanism`/`owning_module`/`reuse`/`invent`/`not_to_do`/`req_map`，优先从 `framework_candidates` 选型 |
| `framework_decoupled_only` | 禁止耦合写法；`plan.coupling_findings` 必填（无则「无」/「无耦合」） |

**另必填**：`plan.scrutiny_basis`（`checklist`≥2 + `doc_paths`≥1；仅写「合理」不够）、`plan.requirements`≥1、`acceptance`≥1 且**至少 1 条 `type=unit`**、`dev_tasks`、可选 `scope_paths`/`forbidden`/`risk`/`workflow_phase`。

汇报须含「**需求纠偏**」与「**耦合提示**」小节（无调整/无耦合也要写明）。

## 3. 宿主计划模式与计划正文（硬门槛）

### 3.1 `host_plan_mode_for_planning`

进入本阶段（澄清规格 `ready-for-plan` 之后、扩展点选型/架构映射/分章计划期间）**默认必须启用宿主 Plan Mode**。Cursor：立即 `SwitchMode` → `target_mode_id=plan`，在 Plan Mode 内完成 `architecture_design`、扩展点、章节/`dev_tasks`、`acceptance`；**禁止**在计划阶段改业务 PHP/phtml/CSS。用户明确批准实现后，再 `SwitchMode` → `agent` 进入 §5。

**简单需求可跳过**：同时满足时可记 `plan_complexity=simple` + `plan_skip_rationale`≥24 字——单模块、无新建扩展点发明、无多章计划、约 ≤2 小时/单表面、前后端架构无歧义。**跳过计划 ≠ 跳过验收**（`requirement_acceptance_always`）。同一条件走**监工**，不叫团队，对外每句以 `监工:` 开头。

### 3.2 `plan_content_focus_only`

计划正文（Plan Mode / `doc/开发/plan.md` / 会话计划笔记）**只写三块**：

1. **背景**——本题为何、现状缺口；
2. **方案**——要做什么、选定做法（`mechanism`/`owning_module`/`reuse`/`not_to_do` 用短子弹）；
3. **细节**——怎么做：步骤、章节/`dev_tasks`、路径、验收怎么验。

**禁止**：流程目录散文、无关模块巡礼、愿景/价值主张、整套 MCP 工作流复述、旁支功能推销、装饰性总览。必填结构化字段仍要有，但压成上述三节下的短子弹。

### 3.3 前后端范围（`requirement_fe_be_scope_analysis`）

每条需求须分析并记录 `fe_be_scope=frontend|backend|both|na` 及各侧要点；**禁止**只做一侧却漏该做的另一侧。

### 3.4 验收不可省（`requirement_acceptance_always`）

宣称完成前必须有真实验收证据。触及 Web/UI 时，即使仅 simple 豁免 Playwright e2e，也必须本机 Browser **WB-OP**：视觉（可截图则 WB-VIS）+ 真机点选逻辑；curl/CDP 不能替代。

布局/人性化/吐槽/审图命中时 `ui_skill_decision=participate`，**原型 + frontend-design 必须参与并调整**（禁止只点评）。

## 4. 工程团队（复杂才自己选 team）

### 4.1 模式选择（`engineering_team_for_new_requirements`，硬门槛）

父会话**自己选模式**，不必等用户开口。

| 模式 | 触发 | 前缀 |
|------|------|------|
| 监工 | 简单需求 | 每句 `监工:` |
| 工程团队 | 非简单 | 父会话**仅** `Team:项目经理:` |

- 其余席位**必须是真实子智能体**（`one_seat_one_agent`）；**禁止**父会话换前缀扮演。转述子智能体结论时才出现 `Team:架构师:` 等前缀。
- 席间经 `channel/{thread}.md` + resume **互聊**（`peer_talk_via_channel`）。
- 项目经理 = **SESSION 记账 + 计划生命周期主人 + 交换机**（DoD 检查，不替代专席技术复审）。
- 细则：[工程团队.md](../../../../../../dev/ai-command/ai/工程团队.md)。
- **免除**：内容运营（产品优化/详情优化/翻译优化/主图优化/新建文章/规格修复）两种前缀都不用。

### 4.2 需求会话总控（`requirement_session_dashboard`）

立项即建仓库根 `dev/session/{slug}.md`（与归属模块 `doc/开发/spec/{slug}.md` 同 slug；模板 [requirement-session.md](../../../../../../dev/ai-command/ai/templates/requirement-session.md)）。集中阶段、计划项进度、未完成清单、审查索引、交付通知日志；**仅 PM/监工维护**。

**禁止**写入模块 `doc/`（`module_doc_forbids_ephemeral_work_artifacts`）。**无 SESSION 不得施工**；未完成清单非「无」不得宣称完成。

### 4.3 项目经理计划生命周期（`pm_plan_lifecycle`）

审缺口 → 派人 → 监控 → 席位交付必 `notify_pm` → PM DoD 检查并更新 SESSION → 按 deps 唤醒（已满足 deps 可并行）→ 等测试通知 → PM 复检 → 关计划项。发现须开子 `plan_id` 跟到测试+复检闭环；返工记 SESSION 再拉人循环；**全部 closed + 汇审通过**才汇报。

### 4.4 发起方盯验收（`requirement_issuer_owns_acceptance`）

escalate / `dev_ask` 的**发起席不得甩手**：须 `waiting_acceptance`，在进度节点 resume 并读 PM 进度后写 `issuer_acceptance`。**缺发起方签收不得关项、不得汇审宣称完成。**

### 4.5 席位专项技能镜（`seat_skill_mirrors`）

每席子智能体提示 = **通用骨架 + 该席增量**；开工前必须 `get_skill` / Read 本席 MCP 技能与权威文档。

| 席位 | 必挂技能 / 文档 |
|------|-----------------|
| 前端 | `frontend_development` + Taglib/Theme |
| 事件 | `event_extension` |
| API | `api_sdk_development` + API接口开发规范 + BinQuery Provider开发指南 |
| 支付 | `payment_development` + payment-shell + provider-development（改完必拉测试席真浏览器过触及支付全流程） |
| 数据分析 | `visitor_data_analytics` + 技能引用 `frontend_development`+`taglib_ui_control` + 像素指南（整模块 Visitor；≠通用事件席；GTM/GA4 互斥+去重） |
| 性能检查 | `performance_check` + 统一缓存范围与性能优化（设计检查+开发后复审） |
| 电商顾问 | `ecommerce_advisor` + 电商顾问.md（**禁写码**；联网政策；合并原合规） |
| 主题开发 | `frontend_development`（薄 `theme_development`）+ 主题开发.md；开工声明 `work_mode` |
| 部件开发 | `widget_development` + 部件开发指南.md |
| 翻译 | `translation_engineer` + `template_i18n` + `module_i18n_csv` + 翻译工程师.md + 模块翻译CSV规范.md |
| 提示词优化 | `prompt_optimization` + 提示词优化.md + 工程团队.md |
| 后端 | 模块开发指南 + 升版门禁 |

**禁止只发通用骨架**；**禁止席位未 get_skill 本席文档就写码**。

### 4.6 团队运作硬条

| 条 | 要求 | 禁止 |
|----|------|------|
| **框架优先** | 需求/设计/施工/复审先映射框架机制与组件，再谈业务补丁 | 绕过框架直接写业务补丁 |
| **全专席双轨** | 凡触发专席 = 施工轨 + 合规复审轨；复审 fail → 返工 | 带病进验收 |
| **流水线流动**（`team_flow_on_contracts`） | 立项会后开**对齐冻结会**（测试主持）：先钉可执行 UC + `contracts.md` + `deps.md`，再技术方案定稿与施工；按依赖**唤醒并发**；验收只执行已冻用例 | 「开发完才补主路径用例」；全员空等终点 |
| **组件协商**（UI in_scope） | 优先复用 `w-*` / Taglib / Widget；不足须**原型 ∥ UI**（±主题）真实子智能体通道互聊写入 `component-negotiate.md` 后再扩展 | 未协商就扩展组件 |
| **先审后测**（`ui_prototype_gate_before_test`） | **UI** 写 `acceptance-ui.md`、**原型** 写 `acceptance-prototype.md` 亲自对照活页审查（有否决权）；**两席都 pass 后**测试席才执行 e2e/WB；测试 pass → PM 汇审 → 才可汇报 | e2e 全绿代替 UI/原型门禁或 PM 汇审 |
| **发现问题拉起 PM**（`findings_wake_pm`） | 专席一找出问题立刻 escalate + `@项目经理：请立刻组队解决`；PM 同回合组队并落 SESSION 计划项 | 用 Issue 任务列表；找出问题不 escalate |
| **本机测试账号**（`local_dev_test_accounts_self_serve`） | 后台默认 **admin / admin**；前台自建测试顾客 | 向用户索要账号密码或「请你登录验证」 |
| **并发** | 仅 team 模式，且文件/扩展点不重叠、contracts+UC 已冻结、本席依赖已满足 | 重叠文件并行改 |
| **上报与停工** | 跨轨或硬规则问题必须上报并开会（通道互聊）；无人能拍板或重大架构矛盾 → 停工汇报，确认前禁止改 PHP/模板/CSS | 重大矛盾不停工就继续改 |
| **纪要** | 仅 team 模式写入 `dev/team/{slug}/`（`roster.md` / `channel/` / `surfaces.md` / `components.md` / `contracts.md` / `deps.md` / `{席位}-review.md`） | 写入模块 `doc/开发/team/` |

子智能体回报完成**不是**交付；进度以 SESSION 为准。

### 4.7 计划合规自检（七维）

收口自检须从以下维度判定计划是否合规，返回 `compliance_dimensions` + gaps：

1. **架构层映射**
2. **解耦**
3. **电商合规**（触及站店渠/商品/结账/支付时须写合规要点，并由**电商顾问**参与；非电商可 N/A）
4. **原型设计**（`ui_skill_decision`；participate→prototype+frontend-design+weline-theme-development+shentu）
5. **e2e 用例完整性**（feature→**每章独立完整功能通路 `type=e2e`** + **计划级 `e2e-plan-suite` 组套件**）
6. **计划体量**（单次宜 2–4 小时；过大须拆章节/child）
7. **逻辑闭环**

**章节硬绑定**（`task_plan_compliance_review` / `chapter_ut_rt_wb_dl` / `plan_full_pathway_e2e_suite`）：`dev_tasks` 须有章节细节（id/title 含 `chN`/`章节`/`chapter`）；**每章必须硬绑定 `acceptance_ids`**；feature 章须含**互不共用**的通路 `type=e2e`，组套件单独一条；多需求须 `covers_requirements` 覆盖全部 requirements；**仅当绑定验收全部 `passed`+evidence 后**才允许该章 `done` 并开下一章（至多一个 `in_progress`）；**全部章完成后统一跑计划组套件 e2e 才可 closeout**。

## 5. 实现与复审

- **实现**：先有需求拆解与架构映射，再宿主原生编辑；**TDD** 红→绿→重构；只改任务授权范围；保留用户无关工作区改动。
- **复审（始终三维）**：架构（模块边界、扩展点是否正确）、缺陷（边界条件、错误路径）、安全（凭据、ACL、输入校验、跨站边界）。
- **专席合规复审**：事件/扩展点/Taglib/Hook/Provider/UI/i18n/ACL/Setup/电商顾问/API 等凡 roster 触发，必须各自 pass；产物 `meetings/{席位}-review.md`（可合并为分节）。任一 fail → 点名返工，不得进入验收。
- **UI 复审**（UI in_scope）：功能在页面上完整可用 + 审美过审图/原型标准。
- **i18n 复审**（文案 in_scope）：`@lang` / `__()` / Taglib 用法、源串简中、CSV、`i18n:collect`。

## 6. 分层测试与验收

### 6.1 最低证据表

| 变更表面 | 最低证据 |
|----------|----------|
| 纯函数 / Service 局部 | 聚焦单测 |
| 命令 / API / 持久化 | 真实命令或 API 结果 + 必要单测 |
| Model / Controller / 注册表 | bump `etc/module.php` version + `setup:upgrade` 或 `--route` 成功 |
| i18n CSV / 新增可翻译文案 | **源串默认简体中文** + `zh_Hans_CN.csv` + `en_US.csv` 对齐（**禁止其它 locale CSV**）；用户提到翻译时还须覆盖默认网站已选全部语言（非中英语种进系统词典）+ 中英改动后 `php bin/w i18n:collect` |
| 页面 / 交互 / SSE | 真实 WLS + **当前宿主可用的真实 Browser** 操作员路径（**WB-OP**）+ **截图 + 对照模块 `doc/原型设计.md` 视觉清单（WB-VIS）**；多断点 375 / ≈768 / ≥1024 |
| 文档 / 规则 | Diff、链接、渲染检查；**与实现对照无漂移** |

### 6.2 硬门槛条文

| 规则 id | 要求 | 禁止 |
|---------|------|------|
| `agent_self_verify_before_done` | 实现后 Agent **必须亲自执行**测试命令并按验收层级验证，再标 acceptance / 宣称完成；`unit` 的 `passed` evidence 须含可识别真实跑测输出（phpunit/PASS） | 「只改代码就收口」；`passed/skipped/na` 无 evidence |
| `acceptance_phase_requires_shentu` | `ui_skill_decision=participate` 或含视觉 Browser/UI 验收时，verify 阶段必须对验收截图执行审图（线稿→原型→UI→主题），`acceptance` 须含 `type=shentu` 且 evidence 含审图/线稿/checklist 信号 | 弱证据仍宣称完成；非功能且无 UI 可 `na` 并写明原因 |
| `acceptance_real_business_pathway` | 收口 e2e/WB 必须跑冻结主路径并留下可回查业务证据（如真实 `order_uuid`） | 空 query 取消页 CTA 文案、账户页不 fatal、模板字符串 UT 冒充功能完成 |
| `tester_tests_must_be_real` | 证据须经真实业务栈产生且可独立回查 | 「自造假数据/假响应→再断言假数据→宣称 pass」；证据只存在于测试进程内存 |
| `ui_feature_requires_e2e` | feature 须 Playwright 章 e2e + 收口组套件 PASS | 无章通路 `type=e2e` / 无 `e2e-plan-suite` / 用 skipped 冒充 |
| `e2e_playwright_formal_runner_only` | 仅 `php bin/w e2e:run` 或 `npx playwright test`（仓库 `tests/e2e` 配置） | `node -e` / 临时 `chromium.launch` 探活（易残留无头浏览器） |
| `e2e_playwright_headless_default` | 默认无头 | 默认加 `--headed`/`--ui` 弹 Chromium 干扰桌面（用户明确要求观看才例外） |
| `browser_strip_automation_flags` | 开验收 Browser / e2e 须抹掉自动化标志 | 带 `navigator.webdriver`/AutomationControlled 去点人机验证，再把 reCAPTCHA 拦截当 pass |
| `browser_operator_non_preemptive` | WB-OP 默认**非抢占后台**：省略 `position` | 默认 `position:active` 抢 IDE/对话焦点；后台 ≠ 免测 |
| `browser_cache_disabled_on_open` | 每次打开/导航验收页前禁用 HTTP 缓存（Cursor 先 `Network.setCacheDisabled`，失败则 `Page.reload({ignoreCache:true})`） | 用默认磁盘缓存验本回合 CSS/JS/HTML |
| `browser_release_after_delivery` | 写完「交付地址」小节后**立即关闭**本回合全部验收 Browser 标签/webview | 留下空转 Renderer（用户明确要求保留可例外并注明） |
| `forbid_user_manual_test_handoff` | Agent 自动跑测自行闭环 | 请用户测试/刷新再试；只做部分章节不测就汇报完成 |
| `chapter_ut_rt_wb_dl` | 每章须 **UT → RT → WB → DL** 四段全 pass 才开下一章；含 Web 的章 WB = WB-OP + WB-VIS；截图存 `doc/evidence/ch{N}/` | curl/单测/纯文字替代 Browser 视觉证据 |

未完成对应层级时，只能报告「代码已改，测试未完成」「WebUI 验收未完成」或「真实通路验收未完成」。

### 6.3 收口高压线（凡含页面/UI）

1. AI **必须**用**当前宿主可用的真实 Browser**（IDE Browser / Browser MCP / Playwright 等，**不绑定 Cursor**）**亲自按用例自测**（WB-OP）；单测 / curl **不能**替代。
2. **每次打开/导航验收页前必须禁用 HTTP 缓存**。
3. 面向用户的完成/阶段性汇报**末尾必须**有「交付地址」小节（探活过的 http(s) Markdown 链接）。
4. 细则见 [WebUI浏览器验收与交付地址门禁.md](../../../Framework/doc/3-开发/WebUI浏览器验收与交付地址门禁.md)。

### 7.1 本机默认 Host（硬）

`{project_hash}.test.weline.com`（例：`http://p05113ef3.test.weline.com:9555/...`）。

**禁止**把 `*.weline.test`（例 `p05113ef3.weline.test`）当主验收 Host（即使 `/etc/hosts` 也解析）；仅当不存在可用的 `*.test.weline.com` 时才用 `127.0.0.1`。本机常为 http，勿伪造 https。

### 7.2 交付地址分组

- **前台 / 后台主验收**：每行一条可直接打开的 http(s) Markdown 链接。
- **API / Query**：`w_query` 资源名、路由或 `php bin/w http:request` 可复现示例。
- **纯逻辑**：对应表面写 `N/A`，并给出 CLI 命令或接口入口。

交付前须探活；探活失败不得交付可点击死链。写完本小节后执行 **交付后关闭 Browser**（`browser_release_after_delivery`），再结束收口。同步 `doc/开发日志.md`：门禁表、阶段变化、证据路径（含响应式断点证据路径与 URL 清单）。需求变更写入 `需求.md`（需用户确认）。commit / push / 部署仅在有明确授权时执行。
