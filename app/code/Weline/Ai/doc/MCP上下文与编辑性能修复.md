# MCP 上下文与编辑性能修复（2026-09-05）

## 问题与改动

1. 指定函数曾固定裁成约 600 tokens，却返回整函数 Hash。现从 SQLite 完整文件内容提取符号：可容纳时返回完整内容，不足时明确 `content_complete=false`、`truncated`、完整范围和所需预算；整符号替换只使用完整内容。
2. 索引默认上限曾为 512 KiB、编辑为 1 MiB，导致合法写入后目标消失但报完成。两者默认统一为 1 MiB，旧配置的有效索引上限覆盖启用的编辑能力；写后/回滚后的索引 Hash 匹配才清除 pending。
3. 指导响应预算曾只数片段，不数工作流、重复别名和封装。现按最终 tools/call JSON 估算；默认只传一次正文、仅保留任务匹配规范。完整规则仍在准备阶段下发。估算采用 Unicode 字符数÷4，不是模型实际计费 token。
4. 每个受保护调用曾全项目发现并 stat 所有文件。现准备/周期更新负责全量发现，已准备会话对显式文件或目录定向刷新；分支和必备文档检查仍逐次执行，锁内写入 Hash 保护仍保留。
5. 插件 `enabled_tools` 漏了 5 个必需工具，且 ensure 用 Cursor 安装状态判断 Codex。生成器与已安装插件目录现为 22 工具，宿主按实际运行环境识别；脚本无法观测当前会话时明确返回未知，源码变化不自动重启整个应用。
6. 统一 JS 模块加载规范，删除与 declare 加载相矛盾的旧 `@static` 指导。

## 实际 STDIO 证据

对当前配置项目，用新的本地 STDIO 进程调用同一诊断需求：3500 预算的响应从 129,117 字符降至 13,583 字符，最终估算 3,396，未超预算。此比较是响应字符量，不声称同等比例的模型计费节省。

独立临时项目完整执行 `prepare_project → submit_task_plan → get_edit_bundle → apply_compact_edit`：11,906 字节输入文件返回 11,882 字节的完整目标方法，真实 PHP 输出 `['after','TAIL_MUST_REMAIN']`；编辑状态 validated，随后 rollback 恢复原文件。原缺陷复现中同一方法只返回约 2,404 字节、尾部未展示。

修复后当前项目同一 STDIO 会话连续读取指定文档：285、337、257 ms。该次源码变动后的首次 prepare 为 73.6 秒，目录上下文调用 6.1 秒，均如实保留。实时耗时受并行任务、首次重索引和目录范围影响；这些采样不是全链路 Agent 写代码耗时，也不代表所有项目的稳定速度。首次建立索引及到期的全量发现仍需扫描，优化不跳过必要的内容校验。
